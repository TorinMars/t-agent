## Architecture notes (must read before changing code)

**Frontend data-source mode** (the core of v2.29.0)
- `public/js/tasks.js`: the local Client and each remote Engine is a "data source" (the `sources` Map) sharing one UI. The tasks of the current data source are in `tasks` / `selectedId`, and `activateSource(key)` switches.
- Request base path: local `/api/tasks`, remote `/api/remote-servers/:id/tasks`, built with `taskUrl()`; the localStorage keys use `storageId()` (local keeps the original key names, remote ones carry a `remote:ID:` prefix); the terminal cache key is `[sourceKey, taskId, terminalId]`.
- Capability switches: `can('documents:write')` and so on. For local, `caps === null` means everything is available; for remote, `Engines` reads `GET /api/remote-servers/:id/info` and then calls `Tasks.setSourceAccess()`, and a `readonly` role loses the write capabilities. A remote data source is an empty set (treated as read-only) until its capabilities are known.
- `public/js/engines.js` (the global `Engines`, replacing the deleted `remote-tasks.js`): only handles the connection list, engine tabs, pairing, updates, editing/removing connections and the "cannot connect" hint.
- Terminal run state is polled per data source: `public/js/terminal-activity.js` (1.5 seconds for the current data source, 10 seconds for the others).

**Backend**
- The Client's built-in Engine: `routes/engine-v1.js` (`/v1`), service in `services/engine-tasks.js`. The Client proxy is in `routes/remote-servers.js` and stream forwarding in `services/remote-stream.js`.
- The local `routes/tasks.js` and the Engine's equivalent endpoints stay consistent through shared modules: `lib/file-watch-sse.js` and `services/task-assets.js`.
- New Engine capabilities (written to `capabilities` in `/v1/info`, `api_version` stays 1): `tasks:reorder`, `documents:create`, `documents:watch`, `files:assets`, `paths:validate`, `terminal:activity`. When an old Engine lacks them the frontend degrades automatically.
- `test/task-parity.test.js`: the same assertions run against the local routes, the Engine and the Client proxy; add to it when adding endpoints.

## Known limitations / leftovers

- The run state of remote terminals depends on `ta` having been run once on the Engine machine (to sync the hook configuration); when you ssh into a remote machine and then run an Agent, the environment variables do not carry over, so the state can only be judged from output rhythm.
- Agent state decision: with hooks, the hook wins; Esc/Ctrl+C interruptions do not trigger the Stop hook and are covered by "running and silent for 20 seconds"; an Agent without hooks is judged by output (several outputs within 1.5 seconds means running, about 3 seconds of silence means waiting).
- The tables `remote_servers`, `engine_*` and `remote_access_tokens` are kept in old databases and **must not be deleted** (they contain remote connections the user saved). New databases still create these tables.
- There is also an old standalone Engine running in Docker on this server (`node apps/engine/server.js`, running for a long time). The `apps/engine` code has been deleted from the repository, so **rebuilding that image later will fail**; whether to stop it is for the user to decide, so do not touch it on your own.
- The fields `min/max_remote_api_version`, `api_version` and `schema_version` in `VERSION.json` **must not be changed casually**; old clients use them to recognize updates.
- The local `GET /api/tasks/:id/file` has no `Content-Security-Policy: sandbox` (remote files of the Engine and the proxy do). Local behavior is kept as it was; decide separately if it should be unified.

## Working-style reminders (lessons from this round)

- **Before a large deletion, list what will be deleted and have the user confirm.** v2.28.0 deleted by mistake because "standalone Engine" was understood as "the whole Engine feature", and it took a version to restore.
- When cleaning up test processes **do not use fuzzy `pkill -f`**: it matches your own shell and may kill live processes. End them precisely by PID. The live Client is at `/www/wwwroot/t-agent/` (systemd `t-agent.service`); the directory here is a development copy.
- The auto-mode classifier refuses operations that "change the Agent's own configuration" (such as writing `~/.claude` or changing the sync scope of `agent-sync.py`). When refused, stop and tell the user instead of working around it in another way; act after the user explicitly authorizes it.
- Before pushing, check that the version fields agree and run `git diff --check`, stage only an explicit file list, and after pushing verify that `HEAD` and `origin/main` agree.
