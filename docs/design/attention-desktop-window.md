# T-Attention desktop window (macOS)

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

> Code: `services/attention-widget.js` (settings and launcher), `routes/attention-widget.js` (widget API and settings routes), `services/remote-attention.js` (the remote helper shared with the `/api/remote-servers/:id/attention` proxy), `widgets/macos/*.swift` (the native window, entry point `main.swift`), `widgets/macos/strings.json` (its English words), `scripts/h5-shell/AttentionWidgetSettings.jsx` (the settings card), `services/widget-notices.js` and `plugins/notifiers/widget/` (the bubbles), `services/page-channel.js` (the open pages Open session can switch). Tests: `test/attention-widget.test.js`, `test/attention-widget-open-terminal.test.js`, `test/attention-widget-session.test.js`, `test/attention-widget-tick.test.js`, `test/widget-notices.test.js`, `scripts/test-h5-attention-widget-browser.cjs`, `scripts/test-h5-open-terminal-link-browser.cjs`.

A small native AppKit window on the Mac that runs T-Agent. It stays above other windows as a small pill (26 pt high: the unfinished count and a red Needs you badge; `widgets/macos/README.md` has the sizes) and, on hover, a panel (312 x at most 440 pt) with the T-Attention tasks of this machine and of the connected services, with the row actions of the page (Confirm, Reject, Handled), Open link on tasks with a link, Open session on tasks with an agent terminal (`session` of the item), Reply on `waiting_user` rows whose agent terminal is live on this machine, create, edit, delete and drag to reorder. It is a port of the floating window of the older SELF-ATTENTION tracker, and it talks only to this server.

**Launch** (`createWidgetLauncher`). Only when `process.platform === 'darwin'` and the switch is on (the default). After the server listens, `server.js` calls `start({ url })` with the loopback address of the server. Startup never waits for it and it never throws: a failure is one log line (`T-Attention desktop window: ...`) and `last_error`.
- swiftc is found with `/usr/bin/xcode-select -p`, then `/usr/bin/xcrun --find swiftc`. The `/usr/bin/swiftc` stub is never run, because on a Mac without the command line tools it opens the system's install dialog. A missing swiftc is looked for again after 30 s at most.
- Build: `swiftc -O -swift-version 5 -framework AppKit <every widgets/macos/*.swift, sorted by name> -o <data folder>/widget/t-attention-widget.<pid>.tmp`, then a rename to `<data folder>/widget/t-attention-widget`, and a stamp `t-attention-widget.json` with the T-Agent version and the file names. The source is several files along the code's sections, so parallel work merges cleanly; `main.swift` is the entry point (Swift runs top-level code only there; without it the source counts as missing), and `TAttentionWidget.swift`, the single file of v2.132.0 and older that an archive update leaves behind (it copies and deletes nothing), is never built. `createWidgetLauncher({ sourcePath })` builds one file instead (tests). It is rebuilt when the binary is missing, is older than the newest source file, the stamp names another version or another set of files. An old server that still runs the single-file launcher after an update only reports "The window source is missing from this install" (git install) or starts its old binary (archive install) until it restarts into the new one, which builds. Timeout 600 s. A failed build leaves the old binary (or none) and no temporary file.
- Spawn: `t-attention-widget --parent-pid <server pid>`, stdin and stdout ignored, stderr kept (the last 2 KiB, for `last_error`). Environment: only `PATH`, `HOME`, `TA_WIDGET_URL=http://127.0.0.1:<port>` and `TA_WIDGET_TOKEN` (32 random bytes, base64url, new for each spawn, kept only in memory).
- A window that exits on its own (the person chose Quit, or it crashed) is not started again until the switch is turned off and on, or the server restarts. Turning the switch off sends SIGTERM. A graceful shutdown of the server sends SIGTERM too (`process.on('exit')`), and the window also exits by itself when its parent process is gone.
- Never started with `NODE_ENV=test`, `TA_WIDGET_DISABLED=1`, `CI` set (not `false` / `0`), or inside a T-Agent terminal without PM2 (`TA_PEER_TASK` or `TA_HOOK_TOKEN` in the environment and no `pm_id`: a server an agent started there by hand is a test or development copy; a server under PM2 is the real service even when the PM2 daemon was first started from a T-Agent terminal and passed that terminal's variables on). `last_error` then says "Not started: ...". `spawn`, `execFile`, the platform and the environment are injected in tests, so no test opens a window or runs swiftc.

**Auth.** `/api/attention/widget/*` (except `/settings`) is answered by `bearer` in `routes/attention-widget.js`, mounted in `server.js` before the attention Bearer router, the session, the access gate and the login gate. It needs `Authorization: Bearer <TA_WIDGET_TOKEN>` of the window that runs now (compared in constant time; no window, no valid token) and a request from this machine (`fromThisMachine` of `lib/terminal-relay-auth.js`: a loopback peer, no `X-Forwarded-For`, `Forwarded` or `X-Real-IP`). Anything else is `401 WIDGET_TOKEN_INVALID`. It answers every request it takes (an unknown path is a JSON 404) and never passes one on. Answers are JSON with `Cache-Control: no-store`. The window acts as the person (`actor: 'user'`), like the page.

**API.** Keys are `<engine>:<id>`, the engine being `local` or `remote:<remote_servers id>` (ids repeat between engines).
- `GET /items` -> `{ items, engines: [{ key, name, local, color_index }], failed: [<engine name>], host, updated_at }`. Item: `{ key, engine, id, parent_key (same engine) | null, title, status, custom_status, result, attention_reason, pending (context.pending.text or null), link_url, link_label (both as stored, or null), priority, due_date, sort_order, updated_at, created_at, session }`, sorted like the page inside a group (the highest `sort_order` first, then the highest id). `color_index` is the device tag colour of the page (`tagColorIndex` of `task-order.mjs`, FNV-1a of the instance id; -1 without one; ported to the server and checked against the page's function in the test).
- `session` (on every item the API answers with): the T-Agent terminal the item's agent runs in, from `context.tagent` (`{ task_id, terminal_id }`, set by `tieToTerminal` in `services/attention.js` when the agent writes with its terminal token), or `null` when the item has none (or one whose `task_id` is not a positive whole number or whose `terminal_id` is not 1 to 64 of `A-Z a-z 0-9 _ -`): `{ engine, task_id, terminal_id, agent, live, open_path }`. For this machine `agent` is the `task_terminals.agent` of that terminal (`claude`, `codex` or null) and `live` whether its shell runs now (`terminalInfo` in `routes/terminal.js` for one item; for the list, one `task_terminals` query for all items and `liveTerminalIds` in memory, where a shell that is being closed counts until it has ended). A connected service's items come with their whole `context` (its `/v1/attention` rows), so they have a session too, with `agent: null` and `live: null` (not known here). `open_path` is `/?openTerminal=<engine>:<task_id>:<terminal_id>`, the page link below; the window opens it on `TA_WIDGET_URL`, also for a remote item (the page opens that service's terminal itself).
- `POST /items` `{ engine, title, status?, notes?, parent_key? }` -> 201 item.
- `PATCH /items/:key` -> the body of the normal PATCH (status, title, notes, custom_status, result, attention_reason, activity ...), with `parent_key` (same engine, or null) instead of `parent_id` -> item.
- `DELETE /items/:key` -> 204 (409 `HAS_CHILDREN` with `children` passes through).
- `POST /items/:key/move` `{ before_key | after_key | position: 'top' | 'bottom', status? }` -> `{ ok: true }`. A key of another engine is `400 VALIDATION_FAILED` "Target is on another device".
- `POST /items/:key/confirm` (review -> done), `/reject` `{ reason? }` (review -> working, `attention_reason` null, activity note "Rejected: <reason>" or "Rejected"), `/handled` (waiting_user -> working, `attention_reason` null, activity note "Handled"). The item is read on its engine first: `409 WRONG_STATUS` when it is not in the starting status. The notes are the same English sentences the page stores.
- `POST /items/:key/reply` `{ text }` -> `{ ok: true }`: a reply to the agent, typed into its terminal. The text is trimmed and must then be 1 to 4000 characters (`400 VALIDATION_FAILED` "text must be 1 to 4000 characters"); then a `remote:` key is `409 REPLY_REMOTE` "Replies go only to terminals on this machine" (the remote is not asked), an unknown item `404 NOT_FOUND`, an item without `session` `409 NO_SESSION` "This task has no agent terminal", and a terminal without a live shell `409 TERMINAL_NOT_RUNNING` "The agent's terminal is not running". `sendToTerminal` (`routes/terminal.js`) writes it as one bracketed paste (`ESC[200~` text `ESC[201~`; line breaks as `\r`, the other control characters removed, so an `ESC` in the text cannot end the paste), then `\r` alone 150 ms later (Codex takes keys that follow each other quickly as a paste burst, so an Enter in the same write would be part of the text); no Enter goes to a shell that ended meanwhile. Each write counts as the person's input (`activity.noteInput()` and `noteTerminalInput`, as the socket's input does). On success the item gets the activity note "Replied from the desktop window" (actor `user`); its status is not changed.
- `GET /activity` -> `{ terminals: [{ engine: 'local', task_id, task_title, terminal_id, title, agent, state, since, open_path }], updated_at }`: what the agents in this machine's terminals are doing (`liveTerminalActivity` in `routes/terminal.js`). Every live shell (every task) whose activity is not `idle`: `state` is `running`, `waiting` (done at a permission prompt: `awaitingAnswer()`) or `done` (finished, not acknowledged yet); `since` is the ISO time of the last state change (`since()` of `lib/terminal-activity.js`, set on every change; the tracker's start until the first). `task_title` is the task's title, `title` and `agent` are those of the task's terminal list (`listTerminals`: an agent terminal shows its session's name unless the person named it). Sorted running, then waiting, then done, and within a state the newest `since` first; at most 50. Connected services are not included.
- `GET /strings` -> `{ lang: 'en' | 'zh', strings: { "<English>": "<shown>" } }`.
- `GET /prefs` -> `{ hotkeys, dim_when_idle, show_activity }` (booleans, the window preferences of the settings card). A window on a server without `/tick` reads it at start and every 5 s; a 404 (an older server) means all on, tried again after 5 minutes.
- `GET /tick?after=<notice seq>&items=<etag>[&activity=0]` -> `{ etag, list, notices, activity, prefs, updated_at }`: the window's one request every 5 s. `list` is the answer of `GET /items`, or `null` when `items` is the current `etag` (a hash of `items`, `engines` and `failed`; a value that is not 1 to 64 of `A-Z a-z 0-9 _ -` counts as none); `notices` the answer of `GET /notices?after` (same `after` rule, same 400); `activity` the answer of `GET /activity`, or `null` with `activity=0` (the window sends it while `show_activity` is off); `prefs` the answer of `GET /prefs`. The list comes from the kept list below, so a tick in which nothing changed reads neither the database nor a connected service. The old endpoints stay for a window older than `/tick`; `GET /items` reads every part again on every call (and refreshes the kept list).
- Links are opened by the window itself, not through this API. It checks `link_url` again (`taskLink`: http(s) with a host and without a user name or password, or a page path `/...` that is not `//host` and has no backslash or whitespace; anything else is no link) and opens it with `NSWorkspace.shared.open`: an address as it is, a page path on `TA_WIDGET_URL` (this server), also for an item of a connected service, as the page opens it on its own host.
- `GET /notices?after=<seq>` -> `{ seq: <latest seq>, notices: [notices with seq > after, oldest first] }`; without `after` (the window has just started) the notices of the last 60 s. `after` must be a whole number of at least 0 (else `400 VALIDATION_FAILED` "after must be a whole number of at least 0"); an `after` above the latest seq (this server restarted since) counts as no `after`. See "Floating window notices".
- Errors of the owner pass through as `{ error, message, children?, id? }` (this machine's `AttentionError`, a remote's answer through `services/remote-attention.js`). An unknown or disabled `remote:<id>` is `404 ENGINE_NOT_FOUND`.

**Merge rules** (the page's one list, `attentionEngines` in `attention-model.mjs`). This machine and every enabled row of `remote_servers` of the single user that is not hidden in the task list (`hiddenDevices` of `routes/task-list-prefs.js`, the storage of `/api/task-list/hidden-devices`; when every device is hidden, none is). Remotes are read in parallel through `services/remote-attention.js` (the capability `attention:remote` check with its 30 s cache, the same helper as the browser proxy), within 4 s per engine: `?limit=1000&recent_finished=50` (the open items, then the 50 finished last, in one read; the answer says `recent_finished: 50`). A service older than that parameter ignores it, so while it is not known which one a service is (and for an older one) the finished items are read in parallel as before (`status=done,failed,cancelled`, `limit=1000`); the kind is learnt from every answer. An engine that fails or is too slow is named in `failed` (and stays in `engines`); one without T-Attention (501) is left out quietly. When no listed engine has T-Attention (this machine hidden), this machine is shown, as on the page. Finished items (done, failed, cancelled) are cut to the 50 newest by `completed_at` across all engines. This machine's part is one call of `list({ limit: 1000, recentFinished: 50 })`. Unlike the page, an engine whose last state is offline is still tried (and named in `failed`), since the server has no live view of which Engines answer.

**The kept list** (`/tick`). The merged list is kept between ticks, as each engine's part (the items as the window reads them, of the finished ones only the 50 newest) with the change counter it was read at, and read again only when needed: this machine's part after a change on its change bus (`service.onChange`; never kept after a failed read); a connected service's part when it is 10 s old (`remoteTtlMs`), and by the next tick after the window changed one of its items (any action of the API, also one that was refused); the engines (rows, hidden devices, names, colours) every 30 s (a device added, removed or hidden shows within that time); the agents of this machine's terminals in one query when the set of terminals or of running ones changes, else every 60 s; whether a terminal's shell runs is asked in memory on every tick, so a terminal that starts or ends changes the list at once; the preferences every 30 s, and at once after a save on the settings card. A tick waits for a read it needs (the first, or one after a change) up to the 4 s of `GET /items`, and for a read that only the age asked for up to 250 ms (`tickWaitMs`): a slower one is in the next tick, which meanwhile answers the part as it was. A connected service that failed stays in `failed` until its next read. Measured with nothing changing (30 open and 600 finished items here, one connected service with 20 open and 300 finished, `test/attention-widget-tick.test.js` and a bench of the same setup): the old window's 48 requests a minute ran 1,140 statements reading 7,560 item rows and made 24 remote reads (3,840 items); `/tick` is 12 requests, 27 statements (the engines and prefs ages; no item rows) and 6 remote reads of 70 items each. No item or event is ever deleted for this.

**Finished items in the list query** (`services/attention.js` `list`). `recentFinished: n` (`recent_finished=n` on `GET /api/attention` and `/v1/attention`; the routes put `recent_finished: n` into the answer) adds, after the open items of the default list (no `status`, no `include_done`; otherwise it is ignored), the `n` items finished last (`completed_at` DESC, then the list's order), under the same `parent` and `q` filters; `n` is 1 to 1000 (`400 VALIDATION_FAILED` "recent_finished must be an integer between 1 and 1000"). They are read along the index `idx_attention_items_completed` (`attention_items (completed_at)`) from its newest end; without it SQLite read and sorted every finished row (about 10 ms for 2,000 items and 108 ms for 20,000, against 0.7 and 1.4 ms with it, `EXPLAIN QUERY PLAN` `SCAN ... USING INDEX` instead of `USE TEMP B-TREE FOR ORDER BY`). The index is made by `db/schema.sql` on every start and by `ensureTreeColumns` for a database made from an older `schema.sql`, so existing databases get it at their next start. An index is not a table or column change: an older version reads and writes the table as before, so `schema_version` is not raised (as for `attention_tokens.scopes`). The open items of the default list are asked for by name (`status IN` the four open statuses, which walks `idx_attention_items_status`) instead of `NOT IN` the finished ones (which read the whole table); the statuses are checked on every write, so the result is the same.

**Floating window notices** (`services/widget-notices.js`). The bubbles the window shows beside itself, pushed by the `widget` notifier (see "Desktop window bubble" under "T-Attention notifiers") and read by the window on its 5 s refresh with `GET /notices?after=<the last seq it saw>`. In memory only, per server process: at most 20 notices, none older than 10 minutes, `seq` one higher for every notice (the first is 1; it starts again at 1 after a restart, together with a new window). A notice, the contract of the Swift side:

```json
{ "seq": 7, "at": "2026-11-17T10:02:00.000Z", "kind": "item", "title": "Fix the login test", "text": "Claude wants to run a command",
  "from": null, "status": "waiting_user", "key": "local:12", "target": "http://127.0.0.1:3000/", "seconds": 8 }
```

- `kind` `item` | `direct` (`tcli notify`) | `test` (the Settings test); `title` one line of at most 200 characters (a missing title is the first line of the text); `text` at most 500 characters, line breaks kept, trimmed; `from` one line of at most 80 or null; `status` (the item status) and `key` (the window's item key) only for `item`, else null; `target` an absolute http(s) address without credentials, or null; `seconds` how long to show it, 0 = until it is clicked or closed. Control and direction characters are removed and a cut text ends with an ellipsis.
- The words of a bubble the window needs ("Close", "Open", "Message from an agent", "Test message", the test sentence, the status labels) have Chinese translations in the dictionaries; the Swift side adds the ones it shows to `strings.json` (which must list exactly the strings of the Swift files).

**Strings.** `widgets/macos/strings.json` is a JSON list of the English words the window shows (the Swift side adds to it). `GET /strings` looks each one up in the Chinese dictionaries of the page (`public/js/i18n-zh-server.js`, `i18n-zh-extra.js`, then `i18n-zh-ui.js`, read in a `vm` sandbox and read again when a file changes); a word without a translation is shown in English, placeholders like `{1}` stay. The window's words are in `i18n-zh-ui.js`; `test/attention-widget.test.js` fails when one has no translation. Error messages from owners are not translated.

**Notice bubble.** With each 5 s tick the window also gets the notices (`notices` of `GET /tick`, or `GET /api/attention/widget/notices` from an older server; no `after` on the first call, so the server answers the last 60 s; then `after=<last seq>`; one request at a time) and shows each new notice in a bubble beside the pill: a borderless non-activating panel, 280 pt wide, on the side toward the middle of the screen (left of a pill in the right half, else right), its top level with the pill's top, inside the visible frame; while the task panel is open it sits beside the pill and the panel together, and it follows the pill while it is dragged. It holds a status dot, the bold title, the text (three lines at most), the sender and a × "Close"; it slides in over 0.2 s (it just appears with Reduce motion) and is announced to VoiceOver. A click opens, for a notice of a task the window's list has, the task's link (the notice's `target`, which the server made from it), else the task's session (`TA_WIDGET_URL` + `session.open_path`); otherwise `target` (only an absolute `http(s)` address with a host is used), else the T-Agent page at `TA_WIDGET_URL/`; and closes it. It closes after `seconds` (default 8, 0 = until closed); the pointer over it pauses the time and leaving starts it again. One bubble at a time: the others wait oldest first, a newer notice with the same `key` replaces a waiting one, and when more than three wait only the newest is shown with "+N more". A seq lower than the last one (the server started again) is taken as the new start; a 404 (an older server) stops the polling for 5 minutes.
- Actions: under the text of an `item` notice whose `key` is in the window's item list, the buttons of that task's row by the status the list has now (refreshed every 5 s, so a notice that comes before the list catches up gets its buttons on the next refresh): review -> Confirm and Reject, `waiting_user` -> Handled, plus Reply when the item's `session` is `local` and `live: true`. They run the row's code (`POST /items/:key/confirm|reject|handled`, Reject without a reason as on the row, a failure opens the panel with "Action failed: ..."), close the bubble and open nothing.
- Reply: shows a one-line field with Send under the text. Only then may the bubble (a non-activating panel) become key, so typing works while the other app stays in front; closing the field gives the keyboard back. Return or Send posts `POST /items/:key/reply { text }` (trimmed, 1 to 4000 characters; the contract is in the server's part of this section); Esc goes back to the buttons; Return and Esc belong to the input method during a composition. While the field is open the bubble's timer waits and a click on the bubble body does nothing. Success closes the bubble and refreshes the list; a refusal stays in the bubble in red ("Reply failed: <server message>") with the text kept, and a 404 or 409 also reads the list again (the terminal may have stopped, which hides Reply). An answer that comes after the bubble was closed shows in the panel.
- Sessions: `session` is optional in the item model (older servers send none and every session feature stays hidden). `session.open_path` is used only when it starts with `/?openTerminal=`, has something after it and has no whitespace, control character or backslash. Rows with one get Open session (after Open link, in every section, also in the row's right-click menu; it stays on while the row's request is out). `waiting_user` rows whose terminal can take a reply get Reply after Handled; it opens a small reply form over the list (the task's title, the field, Cancel and Send), which behaves like the task form for the keyboard and shows "Reply failed: ..." on a refusal.
- Open session on the open page (`openTerminalPage`, Swift "Part F"; also a Working now row and a bubble click that opens a session): the window sends `POST /api/attention/widget/open-terminal { engine, task_id, terminal_id }` (parsed from `open_path` with the page's own pattern) instead of opening a new tab. An answer `{ delivered >= 1 }` means a T-Agent page switched in place: nothing opens, and unless `focused: true` (the browser extension brought that tab forward) the window activates the default browser (the app for `http:` addresses, `NSWorkspace.openApplication`, which only activates a running app) without an address. `delivered: 0`, a 404 (an older server) or any other failure opens `TA_WIDGET_URL` + `open_path` as before (for remote items too; the page opens that service's terminal itself).

**Panel look** (Swift "Part F"). Rows: the title alone on one line (cut with an ellipsis; the full title and second line are the row's tooltip and VoiceOver label), then at the right end of that line the row's actions as 18 pt icon buttons (SF Symbols as templates, `NSImage(systemSymbolName:)`, macOS 11+; Open link `link`, Open session `terminal`, Confirm `checkmark.circle.fill` in the accent colour, Reject `xmark.circle`, Handled `checkmark.circle`, Reply `arrowshape.turn.up.left`; the English words as tooltip and accessibility label; text pills when the system has no symbols) and the engine tag; under it, 11 pt and muted, the custom status and the pending text (or reason, or result), at most two lines. The icons always show in Needs you; elsewhere only under the pointer, and everywhere while VoiceOver runs; every action is also in the row's right-click menu (Open link, Open session, then Confirm and Reject or Handled and Reply, before Edit and Delete) and in the row's accessibility custom actions, so none needs a mouse. Rows went from 37 to 73 pt (with a text button row) to 32 pt with a second line and 18 pt without (`--render-sample` prints them). Section headers are a drawn colour dot (Needs you red, Working green, To do yellow, Finished grey, Working now teal), the name and a muted count, without emoji. The top row is "Tasks" with the unfinished count, a magnifier that opens the search field in its place (also Cmd+F and Ctrl+Option+T) and `+`. Every background (pill, panel, forms, bubble) is the `.menu` material's blur under a veil of `windowBackgroundColor` at 86%, so terminal text behind the window no longer mixes with the panel's text. The bubble keeps text buttons: it has two or three, and words read faster in a notice that is only shown for a few seconds.

**Live agent activity (window side).** With each 5 s tick the window gets `activity` of `GET /tick` (from an older server `GET /activity`, one request at a time; a 404 from an older server hides it and asks again after 5 minutes; any other failure hides it until the next answer). The pill shows, right of the counts, a teal dot with the running count (it pulses, still with Reduce motion) and an orange badge with the waiting count (`waiting` = a permission prompt: it needs the person, like Needs you); the pill stays 26 pt high (about 124 pt wide with every part at two digits). The panel starts with "Working now" when there is a terminal: waiting first (so it never hides behind "+N more"), then running, then done, newest `since` first; one line each with a state dot, the task title, the agent (Claude, Codex, else the terminal title), the state and the time since `since` ("42s", "3m", "1h 2m", moved on each tick); at most 5 rows, then "+N more". A click switches an open T-Agent page to that terminal like Open session, else opens `TA_WIDGET_URL` + `open_path` (only `/?openTerminal=...` without whitespace or backslash) in the browser. VoiceOver reads the pill's indicator ("2 running, 1 waiting for you") and each row as a button. `WidgetController.showActivity` (default true) is the switch for `show_activity` of `GET /prefs`: off means no request and nothing shown. Details: `widgets/macos/README.md`.

**Settings.** `GET / PUT /api/attention/widget/settings` (the browser session, after the `/api` gate and the same-origin rule) -> `{ enabled (default true), language: 'auto' | 'en' | 'zh' (default 'auto'), hotkeys, dim_when_idle, show_activity (window preferences, booleans, default true), platform_supported, swiftc, running, building, last_error }`. A preference that is not `true` or `false` is `400 VALIDATION_FAILED` "<name> must be true or false"; a preference never starts or stops the window. `building` (a build is running) is an addition to the first contract, for the status line. Stored in `system_state` (`attention_widget_settings_v1`). A change of `enabled` starts or stops the window at once; the answer waits at most 1.5 s for a quick start. 'auto' follows the language of the person's T-Agent page: the server only knows it from the `ta-lang` cookie (`wantsChinese`), so it remembers the language of the last page load and of the last settings read (`attention_widget_page_language_v1`); before the page was ever opened it is English. A settings request with a Bearer header is `403 TOKEN_NOT_ALLOWED`.

**Settings card.** In Settings -> T-Attention, after the plugins (`registerAttentionSettings` id `widget`, order 35): the switch "Desktop window (macOS)", a short description, three switches for the window preferences ("Global shortcuts (Ctrl+Option+T panel, Ctrl+Option+N new task)", "Fade when idle", "Show working agents"; disabled where the window is not supported, left out when the server does not answer them), the hint "The window opens with T-Agent. To start T-Agent when you log in, run pm2 startup and pm2 save.", "Window language" (Same as this page / English / Chinese, a native select) and a status line: Off, Running, Building the window... (read again every 3 s until it ends), the last error, "Not supported on this system" (switch and select disabled), or "Xcode command line tools needed: xcode-select --install". The switch and the preferences are per device: a linked device's tab saves them there (`routes/device-settings.js` passes `enabled`, `hotkeys`, `dim_when_idle` and `show_activity`); the language is shared.

**Window preferences and keyboard** (Swift, the `Part D: shortcuts and preferences` section). Global shortcuts use Carbon `RegisterEventHotKey` (no Accessibility permission; `import Carbon` links with the same `-framework AppKit` build): Ctrl+Option+T opens the panel and keeps it open with the keyboard in its search field until it is pressed again, Esc or a click in another app (a global mouse monitor, which needs no permission either); Ctrl+Option+N opens the New task form. Turning `hotkeys` off unregisters them at the next tick; a shortcut another app holds is reported once on stderr. With `dim_when_idle` the pill fades to 45% after 30 s without the pointer over it, without the panel or a bubble showing and without a rise of the Needs you count (at once with Reduce motion); any of those brings it back to 100%. `show_activity` is passed to the live activity part (`showActivity`). Window-local, in UserDefaults: a search field in the top row, opened by its magnifier (title, notes and custom status; case, diacritics and width ignored; Cmd+F focuses it while the panel has the keyboard, Esc clears it; no drag reordering while it filters), the Finished group (done, failed and cancelled rows under "Finished" with its count, collapsed by default, `finished_expanded`; a search shows the matching finished rows), and the pill's position per display (`display_positions`, keyed by the display UUID, else its name and frame, as fractions of the free room; `display_last` is the display it was last dragged to). When the displays change the pill goes to the saved spot of the display it was last placed on when that is connected, else of the display it is on now, clamped into the visible frame; the old `x` / `y` keys stay the fallback. Launch at login is T-Agent's: the window starts with the server, so `pm2 startup` and `pm2 save` cover it.

**Page link to a terminal** (`openTerminalFromLink` in `public/js/h5.js`). `/?openTerminal=<engine>:<task id>:<terminal id>`, engine `local` or `remote:<remote_servers id>`. On load the parameter is taken out of the address at once with `history.replaceState` (other parameters stay), so a reload shows the page as usual. After the services are known the page reads that service's tasks (the read already on its way, or a new one; a device hidden in the task list is reached too), then that task's terminals; when both are there it selects the task on that service and shows that terminal (`selectTask` with `{ terminal }`, which also remembers it as the task's terminal, `h5-terminal:<source>:<task>`), over the task the page remembered, and the phone's task sheet stays closed. While the multi-column view is shown it goes to the focused column instead (`openInColumn` with `terminalId`), and the hidden normal view brings back its remembered task as for a chat link. An unknown service, task or terminal, or a value that is not such a link, shows the normal page and the notice "That terminal is not available any more". The early socket of the remembered terminal is not opened when the page has such a link. The desktop window does not open such a link when a T-Agent page of this machine is already open: `POST /api/attention/widget/open-terminal` pushes `event: open-terminal` over that page's attention stream (only top-level pages of this machine that connected with `?tab=1`, the one seen last; see "T-Attention on the page"), and the page runs the same `openTerminalFromLink` in place (`ui.actions.openTerminalLink`, no reload; columns view -> focused column); the browser extension's `tabs.reveal` brings that tab forward when it is connected. A hidden or background tab still gets it (the attention stream stays open while hidden). Old pages without `?tab=1`, column iframes, phones and other devices never count, so the window then opens the link as before. Test: `scripts/test-h5-open-terminal-link-browser.cjs` (this machine and a connected service, at computer and phone size; the address after the link and after a reload; a missing task, terminal, service and a malformed value).

**Limits.** Not tried on a real Mac in the tests (fake spawner and execFile only). The window needs the GUI login session: a T-Agent run as a service without one (for example by launchd as root, or over SSH only) cannot show it. One window per server; a second T-Agent server on the same Mac starts its own. The token lives only in memory, so a restarted server starts a new window with a new token (the old one exits with its parent).
