# T-Attention notifiers

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

> Branch `feat/todo-notify`. Code: `services/attention-notify.js`, `plugins/notifiers/telegram/` (`manifest.json`, `index.js`), `scripts/h5-shell/NotifierSettings.jsx`. Tests: `test/attention-notify.test.js` (fake bus and notifier), `test/attention-notify-telegram.test.js` (mocked gramjs), `scripts/test-h5-notifier-browser.cjs`. Foreground rule: `lib/terminal-presence.js`, `routes/terminal.js`, `public/js/h5.js`, chat presence in `services/agent-chat.js` and `scripts/agent-chat/store.mjs`; tests `test/terminal-presence.test.js`, `test/remote-terminal-presence.test.js`, `test/agent-chat-service.test.js`, `test/agent-chat-routes.test.js`, `test/remote-agent-chat.test.js`, `scripts/test-h5-presence-browser.cjs`.

Tells the user on another channel when an attention item enters a status that needs them. In-process: `start({ db, sessionSecret, onChange?, getItem?, getOwner?, notifiers?, log?, now?, timers? })` subscribes to `onChange(fn) -> unsubscribe` of `services/attention.js` (looked up when `onChange` is not passed; without that module it only serves its settings) and returns `{ createRouter(), handle(change), stop(), getRules, saveRules, recent }`. `server.js` mounts `start(...).createRouter()` at `/api/attention-notify` and passes the same service instance the routes use: `onChange: attentionService.onChange` (the public bus: the excerpt never reaches a notifier) and `getItem: id => attentionService.get(id)`, which a delayed call uses to send the item as it is when the call fires (with a `context.summary` that arrived after the status change). The AI summary is stored with `actor: 'summary'` and the same status, so it notifies nobody and keeps a planned call (`test/attention-notify.test.js`, also with the real service).

**Plugins.** Every `plugins/notifiers/<name>/` with `manifest.json` (`{name, version, kind: 'notifier', description}`) and an `index.js` exporting `{ name, label, configFields, async notify({ item, previous, reason, mode, config, values, log, link, error }), async test(config, { kind, link }) }` is loaded at start; a broken plugin is skipped and logged. Optional extras: `ready(config)` (false = not set up, skipped; a plugin switched off in its manifest settings is skipped before this, see "Plugin settings from the manifest"), `status(config, owner)` (the safe view for Settings), `routes(router, { store, owner, NotifyError, log })` (own endpoints under `/api/attention-notify/<name>/`), `close()`. `reason` is `status` (entered the status), `still` (a delayed call) or `call_failed` (the fallback message, with `error`); `link` is the absolute page link. A call returns `{ outcome }` or `{ fallback: 'message', error }`. A delivery relayed from another linked device also has `origin: { name }` (also in `test(config, { kind, link, origin })`): the Telegram card shows "From <name>". A plugin that takes free-form messages of agent sessions exports `direct: true` and gets `notify({ reason: 'direct', mode: 'message', item: null, message: { title, text, from }, link, config, values, log, origin })` (see "Direct messages" below); Telegram, email and the desktop window bubble (`widget`) do. Optional `whyNotReady(config)`: the reason a plugin that is not ready cannot send, used as the Settings test answer instead of "The plugin is not set up yet" (the widget: not macOS, the window off or not running).

**Rules** (per user, encrypted in `system_state` as `attention-notify:<owner>`; plugin settings as `attention-notify:<plugin>:<owner>`; no schema change): `statuses` (default `waiting_user`, `failed`, `review`), `modes[notifier][status]` = `message` | `call` | `off` (missing = `message`; only the modes the notifier's manifest `modes` allows: `PUT /config` refuses another one with 400 "<name> cannot make calls" / "<name> cannot send messages", a mode saved before or synced from an older device counts as `message` (or `off` when messages are not allowed), and `GET /config` gives each notifier its `modes`, so the rules page offers only those), `messageDelayMinutes` (default 3, 0 to 120; see "The wait before a message" below), `callDelayMinutes` (a call is made only if the item is still in that status after M minutes; 0 = at once), `quietHours {enabled, start, end, timeZone}` (the browser's zone; ranges over midnight work; nothing is sent inside them, a delayed call that falls inside is dropped), `rateLimit {message: 20, call: 6}` per notifier per hour, `publicUrl` (the page link of every message is `<publicUrl>/`, none without it; before, an http(s) `link_url` of the item replaced it and a `/...` one was appended to it, which made "Open in T-Agent" open the task's link. The task's link now reaches the notifier with the item and the card shows it on its own line), `agentMessages` (default `true`: agent sessions may send direct messages with `tcli notify`; a missing or non-boolean stored value is the default, and an older device keeps the field when it saves, like `messageDelayMinutes`, so it travels with the synced `notify-rules` group). Only a status change INTO a listed status notifies (or a created item in one); `working`, `done`, `todo` and `cancelled` are not in the default list. In Settings the three default choices read "Needs you" (`waiting_user`), "Finished (ready for review)" (`review`) and "Failed" (`failed`), with the line "No message while the session is open on a screen you used in the last 5 minutes." under them, then the field "Send a message only if still in that status after (minutes, 0 = at once)" (`#h5-notify-message-delay`, hidden when the server's rules have no `messageDelayMinutes`) with the hint that "Needs you" waits too. The same notifier + item + status is not sent again within 10 minutes. A delayed call is cancelled when the item changes status, is deleted, or is edited by the user in the page (actor `user`); a listener refreshing the same status keeps it. A call over the limit or a failed call becomes a message (counted as a message). A notifier that is switched on but not set up on this device (`ready(config)` false, or a required manifest setting missing) and that no linked device sends for is skipped quietly at a status change: nothing is planned and the recent list gets no line for it (before, every change left "Message planned" and then "Skipped: not set up" for each such notifier, email for one until it is set up). Background events belong to the single user (`ensureSingleUser`).

**The wait before a message** (`messageDelayMinutes`, default 3; `sendLater()` in `services/attention-notify.js`, the same machinery as a delayed call, whose wait is `callDelayMinutes`). At the change the usual checks run (mode, switch, dedupe, foreground, quiet hours); then the message is planned (recent outcome `message_scheduled`, "Message planned", detail `3 min`). When the time comes it is sent (reason `still`, with the current item from `getItem`, so a `context.summary` that came meanwhile is in it) only if the plugin is still loaded and switched on, the rules still send `message` for that status, the item still exists in the same status, it is not quiet hours, nothing was sent for the same notifier + item + status in the last 10 minutes, and the session was not on a screen at any moment of the wait (`onScreen(item, since)`, below). A status change, a delete or an edit by the user (actor `user`) drops it at once; a listener or the summary refreshing the same status keeps it. A drop is logged as outcome `cancelled` ("Not sent: it changed before the wait ended") with the reason as detail (`the status changed`, `you changed the item`, `the item was deleted`, `the item is gone`, `the rules changed`, `the plugin was turned off`); a skip at the end is `foreground` (detail "the session was open on screen during the wait"), `quiet_hours` or `duplicate`. Dedupe and the hourly limits count only what is actually sent: the dedupe time is noted when a delivery goes out (also for a delayed call, which before noted it when planned) and `deliver()` counts the limit, so a dropped wait uses neither. The wait applies to every status, `waiting_user` too: a permission prompt or question is often answered within a minute at the screen, and one rule is simpler; the hint says so and 0 brings back messages at once. Mode `call` uses only `callDelayMinutes`. The waits are timers in memory: a restart drops them, so an item that entered its status less than the wait before a restart is not sent (accepted: persisting them is not worth it for a few minutes). Rules saved or synced by an older version have no `messageDelayMinutes` and get the default (also a value out of range, and the same for `callDelayMinutes`) in `getRules()`; an older device keeps the field when it saves (its `normalizeRules` starts from the stored rules), so the field travels with the synced `notify-rules` group.

**Foreground rule (only when the session is in the background).** Before a delivery, and again when a delayed message or call is due (with the current item from `getItem`), nothing is sent when the item's session is open on a screen (`onScreen(item, since)`; with `since`, the start of the wait, "was on screen at some moment since then" counts too). Either (1) `item.context.tagent` names a T-Agent terminal and `isForeground(task_id, terminal_id, since)` is true; a terminal of THIS server (`isLocalTerminal`: its shell runs here or it is a `task_terminals` row of the task; terminal ids are UUIDs) counts whatever `context.host` says, and only for a terminal this server does not know is `context.host` compared with `os.hostname()` read at the check (a mismatch means another machine; nothing is asked). Up to v2.123.0 the host name was read once at the start and compared for every item: on a Mac whose `HostName` is not set, `os.hostname()` follows DHCP / reverse DNS (an IP address such as `192.168.1.224`), so after a network change the listener wrote another name than the server had and no item was ever suppressed. Or (2) `item.context.session` `{ agent, id }` is the session of an agent chat of this server (`agent_conversations.session_id`, or the running chat's id) and a page shows that chat (`isSessionForeground(agent, id, since)`, `services/agent-chat.js`): a chat runs Claude through the Agent SDK with the user's settings, so the Claude listener writes items for it without `tagent`. That is recorded in the recent log as outcome `foreground` (detail "the session is open on screen", shown as "Skipped: the session was open on screen") and does not count as sent, so a later change in the background is sent. Items with neither (made by hand, the CLI outside a T-Agent terminal, other listeners) are always sent. `server.js` passes `isForeground: terminal.isTerminalForeground(taskId, terminalId, since)`, `isLocalTerminal: terminal.isLocalTerminal` (routes/terminal.js) and `isSessionForeground: getAgentChat().isSessionForeground`; the defaults (tests, no option) are never foreground and an unknown terminal; a check that throws counts as background.
- Foreground, as the page reports it (`public/js/h5.js`): the terminal is the one shown in that page (not hidden under a chat), `document.visibilityState === 'visible'`, the page was not left (`pagehide` says false at once, even where the browser still says visible; `pageshow` brings it back), and the person used the page (`pointerdown`, `keydown`, `touchstart`, `wheel`, `input`; loading the page counts) in the last 5 minutes. The server counts a terminal as foreground while at least one of its open sockets last said `foreground: true` AND was heard from (any frame; the page pings every 15 s) in the last 50 s (`lib/terminal-presence.js` `staleMs`): a frozen page (a locked phone, a suspended app) whose last "false" never left, and whose socket the browser's network process keeps answering at the protocol level, stops counting by itself. A socket that closes drops out at once. `seenSince(key, since)` keeps the last foreground moment of each key (of a socket that turned false, closed or went quiet), so a delayed send can ask whether the session was seen during the wait.
- Agent chat (`scripts/agent-chat/store.mjs`, `services/agent-chat.js`, `routes/agent-chat.js`): the page shows a chat over the terminal; `h5.js` tells the mounted chat `setForeground(shown && visible && not left && used in the last 5 minutes)` on the same events as the terminal presence. The store opens its event stream with `?viewer=<random id>` and, when the snapshot has the capability `presence`, posts `POST …/conversations/:cid/presence { viewer, foreground }` on every change, after each (re)opened stream, and every 20 s while true. The server keeps it per stream (the same presence tracker, 50 s stale time): a report for a viewer without an open stream is ignored (`{ ok: false }`), and closing the stream drops it. 400 `INVALID_PRESENCE` for a bad viewer id or value. The remote proxy forwards the POST and the `viewer` of the stream to the Engine that runs the chat. An older Engine has no `presence` capability, so nothing is posted.
- Multi-column view: each pane is a page of its own with its own sockets, so each reports its own terminal with its own visibility. The activity is shared: the top page keeps one record on its window (`window.__tAgentActivity = { at, listeners }`) and every pane of the same origin uses it, so using any column (or the top page's bar) keeps every visible column in the foreground. A column scrolled out of the strip still counts as visible (its document is visible).
- Remote terminals and chats: the page's presence frames go through the proxy (`services/remote-terminal-proxy.js`, also over a service-link tunnel) unchanged to the Engine that owns the terminal, and a remote chat's presence POST goes to the Engine that runs it, so the Engine whose listener wrote the item checks its own terminal or chat with the same rule (its own `isLocalTerminal`). An item written to another machine's T-Attention (a listener paired elsewhere: the terminal is unknown here and `context.host` differs) is always sent.

**One Telegram sender for linked devices** (`services/attention-relay.js`; tests `test/attention-notify-relay.test.js` with in-process devices and two real `server.js` linked by a real tunnel, fixture `test/fixtures/attention-fake-telegram.js`; `scripts/test-h5-telegram-relay-browser.cjs`). The same Telegram session used on two machines at once makes them push each other out, so of all linked devices (service links) only one sends to Telegram; the others relay their deliveries to it.
- Who sends (`resolve()`, the same rule on every device): (1) the stored choice `telegram_sender` (`system_state`, plain JSON `{ instance_id, updated_at }`) when it names this device and Telegram is set up here (`localReady`: the plugin is loaded, switched on and `ready(config)`), or a linked device with the capability `notify:relay` that is not known to be an older version or to have no Telegram; (2) otherwise the devices where Telegram is set up (this one and the linked ones whose `GET /v1/attention/notify-relay/status` says `ready`): the one with the smallest instance id, so that all agree without asking, and with more than one the page asks the person to choose (`conflict`); (3) nobody: this device behaves as before (its plugin, not set up, is skipped). A chosen device that logs out stops being chosen by (1) as soon as the others see `ready: false`. The facts about each link are cached for 60 s (15 s after a failed probe), read again when the link changes or comes online, and kept while it is offline. A relay (a delivery, a direct message or a test) that the sender accepts from a link marks that link as sending through it at once (`noteRelaying`), so its page lists the device without waiting for the next probe: when two devices come online together the sender may ask the other before the other has asked it, and the answer "no sender yet" was kept for the whole 60 s (this made the two-server test time out at `A lists B` on slow CI runners).
- The relay (`attention-notify.js deliver()` → `relayOut`): every decision is made on the device that owns the item (statuses and modes, the foreground check — terminal presence is local to that device —, dedupe, quiet hours, and the wait and "still in that status" check of a delayed call); only the final send goes to the sender, `POST /v1/attention/notify-relay` `{ notifier: 'telegram', mode: 'message' | 'call', reason: 'status' | 'still', item, link }` (a direct message of an agent session has `reason: 'direct'` and a `message` instead of the item, see "Direct messages" below). `item` is `relayItem(item)`: id, title, status, source, attention_reason, `link_url` (at most 2000) and `link_label` (at most 200) when set, and of the context only `pending` (kind, text, tool, command), `cwd`, `branch`, `host`, `latest_prompt`, `summary.text`, `last_reply`, `files` (path, added, deleted; at most 50), each cut to a size the card never exceeds — never the excerpt, `context.tagent` or a secret. `link` is the absolute page link of the origin (`<publicUrl>/`); the sender's card puts a page path `link_url` under it. The sender takes the origin from the link record of the token (`peer_instance_id`, `name`), never from the body, refuses with 409 `NOT_SENDER` when its own rule names another device, and runs its plugin through the same `deliver()` with its own rate limits (a call over the limit or a failed call becomes a message, as for its own items) and a dedupe key `telegram:<origin instance id>:<item id>:<status>`; it does not check quiet hours or the foreground again. The plugin gets `origin: { name }` and the card has the line `From <name>` under the header. Answer `{ outcome, detail? }` (the sender's outcome: `sent`, `call_*`, `fallback_sent`, `rate_limited`, `duplicate`, `skipped`, `error`).
- On the origin the recent log says `relayed` (with `via` = the sender's name and the sender's outcome as `detail`) or, on failure, `relay_offline` (the link is down or the sender cannot be reached) or `relay_failed` (the sender answered an error, or its outcome is `error`). An offline or failed relay is tried once more after 30 s, kept with the item's delayed calls so that a status change or an edit by the user drops it; never a second retry, and never a send from the origin instead (it may be logged in, but must not use Telegram). An `error` outcome of the sender is not retried: the sender already did its own fallbacks.
- The switch: "Use this device as the sender" (`PUT /api/attention-notify/relay/sender { use: 'self' }`, 409 unless Telegram is set up here) stores `{ instance_id: <this device>, updated_at: now }` and sends it to every linked device with `notify:relay` (`PUT /v1/attention/notify-relay/sender`). Last writer wins on `updated_at`; a device that was offline gets the choice when its link comes up, because each probe compares the choices and the older side takes the newer (or pushes its own). A peer's PUT is never sent on. The old sender stops at once: its own rule now names the other device, so its deliveries are relayed there.
- Tests through the sender: on a device that is not the sender, `POST /api/attention-notify/telegram/test`, `POST /api/attention/plugins/telegram/test` and `POST /api/attention-notify/relay/test { kind }` go to `POST /v1/attention/notify-relay/test { notifier, kind }` on the sender, which runs `test(config, { kind, link, origin })` (the sample card with `From <name>`). Errors: "The sender device is offline; try again when it is online", "The sender device has changed; try again", "The sender device could not send the test".
- Engine routes (`routes/engine-v1.js`, mounted before `/v1/attention`): only a token issued for a live service link (403 `LINKED_ONLY` otherwise), the token checked before the body is read, a body of at most 64 KB. `GET /status` → `{ instance_id, notifiers: { telegram: { ready } }, sender: { telegram: { instance_id, updated_at } }, effective: { telegram: <instance id> | null } }`, never a secret. The paths pass the tunnel's allowlist. A linked device without `notify:relay` (an older version) keeps its own behaviour (it sends itself if it is logged in), is never chosen, and is told nothing.
- Page (`NotifierSettings.jsx`, from `relay` in `GET /config`, null without the relay; nothing is drawn without linked devices that can relay): on the sender "This device sends Telegram notifications for all linked devices" with the devices that send through it (their reported `effective`) and their online state, plus "Use this device as the sender" while there is a `conflict`; on another device "Telegram notifications are sent through <name> · Online/Offline", "Send test message" (through the sender) and, when this device is logged in too, "Use this device as the sender" and "Log out here" (its own account 2, test and logout are hidden while it does not send); not logged in, the login is behind "Log in on this device instead". The plugin row says `Sent through <name>` and counts as set up. The recent list adds "Through <name>" or "From <name>".
- Not covered: the person's settings for Telegram (login, account 2, ring time) stay on each device; the notifier rules and the other plugins' settings are synced by the settings sync of linked devices, not by the relay. Several linked devices must be linked to the sender directly: a relay is never passed on.

**Direct messages** (`sendDirect({ owner, title, text, from, link, via })` → `{ results: [{ notifier, outcome, detail?, via? }] }`; `tcli notify`, see "tcli (agent command line)"; tests in `test/attention-notify.test.js`, `test/attention-notify-relay.test.js`, `test/attention-notify-telegram.test.js`, `test/tcli-notify.test.js`). A free-form message of an agent session, sent through every selected notifier (`via`: a list of names, or all) that is loaded and has `direct: true`. Input: `text` required, at most 3000 characters (400 `TEXT_TOO_LONG`, not cut), newlines kept, a run of empty lines folded to one, other control and direction characters removed; `title` one line, at most 200 (400 `TITLE_TOO_LONG`); `from` one line, cut to 200 (the relay makes it); `link` only http(s) without credentials, at most 1000 (400 `INVALID_LINK`). The switch `agentMessages` off: 403 `NOTIFY_AGENT_ACCESS_OFF` "Agent messages are turned off in Settings → T-Attention → Rules for all notifiers". None of the selected notifiers is switched on and set up (`ready(config)`, or the required manifest settings), or relayed to a linked sender: 409 `NOTIFY_NOT_CONFIGURED`. Per notifier, in order: switched off `skipped` (`turned off`), not set up `skipped` (`not set up`), quiet hours `quiet_hours`, the same notifier + title + text within 60 s `duplicate` (noted before the send and dropped again when it was not sent, so a failure can be sent again at once), over the hourly message limit `rate_limited` (the same `allow(name, 'message')` window as item messages, so both count against one limit), else sent (`sent`, or `error` with the plugin's error, stored secrets removed). The item rules do not apply (statuses, modes, the foreground check, the wait). Every outcome is remembered in the recent list with `item_id: null` and `kind: 'direct'`; the log line says `direct message`, never the text. In Settings the recent list shows such an entry as "Agent message" (and its `duplicate` as "Skipped: the same message was sent less than a minute ago"), and the rules page has the checkbox "Let agent sessions send messages (tcli notify)" (`#h5-notify-agent-messages`, hidden when the server's rules have no `agentMessages`) with a short hint.
- Through the Telegram sender: on a device that is not the sender (`relay.target('telegram')`) the message goes to the sender as `POST /v1/attention/notify-relay` `{ notifier, mode: 'message', reason: 'direct', message: { title, text, from }, link }`, no `item`; quiet hours and dedupe were decided here. The sender checks it (`relayMessage`: text required, cut to 3000, title and from cut to 200; mode other than `message` 400 `INVALID_MODE`, no text 400 `INVALID_MESSAGE`, not the sender 409 `NOT_SENDER`), takes the origin from the link token, and sends with its own switch, readiness and rate limit (`acceptRelayDirect`), without quiet hours or dedupe; the plugin gets `origin: { name }`. The origin records `relayed` with `via` and the sender's outcome as `detail`, or `relay_offline` / `relay_failed`; a sender of a version before direct messages answers 400 `INVALID_REASON`, which is `relay_failed` with "The sender device needs a T-Agent update". A failed direct relay is not tried again after 30 s like an item delivery: the command reports the result at once, and the agent decides.
- Telegram card (`reason === 'direct'`, the same HTML send and plain-text fallback as the item card): `📣 <b>title</b>` (no title: "Message from an agent"), the text (cleaned line by line, escaped, cut to what is left of `MESSAGE_MAX`), then `From <from>`, `From device <origin>` when relayed, and the `Open in T-Agent` link. The header, the From lines and the link are reserved first. Never a call.
- Status (`directStatus(owner)`, `GET /api/tcli/notify/status`): the switch, quiet hours now, and each direct notifier with `enabled`, `ready` and `via` (the linked sender).

**Scheduled reminders** ([attention-schedules.md](attention-schedules.md)): a change with `scheduled_due: true` (a reminder that came due, published once after the firing was stored) is sent by `remindScheduled` instead of the status rules: through the rules of Needs you (`waiting_user` must be among the statuses; each notifier's mode for it; quiet hours), at once (no message delay: the person chose the time) and whatever is on screen; once per firing (the key names `last_fired_at`). It is relayed with reason `status`, so an older sender takes it. A prompt that could not be sent and a failed script move the item to Needs you, which notifies by the normal status rule.

**Read copies** ([attention-copies.md](attention-copies.md)): the copies of other engines' items never reach a notifier (they have their own bus), so a notification is decided and sent only on the item's owner, never twice.

**Isolation.** The bus callback returns at once and never throws; every delivery is awaited separately and its error is caught and logged (`[attention-notify] <notifier> item <id> <status> <mode>: <outcome>`, never the title or a secret). The last 50 outcomes are kept in memory and the last 20 shown in Settings (`GET /config` `recent`).

**Endpoints** (browser session only, same-origin rule; an attention token cannot reach them): `GET/PUT /api/attention-notify/config` (`GET` → `{ rules, statuses, modes, notifiers: [{ name, label, configFields, modes, status }], recent, relay }`); Telegram: `GET /telegram/status`, `POST /telegram/qr/start {api_id, api_hash}` (QR login: `{ step: 'qr', url: 'tg://login?token=…', svg, expiresAt }` plus the status), `GET /telegram/qr/status` (`step: 'qr' | 'password' | 'done' | 'expired'`, with the current `url` and `svg` while `qr`), `POST /telegram/start {api_id, api_hash, phone}` (sends the code), `POST /telegram/verify {code}` (may answer `step: 'password'`), `POST /telegram/password {password}`, `POST /telegram/cancel`, `POST /telegram/logout`, `PUT /telegram/config {target, callSeconds}`, `POST /telegram/test {kind: 'message' | 'call'}` (through the sender on a device that is not the sender); the one sender of linked devices: `GET /relay`, `PUT /relay/sender {use: 'self'}`, `POST /relay/test {kind}` (see above). Errors are `{ error }` with an English text (Chinese in `i18n-zh-server.js`); Telegram errors are mapped to texts or `Telegram error <CODE>`.

**Telegram** (`telegram` 2.26.22, gramjs, MIT; about 3.3 MB, 11 MB with its new dependencies; one of them, `@cryptography/aes`, is GPL-3.0-or-later; loaded only when used). Account 1 (user API, not a bot) -> account 2.
- Phone login: a pending login (client, `phoneCodeHash`) lives in memory for 10 minutes. After it, the session string, `api_hash`, `api_id`, the masked phone and account 1's name are stored encrypted; the session string and `api_hash` are never logged and never returned (`status` has `hasApiHash` only). gramjs logging is off (`Logger('none')`), `floodSleepThreshold: 0` (flood waits come back as errors). Logout calls `auth.LogOut` and deletes the saved settings.
- QR login (the default in the page; the phone login is "Use phone number instead"): `qr/start` connects a client with an empty session and calls `auth.exportLoginToken {api_id, api_hash, except_ids: []}`. An `auth.loginToken` becomes `tg://login?token=<base64url>`, rendered on the server as an SVG string with the `qrcode` package (never a QR web service) and kept with its `expires`. `qr/status` exports again only when the token expired (1 s early) or `UpdateLoginToken` came (account 1 accepted the scan); one export at a time per login. `auth.loginTokenSuccess` finishes the login like the phone flow (phone from `getMe`, masked); `auth.loginTokenMigrateTo` calls `client._switchDC(dc)` and `auth.importLoginToken` there; `SESSION_PASSWORD_NEEDED` moves to the `password` step (`POST /telegram/password`). The pending QR login lives 10 minutes like the phone login; after it, or after cancel or a Telegram error, `qr/status` answers `expired`. We do not use gramjs `signInUserWithQrCode`: it sleeps 30 s per token and asks for the password through callbacks, which does not fit request/response endpoints. The login token is in the response by design (it is what the QR shows); the session string and `api_hash` never are.
- Page: the api_id / api_hash help is a link to https://my.telegram.org/apps and 4 steps. The QR step shows the SVG (as a `data:` image on a white square), "Open Telegram on the phone of account 1 → Settings → Devices → Link Desktop Device → scan this code" and Cancel; it polls `qr/status` every 2 s, skips the poll while the page is hidden or the QR is not visible (the group is folded or the sheet closed: the group's content stays mounted), and stops when the step ends.
- Not verified with a real account (no credentials here): the QR flow (token refresh, DC migration, 2FA) is tested against a mocked gramjs only; whether `UpdateLoginToken` reaches an unauthorized gramjs client in practice is not checked (if it does not, the scan is picked up at the next expiry, at most about 30 s later).
- Target: a username (`contacts.resolveUsername` through `getEntity`) or a numeric id (the dialogs are read first so the session knows it); stored as `{id, accessHash, username, name}`; must be a user other than account 1.
- Message: a compact card from the item and `item.context` (contract "context recall"), sent as Telegram HTML (`parseMode: 'html'`, no link preview). Lines with no value are left out: `<status emoji> <b>Status</b> · <b>Title</b>`, `From <device>` when relayed, and the task's own link (`link_url`, `link_label`) as `🔗 <a href>label</a>` (no label: the address, its text cut to 100 characters, the href whole); `Needs:` (`pending.text`), `<pre>` `pending.command`, `Reason:` (when it differs from Needs); `You asked:` (`latest_prompt`, one line), `<blockquote>` the `context.summary`, else the first 3 lines of `last_reply`; `Changed: 3 files, +42 -7` with at most 3 file names and `and N more`; the call-failed note in `<i>`; `<code>cwd</code> · <code>branch</code> · host · source`; `<a>Open in T-Agent</a>` (the page link of the notification). The task link is an `http(s)` address without a user name or password (at most 1000 characters), or a page path `/...` put under the page link (`new URL(path without its '/', page link)`, so a public address with a path keeps it; a page link that already ends with the path, as older devices sent it, is used as it is; no page link: left out); `javascript:`, credentials, `//host` and anything else are never written. When it is the page link itself (`/`), the footer link is left out. One emoji per status (the page icon rules cover the web page only). Values are cleaned (control, direction and half-surrogate characters removed) and cut first, then escaped, so an entity or tag is never cut in half and `<b>`, `&amp;` or Markdown marks in user text stay literal. `MESSAGE_MAX` (2000, Telegram allows 4096 UTF-16 units after parsing) is the visible length, shared out section by section: the header, link, note and footer are reserved first, then the task link, counted at its longest (plain) form and kept whole or left out. Only an `http(s)` address of at most 1000 characters is used, never cut; anything else is left out. An address that holds `+` or `tg://user?id=<n>` is written as text, because gramjs `_parseMessageText` reads such a link as a mention, looks it up and drops it. If Telegram refuses the entities (`ENTITY_*`, `ENTITIES_*`, `MESSAGE_EMPTY`, `MESSAGE_TOO_LONG`) the same card goes out once more as plain text (`messageText`, `parseMode: false`, with `🔗 <label>: <address>` and `Open: <address>`); other errors are not retried, and only the error code is logged. The Settings test message is this card with sample content (with a sample task link `PR #12`). A direct message card (below) has no task link. gramjs 2.26.22 `HTMLParser` (`telegram/extensions/html.js`, on htmlparser2) supports `b`/`strong`, `i`/`em`, `u`, `s`/`del`, `spoiler`, `code`, `pre` (with `<code class="language-x">` inside for the language), `blockquote` (`expandable` attribute for collapsed), `a` (`href`, `mailto:` becomes an email entity) and `tg-emoji`; it decodes entities, keeps newlines and counts offsets in UTF-16 units. `test/attention-notify-telegram.test.js` runs the real parser on the cards; how a real Telegram client draws them was not checked (no credentials here). A later change that only adds `context.summary` keeps the status, so it sends nothing again (only a status change notifies).
- Call: `messages.getDhConfig` -> a random `a`, `g_a = g^a mod p`, `g_a_hash = sha256(g_a)` -> `phone.requestCall` (protocol udp_p2p + reflector, layers 65-92) -> wait for `updatePhoneCall` (`phoneCallAccepted` = answered, `phoneCallDiscarded` = declined) or the ring time (default 30 s, 5-120) -> `phone.discardCall` (reason missed after a timeout, hangup after an answer; nothing after a decline). No `confirmCall`, no audio. Errors (`USER_PRIVACY_RESTRICTED`, `FLOOD` with seconds, others) give the message fallback.
- A connected client is reused for notifications and closed after 10 idle minutes.
- Network: gramjs ignores the proxy variables, so `makeClient` passes a SOCKS proxy read from the environment (`ALL_PROXY`, `all_proxy`, then `HTTPS_PROXY` / `https_proxy` when they are socks; `socks5`, `socks5h`, `socks4`, `socks4a`, `socks`, with credentials). gramjs has no HTTP proxy support: an `http://` value is ignored and the connection is direct. Connecting (QR, phone, notifications) and a QR token export give up after 20 s with "Cannot reach Telegram…" (504); the login is dropped, so the page leaves the QR step and shows the error, and the next notification connects again. A client is always ended with `stopClient`: gramjs's `disconnect()` leaves its update loop and a connecting socket alive.

**Email notifier** (`plugins/notifiers/email/`, `nodemailer` 10.3.1, MIT-0, required only when an email is sent; tests `test/attention-notify-email.test.js` with a fake transport and an in-process SMTP server on loopback, and the email part of `scripts/test-h5-notifier-browser.cjs`). Email from the person's own mailbox over SMTP; no relay between linked devices is needed, because every device can send email on its own.
- Settings (manifest `config`, drawn by the generic form): `provider` (`gmail` default, `163`, `custom` "Other SMTP server"; each option has its own help: Gmail needs 2-Step Verification, then an app password from https://myaccount.google.com/apppasswords; 163: Settings → POP3/SMTP/IMAP, turn on the SMTP service, copy the authorization code), `address` (required, also the SMTP login), `password` (required secret: the app password or authorization code, never the login password), `to` (optional, comma separated, at most 10; empty = the sender address), `fromName` (default `T-Agent`), and with `showWhen` provider `custom` only: `host`, `security` (`ssl` default, `starttls`, `none`), `port` (empty: 465 / 587 / 25 by security).
- Presets: Gmail `smtp.gmail.com:465` and 163 `smtp.163.com:465`, implicit TLS (`secure: true`); the preset wins over host, port and security. Custom: `ssl` = implicit TLS, `starttls` = `requireTLS` (the upgrade must succeed, never plain text after a failed STARTTLS), `none` only when the host is loopback (`localhost`, `127.x.x.x`, `::1`; else refused with "Security "None" is only allowed for an SMTP server on this computer…"), so a password never travels in plain text to another machine. Connection, greeting and socket timeouts are 20 s each. Proxies are not used (an SMTP server that is only reachable through a proxy does not work).
- `ready(config)`: a valid sender address and a password (and a host for custom). `status()`: `{ configured, summary }`, for example `Gmail · s***@gmail.com → m***@example.com` (addresses masked to the first letter and the domain, no network, never the password; `· no password saved` when it is missing).
- Status emails (`reason` `status`, `still`, `call_failed`): subject `[T-Attention] <status> · <title>` (one line, at most 180 characters), a text part and an HTML part built from the item like the Telegram card: status and title, `From <origin>` when relayed, the task link (`Link: <label> <address>` in the text, `<strong>Link:</strong> <a href>label</a>` in the HTML; no label: the address; the same rules as the Telegram card: http(s) without credentials, a page path under the page link, never `javascript:`), Needs (`pending.text`) with the command, the reason when it differs, You asked (`latest_prompt`), the summary or the first lines of the last reply, Changed (count, +/- lines, up to 10 paths), the call-failed note, cwd · branch · host · source, and "Open in T-Agent" with the http(s) page link (left out when the task link is that same page). Every value is cleaned of control characters and HTML-escaped; the HTML uses only `div`, `p`, `strong`, `em`, `pre`, `blockquote`, `ul`, `li`, `code`, `a` with inline styles, no images. Headers `Auto-Submitted: auto-generated` and `X-Auto-Response-Suppress: All`; nodemailer's file and URL access is off for the message.
- Calls: the manifest says `"modes": ["message", "off"]`; a call that still reaches the plugin returns `{ fallback: 'message', error: 'Email cannot make calls' }`. Direct messages (`direct: true`, `reason: 'direct'`): subject `[T-Agent] <title>` (no title: the first line of the text, cut to 80 characters), body the text, then `From: <from>`, then the link.
- Test: "T-Agent test email" (a short note and the sample item) → `{ ok: true, message: 'Test email sent to <masked recipients>' }`, plus a hint when the sender address does not match the provider (not `gmail.com` / `googlemail.com` for Gmail, which is fine for Google Workspace; not `163.com` for 163). Never a refusal.
- Errors (`explain`): `EAUTH` / 534 / 535 → "The email server refused the login: check the address and the app password / authorization code"; connection, DNS, socket and timeout codes → "Cannot reach the email server <host>:<port>"; `ETLS` → "The secure connection to the email server <host>:<port> failed: check the security setting"; `EENVELOPE` → "The email server refused the sender or a recipient address"; another SMTP answer → "The email server refused the email (<code>): <answer>" with the password and its base64 forms (AUTH PLAIN / LOGIN) replaced by `[hidden]`; else "Sending the email failed". The raw nodemailer error is never passed on; the log gets only the error code and the SMTP code.
- Security: the password is a manifest secret, stored encrypted in `attention-plugin:email:<owner>` like the other plugin settings and never sent to the browser. The `notifier-plugins` settings group syncs it (encrypted for the link) to linked devices, so each device sends its own email with the same mailbox. Not verified against the real Gmail or 163 servers (no account here): the presets follow the providers' published SMTP settings.

**Desktop window bubble** (`plugins/notifiers/widget/`, label "Desktop window (macOS)"; queue `services/widget-notices.js`; tests `test/widget-notices.test.js`, the notices part of `test/attention-widget.test.js`, the widget test of `test/attention-notify-relay.test.js` and the widget part of `scripts/test-h5-notifier-browser.cjs`). Shows T-Attention messages, `tcli notify` messages and the Settings test as a bubble beside the T-Attention desktop window of this Mac (see "Floating window notices" under "T-Attention desktop window (macOS)"); a click opens its link. `direct: true`, manifest `modes` `["message", "off"]` (a call that still arrives falls back to a message), `test: true`.
- Settings (manifest `config`): `seconds` "Show for", a select of `5`, `8` (default), `15`, `30` seconds or `0` "Until I close it".
- Ready (`ready`, `whyNotReady`, also the `status()` summary) only when the launcher's `state()` of `services/attention-widget.js` (wired by `server.js` through `setWidgetState`) says: macOS (`supported`), a server that may start the window (not `blocked`: test mode, CI, `TA_WIDGET_DISABLED`, a development copy in a T-Agent terminal), the window switch on (`enabled`) and the window running (`running`). Otherwise it is skipped quietly like any notifier that is not set up, and the Settings test answers why: "The desktop window is only available on macOS", "This server does not start the desktop window (test or development copy)", "Turn on the desktop window in Settings → T-Attention first", "The desktop window is not running: turn it off and on again in Settings → T-Attention".
- Local to each Mac: nothing goes over the network, and it is never relayed (`services/attention-relay.js` relays only `telegram`; a relayed delivery naming `widget` is refused with `UNKNOWN_NOTIFIER`). A Mac that sends Telegram through a linked sender still shows its own bubbles. Its manifest settings (switch and `seconds`) sync with the `notifier-plugins` group like the other notifiers; the window switch itself stays per device.
- Item notice: `title` = the item title (else the status label), `text` = `context.pending.text`, else `attention_reason`, else `result`, else the status label; `status`, `key` `local:<id>`; `from` = the relayed origin's name (never set today, since it is not relayed). Direct notice: `title` = the message title or "Message from an agent", `text`, `from`. Test notice: "Test message" with a short sample sentence.
- Target of a click: for an item its own `link_url` (an http(s) address as it is; a page path `/...` resolved against the address the window talks to, `TA_WIDGET_URL`, else against the origin of the notification `link`), else the notification `link` when it is http(s) (the public page address, `publicUrl`), else the T-Agent page the window talks to (`http://127.0.0.1:<port>/`), so a click opens T-Agent even without a public address. Direct messages and the test: the message `link`, else that T-Agent page. Only http(s) without a user name or password; `javascript:`, `data:`, `file:` and the like are never a target (null).

**Security and limits.** The account 1 session is full access to that Telegram account (messages, contacts, other sessions): it is stored with AES-256-GCM under the session secret like the other per-user secrets, and anyone with the data folder and `.env` can use it. Prefer a secondary account as account 1. Automating a user account is allowed by the API terms, but Telegram may limit or ban accounts that send too much or call too often: keep the hourly limits low (defaults 20 messages, 6 calls). Account 2 must allow calls from account 1. Not tried with a real Telegram login (no credentials here): the login, message and call flows are verified against a mocked gramjs only.
