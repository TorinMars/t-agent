# T-Attention: scheduled and recurring tasks

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

The user's request (2026-11-20): T-Attention supports one-time, scheduled and recurring tasks. An item may have a **When** (a schedule: once, or a repeating rule) and a **Then** (what happens at that time: remind me, send a prompt to a session, or run a script). A recurring item is one row: done puts it back for its next time and the timeline keeps every run. This file is the server side (data, the timer, the actions, the API, the CLI, the copies); the page is in [page-attention.md](page-attention.md). Code: `services/attention-schedule.js` (the rules, pure), `lib/lunar.js` (lunar dates, pure), `services/attention.js` (the columns, saving, firing, run now), `services/attention-scheduler.js` (the timer), `routes/attention.js`, the proxy in `routes/remote-servers.js`, `promptState` / `sendPrompt` / `runScript` in `routes/terminal.js`, `scripts/t-attention.js`. Tests: `test/attention-schedule.test.js` (the rules with fixed clocks and zones, yearly and lunar dates, `occurrencesIn`, the Chinese sentences), `test/attention-schedule-service.test.js` (saving, firing, done, prompts and scripts with fake sessions, the person-only rule, the timer, the notifiers, the copy rules), `test/attention-script-run.test.js` (real terminals: exit 0 and 2, the time limit, the last 5 terminals), `test/attention-schedule-http.test.js` (routes, tokens, `/v1`, the proxy), the CLI part of `test/attention-cli.test.js`, the 17 → 18 migration in `test/data-home.test.js`.

## Data (schema 18)

New columns of `attention_items` (`ensureScheduleColumns`, run by `db/index.js` and the service; added when missing, so any lower schema works; the index `idx_attention_items_next` on `next_at` is made there too):

- `schedule` (JSON or NULL): `{ kind: 'once', at: 'YYYY-MM-DDTHH:mm', tz }` or `{ kind: 'repeat', rule: { freq: 'daily' | 'weekdays' | 'weekly' | 'monthly' | 'every' | 'yearly', days? (weekly, Monday = 1), day? (monthly, 1..31; a shorter month uses its last day), interval? (every N days, 1..365), time: 'HH:mm' }, starts?, ends?: { kind: 'on', date } | { kind: 'after', count (1..9999) }, tz }`; a yearly rule is `{ freq: 'yearly', calendar: 'solar' | 'lunar', month, day, leap?, occasion?, year?, time }` (below, "Yearly dates"). Wall times are local to `tz`, the IANA zone of the owner engine when it was saved (a body may name one). Stored in a canonical form (fixed key order, days sorted, `ends: never` and empty parts left out), so the page sending the same schedule back is no change: a value without `tz` (or without `starts` for "every N days") keeps those of the current schedule when it is otherwise the same, else it gets this engine's zone and today. "Every N days" always has `starts` (today when none is given): its days are counted from there.
- `then_action` (JSON or NULL = remind me): `{ kind: 'prompt', task_id, terminal_id, text (1..4000) }` (a session of the owner engine; checked to exist when saved) or `{ kind: 'script', task_id, script (1..4000), timeout_min (1..720, default 30) }` (a task of the owner engine, in use).
- Kept by the server: `next_at` (ISO UTC, NULL when nothing is left to fire), `schedule_state` (`waiting` before its time, `due` fired and not done yet, NULL: no schedule, or nothing left: a once item done, a repeat that ended, cancelled or failed), `runs` (times fired since the schedule was saved: a new schedule starts at 0, "ends after N" counts these), `last_fired_at`, `last_done_at`, `script_runs` (JSON, the last 5 script runs `[{ terminal_id, task_id, at, ended_at, outcome: exit | timeout | ended, exit, duration_ms }]`).
- Every item JSON (list, get, stream, copies, `/v1/attention`, the proxy) also carries `schedule_text` (the English sentence, below) and `last_exit` (the exit status of the last script run that ended, NULL when none or it was stopped). `rowToItem` makes them; the copies' check at start uses the same function, so a journal row matches what the bus wrote.
- No `system_state` key.

## Yearly dates (birthdays and anniversaries)

The user's request (2026-11-26): a calendar of T-Attention with birthdays (also lunar) and anniversaries. They are ordinary repeat items with the rule `freq: 'yearly'` (no new table): shown in the list's Recurring section, fired and reminded like every repeat item, and done puts them back for their next year. Reminding some days before is not in this version.

- Rule keys, only for `yearly`, in this canonical order: `freq`, `calendar` ('solar', the default, always written; or 'lunar', the Chinese lunisolar calendar), `month` (1..12), `day` (1..31; lunar 1..30), `leap` (lunar only, only `true`: the leap month of that number; `false` is left out), `occasion` ('birthday' | 'anniversary'; absent: a plain yearly reminder), `year` (1900..2100, the year it began), `time`. The server only validates and keeps `occasion` and `year`: the page shows the number ("turns 62", "8th anniversary") as the occurrence's solar year minus `year`.
- A solar date must exist at least in a leap year: 2-29 is accepted, 2-30 and 4-31 are refused ("There is no day 30 in month 2"). Solar Feb 29 falls on Feb 28 in a common year.
- Lunar: day 30 of a 29-day month falls on its day 29. A `leap` rule happens only in the years that have that leap month (leap month 6: 2025, then 2036); a rule without `leap` never falls in the leap month (lunar 6/1 of 2025 is 2025-06-25, not the leap 6/1 on 2025-07-25).
- Walking: a yearly rule is not walked day by day (a leap month can be years away) but year by year (`nextDay`, at most `YEARLY_YEARS` = 100 years ahead); a date that does not come in that time has no next time (saving is a 400 like any rule with nothing ahead, and the preview says "This date does not come in the next 100 years").
- Capability `attention:yearly` in `/v1/info` next to `attention:schedule`: an older engine refuses `freq: 'yearly'`, so the page offers birthdays and anniversaries only on an engine that lists it.

### Lunar dates

`lib/lunar.js` is pure and uses only `Intl.DateTimeFormat('en-u-ca-chinese')` with `formatToParts` (no table, no dependency): `month` is "6" or "6bis" (a leap month), `relatedYear` the solar year the lunar year starts in (without it, months 11 and 12 in January or February belong to the year before). `lunarOf('YYYY-MM-DD')` → `{ year, month, day, leap }`; `dayOf(year, month, day, leap)` → the solar day of a lunar date in lunar year `year` (null: no such leap month); `monthStart` finds day 1 of a month from a guess after the new year (January 21 is in the first month or one or two before it) in whole-month steps; a year shorter than 370 days has no leap month and is skipped at once. One Intl call costs about 0.2 to 0.6 ms on a Mac, so every day and every month found is cached (bounded maps). Checked facts: 2026-11-15 is lunar 10/7, 2026-11-12 is 10/4, 2025-07-25 is leap 6/1.

### Page occurrences (`occurrencesIn`)

The page's calendar expands items into days itself (no endpoint): `occurrencesIn(schedule, fromDate, toDate)` → `['YYYY-MM-DD', ...]`, the days in the schedule's own zone between the two dates (both included), for once and every repeat rule including yearly and lunar. It honors `starts` and an end on a date; "ends after N" counts N occurrences from the first one on or after `starts` (from `fromDate` without one), which is exact only for a schedule that has never fired (enough for a calendar). A range longer than 400 days is cut there (`RANGE_DAYS`); a backwards range or a date that is not valid gives `[]`. The page bundles `services/attention-schedule.js` and `lib/lunar.js` with esbuild (as `attention-model.mjs` bundles `lib/attention-home.js`), so neither may use a Node-only module.

## Times and daylight saving time

`localToUtc` turns a wall time into an instant with `Intl.DateTimeFormat` in the stored zone: the offsets around the day are tried and the one whose wall clock matches is taken. A wall time that happens twice (the clock goes back) is the first of the two, so it fires once; one that does not exist (the clock jumps forward) moves to the first minute after the gap (a binary search over minutes), e.g. 02:30 on 2027-03-14 in New York fires at 03:00 EDT. The rule is walked over calendar days of the zone (at most 400; yearly rules year by year), so every rule keeps its wall time across a change.

## Saving

- A new or changed schedule computes `next_at` (the first time after now; a once time in the past is still its time, so it fires at once), sets `schedule_state = 'waiting'`, `runs = 0`, and a closed item becomes To do. A repeating schedule with nothing ahead (it ends before its next time) is a 400. `schedule: null` clears it (`next_at` and `schedule_state` NULL; `runs` stays).
- **Done of a recurring item** (the page, the CLI, `confirm`, a linked engine): `last_done_at`, the next time, status back to To do, `waiting`. Done while it is due: the next time after now; done while it still waits (before its time): that time is skipped. The event is a `status` change with `to_status: 'done'` and `data.recurring: true`, while the item itself is back in To do (one row). When the end is reached it is a normal done item. A note left by a failed prompt or script is cleared.
- Done of a once item: a normal done (`next_at`, `schedule_state` NULL). Failed or cancelled ends what is left to fire; an item opened again picks up its next time.
- Validation: unknown fields, bad dates and times, an empty weekly day list, a part of another rule (`day` on a daily rule), an unknown zone, an end before the start, a prompt without a session, a session or task that does not exist here → 400 `VALIDATION_FAILED` with an English message (Chinese in `i18n-zh-server.js`).

## Firing

`services/attention-scheduler.js` runs on the owner engine (started in `server.js` once it listens): at the start, then at the next `next_at`, at most a minute apart; a change that brings a time closer sets the timer again. Each round fires every item with `next_at <= now` (`fireDue`). The copies of other engines live in `attention_copies` and are never fired.

- Never twice: the firing (`runs + 1`, `last_fired_at`, the next `next_at`, the state, an event `scheduled`) is written in one transaction that checks the item is still due with the same `next_at`; the prompt is typed or the script started after the commit, and the change is published after that. A restart finds the advanced `next_at`. A crash between the commit and the notification loses that notification (at most once).
- Times missed while the engine was off fire once: the event's `data.missed` is the number of times that passed (only when more than one).
- **Remind**: status To do when it was closed (else unchanged), `schedule_state = 'due'`, the item at the top of its group, and the published change carries `scheduled_due: true`. The notifiers (`remindScheduled` in `services/attention-notify.js`) send it once per firing (the key names `last_fired_at`) through the rules of Needs you (`waiting_user`: on or off, each notifier's mode, quiet hours), at once (no message delay: the person chose the time) and whatever is on screen. The page reminds on `scheduled_due` like on Needs you; the copy rows keep the marker, so a linked page reminds too.
- **Prompt** (`promptState` in `routes/terminal.js`): idle means a running shell, the activity not running and not waiting for an answer, and in the foreground the agent of an agent terminal or the shell prompt of a shell terminal (an agent that exited to its shell counts as busy: the prompt is never typed into a shell meant for an agent). Idle: the text is typed (`sendPrompt`: an agent gets it as a paste with Enter on its own, the desktop window's reply path; a shell gets typed keys and Enter), events `scheduled` and `prompt_sent`, and the run counts as done at once (recurring: To do and `waiting`; once: done). Otherwise status Needs you, `schedule_state = 'due'` and the reason "The session was busy at 09:00; the prompt was not sent" ("was not running" for a terminal without a shell, "was not found" for one that is gone; HH:mm in the schedule's zone).
- **Script** (below). A script item whose last run still runs skips the firing (`data.outcome: 'skipped'`, only the next time moves on).

## Run a script

- Each run is a NEW terminal of the task, made and started like one the person opens (`createTerminal` and `getOrCreateSession` in `routes/terminal.js`: the task's folder, the user's shell, the same environment and tokens), named "<title> · HH:mm". The server writes two files to `<data home>/attention-scripts/` (mode 600; when a root service drops to `TERMINAL_USER`, a folder of the temporary directory owned by that user): the script, and a wrapper that prints an OSC 7771 marker with a random nonce and its own pid, runs the script with the terminal's shell, removes both files and prints a second marker with the exit status. The wrapper is the shell's first typed line (with a leading space, so it stays out of the history); xterm ignores the unknown OSC, so the markers are invisible. The server reads them from the terminal's output.
- The terminal stays open at its prompt with the output, so "Open terminal" shows it (`context.tagent` of the item points at the last run's terminal). An item keeps its last 5 script terminals; when a run starts, the older ones are removed (their shell ends and their row goes).
- The time limit (`timeout_min`) sends SIGTERM to the script's process group (the wrapper's pid: an interactive shell puts each job in a group of its own), SIGKILL 3 s later; without a pid yet it sends Ctrl+C. A terminal that ends first (closed, deleted) ends the run as stopped; a run open when the server stopped is ended as stopped at the next start (`recoverScripts`).
- While it runs: status Working, `schedule_state = 'due'`. Exit 0: event `script_done` `{ terminal_id, outcome, exit, duration_ms }`, the run counts as done (recurring: To do and `waiting`; once: done). Another exit status, the time limit or an early end: event `script_failed` with the terminal id, status Needs you, `schedule_state = 'due'`, the reason "Script failed (exit 2) at 09:01", "Script stopped after 30 min at 09:31" or "Script stopped at 09:31". `run-now` runs it again ("Run again"; 409 `SCRIPT_RUNNING` while a run is open).
- **Only the person** sets or changes a script: the page (the browser session, also through the remote proxy, whose Engine token is the person), or a CLI token made in Settings. A terminal's own T-Attention token (what agents use; `tagent` of the token) gets 403 `SCRIPT_NEEDS_PERSON` for creating a script action, changing or removing one, changing the schedule of a script item, and run now of a script item; it may still read it and mark it done. Every change of a script is an `updated` event with its actor.

## API

- `POST /api/attention/schedule/preview { schedule }` (session and tokens; also `/v1/attention/schedule/preview` and `/api/remote-servers/:id/attention/schedule/preview`) → `{ next: [up to 3 ISO UTC], text }`, or `{ next: [], text: null, error }` for a schedule that is not valid (200, for the edit view's "Next" line while the person types). In this engine's zone unless the schedule names one.
- `POST /api/attention/:id/run-now` (session and tokens; `/v1`, the proxy) → `{ item }`. A prompt is sent when its session is idle, else 409 `SESSION_BUSY`, `SESSION_NOT_RUNNING` or `SESSION_NOT_FOUND` and nothing changes; a script runs again; a reminder fires now (a recurring item keeps its next time, a once item has used its time). An item with no schedule and no action → 400.
- Capability `attention:schedule` in `/v1/info`: an older engine ignores a schedule it is sent, so a page offers schedules only on an engine that lists it, and the proxy answers 501 `ATTENTION_SCHEDULE_UNSUPPORTED` for the preview and run now of an engine without it (`has()` in `services/remote-attention.js`, from the cached `/v1/info`). The tunnel lets both paths through (`/v1/attention/*`). It is not in `SHARED_CAPABILITIES` of the version banner: schedules belong to one engine.
- Owner offline: run now is refused (409 `ATTENTION_OWNER_OFFLINE`, "A scheduled task can only be run while the device it belongs to is online"); `schedule` and `then_action` are unsafe fields of the queue (refused), except that a value equal to the copy's is left out first (the page sends its whole form); the preview is worked out on this engine (`local: true`). See [attention-copies.md](attention-copies.md).

## Sentence (`schedule_text`)

"Once on 2026-12-01 at 10:00", "Every day at 09:00", "Every weekday at 09:00", "Every Monday and Thursday at 09:00", "Every Monday, Wednesday and Friday at 09:00", "Every month on day 15 at 09:00", "Every 3 days at 09:00", "Every year on 11-15 at 09:00", "Every year on lunar month 10, day 7 at 09:00", "Every year on lunar leap month 6, day 1 at 09:00", then parts after " · ": "birthday" or "anniversary" (the occasion), "starting 2026-11-20", "until 2027-01-31", "ends after 5 times". Weekly with all seven days reads "Every day", with Monday to Friday "Every weekday". The Chinese is in `public/js/i18n-zh-extra.js`: a template per sentence (one per number of days, so each day name is a slot), the day names, and the parts, which the page's translator takes one by one at " · " (every part starts with fixed words, so no template swallows the whole line).

## CLI

`t-attention add "<title>" --at 2026-12-01T10:00` (once) or `--every daily|weekdays|weekly:mon,thu|monthly:15|every:3d --time 09:00 [--starts YYYY-MM-DD] [--ends YYYY-MM-DD|after:N|never]` (repeats), `--prompt "<text>" --session <task id>:<terminal id>` (then type the prompt; `update --prompt ''` goes back to a reminder); `update <id>` takes the same and `--no-schedule`. The server adds its zone. `list` shows the rule (without its first and last day) and the next time on the row ("Every Monday at 09:00 · next 11-23 09:00 · sends a prompt"), `add` and `show` the whole sentence. Scripts are not set from the CLI in this version (the page sets them). The t-attention skill mentions it in one line.

## Limits

- The timer fires on the owner only: while the owner engine is off, its reminders do not fire anywhere; they fire once (with the count of missed times) when it is back. Copies on other engines show the last state "as of".
- A prompt or script for a terminal of another engine is not possible (the session must be on the owner).
- A script terminal's shell needs a moment to start (the user's shell setup runs first); a script that reads the terminal's input waits for the person.
- The firing is at most once: a crash right after the commit loses that notification or prompt.
