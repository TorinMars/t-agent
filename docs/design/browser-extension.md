# Browser extension

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

A Chrome extension (Manifest V3, `extensions/chrome/`) that agent sessions drive with `tcli browser ...`, so a model can open and operate web pages in the person's own, logged-in Chrome, read the page and its network traffic, and record how a site works (the material of the site capability library, `tcli site`). Three parts: the extension (`extensions/chrome/`, its own tests), the core described here (the server bridge, pairing, the tcli relay, `tcli browser`, recordings, the Settings part), and the site library (its own section). This section holds the shared contract (v1) in compact form; anything not fixed by it is a decision of the part that owns it, listed under "Core decisions".

- **`tabs.reveal { origin }`** (extension 1.0.3, the one method beyond the 25 of v1; in `METHODS` of `services/browser-bridge.js`): brings the tab of a T-Agent page to the front for the desktop window's Open session (`POST /api/attention/widget/open-terminal`). The tab is a top-level page of that exact origin (no `pane` parameter); the active tab of the last focused window when it is one, else the one used last (`lastAccessed`). It reads no page, so it needs no handed tab. `{ focused: true, tab_id }`, or `{ focused: false }` when there is no such tab; an origin that is not `http(s)://host[:port]` is `BAD_PARAMS`. An older extension does not list it in its `hello`, so the bridge answers `UNKNOWN_METHOD` and the caller falls back.

```
tcli browser (terminal) --HTTP, hook token--> /api/tcli/browser/* --+
                                                                    |  services/browser-bridge.js
Settings page --login--> /api/browser-ext* ------------------------+--> pairing, tokens (system_state browser_ext_v1)
                                                                    |    commands c_<n> with timeouts, events
extension options page --one-time code--> POST /api/browser-ext/pair|
extension service worker <==WebSocket /api/browser-ext/ws
```

## Recording

A recording (`record.start`, or `tabs.open` with `record`) attaches the debugger to the tab and injects the page recorder (`installRecorder` in `extensions/chrome/page.js`). Items go out in `record.items` batches (at most 200 per batch, every second and at the stop), redacted by the extension (`redact.js`) and again by the server (`services/browser-recordings.js`), one JSON line each. Kinds: `request`, `response`, `ws`, `console` (from the debugger), `click`, `input`, `change`, `submit`, `key`, `hover`, `scroll` (actions), `nav` (address changes, from `chrome.tabs.onUpdated`) and `dom`.

- **Recording from the first load** (extension 1.0.4; `tcli browser open <url> --record [record options]`). `tabs.open { url, active, record: { network, dom, bodies, types, drop_other_types, max_body_bytes } }` creates the tab on `about:blank` (an HTTP page cannot be scripted before it exists, but the debugger can attach to about:blank), joins it to the T-Agent group, attaches the debugger and starts the recording there, writes a `nav` item `{ source: 'agent', action: 'open', from: 'about:blank', to: url }`, and only then navigates. So the first document request and everything after it are recorded once, with no reload. It answers when the tab has committed the page: `{ tab, recording_id, options }` (the bridge registers the recording with the task and terminal, as for `record.start`). A late `about:blank` from `onUpdated` does not end the recording (`openingUntil`). The page recorder goes in when the debugger reports that the main frame committed a document (`Page.frameNavigated`, with `injectImmediately`) and again at DOMContentLoaded and at load; it runs once per document and recording (a second call does nothing). On a fast page the HTML is parsed before the recorder gets in, so the recorder's first `dom` item also lists what the document already shows, marked `initial: true`.
- **Type and size filters** (1.0.4; `record start` and `open --record`: `--types T` (`types`, CDP resource types in any case: Document, Stylesheet, Image, Media, Font, Script, TextTrack, XHR, Fetch, Prefetch, EventSource, WebSocket, Manifest, SignedExchange, Ping, CSPViolationReport, Preflight, Other; `--type` is the same), `--drop-other-types` (`drop_other_types`, needs `types`), `--max-body N` (`max_body_bytes`, 0 to 2 MiB). Defaults are as before: every type, bodies up to 2 MiB. With `types`, a request of another type keeps its `request` and `response` items but without bodies (no `post_data`, `body`, `body_base64`, frame data; `body_omitted: 'type'`), so the timeline stays whole; with `drop_other_types` it has no items at all. When the recording attached the debugger itself, the bodies of other types are not even fetched (`body_types` in the capture options of `capture.js`); a capture `net start` runs keeps its own rules and the filters apply to the recording's items only (`shapeNetwork` in `background.js`). A body over `max_body_bytes` is cut: `body_truncated: true` (or `post_data_truncated`, or `truncated` on a frame), and `response.body_bytes` / `request.post_data_bytes` hold the size before any cut (also in `net get`). `record.start` answers `{ recording_id, tab_id, url, options }`; the options are kept in the recording's summary (`options`, `record show` prints them as `filters`).
- **Sources.** An action of a tcli command is one item with `source: 'agent'` and `command` (`input.click` → `click` with `button`, `count`; `input.type` → `input` with `value` (the typed text; `<redacted:N>` when the target is a password or a secret-named field), `clear`, `submit`; `input.press` → `key` (a printable key without Control or Meta is `<redacted:1>`); `input.select` → `change` with `values`; `input.hover` → `hover`; `input.scroll` → `scroll` with `dx`, `dy`; `modifiers` when given), with the resolved `target`, written before the input is sent so the requests it causes come after it. The address changes during a tcli `go`, `back` or `forward` (and its redirects) are `nav` items with `source: 'agent'` and `action`; a reload, or a `go` that leaves the address as it was, is one such item of its own. The person's actions are recorded by the page recorder with `source: 'user'` (`synthetic: true` when the page's own script made the event); other address changes (a followed link, a redirect, the person typing an address) have no source, nor do network, console and DOM items. No double items: the recorder leaves out the events of a command, which the page script marks while it dispatches them (`__tagentAgentBusy`) and the worker marks around debugger input (`agentWindow`: `__tagentAgentUntil`, 10 s before, 150 ms after); the Enter of `type --submit` is part of the `input` item.
- **Targets.** `click`, `input`, `change` and `submit` items (and agent items) keep `target { tag, role, name, text, selector, rect }` and add `type` (inputs), `sensitive: true` (a password or secret-named field) and `nearest`: the nearest meaningful element going up from the target, itself included, at most 10 levels and never `<body>`: the first that is interactive (a link, a button, a form field, an ARIA widget role, `tabindex`, `onclick`) or labelled (`aria-label`, `aria-labelledby`, `title`, `alt`, an SVG `<title>`); when the walk has left a run of `cursor: pointer` elements that started at the target, the top of that run; else the first element with a visible text of at most 80 characters. `nearest { tag, depth, role?, aria_label?, title?, alt?, name (the accessible name, about 80 characters), text (visible text, trimmed, at most 80), selector }`; the selector prefers `#id`, then a unique `data-testid` / `data-test` / `data-qa` / `data-cy` / `aria-label` / `name` / `title`, then an `nth-of-type` path.
- **DOM change items** (every 500 ms when something changed): `summary { added, removed, attrs }` as before, and `appeared`: what showed up, in this order of kinds: `dialog` (`dialog`, `role=dialog|alertdialog`, also one that opened by an attribute change), `alert` (`role=alert|status`, `aria-live` regions, `output`; also text put into one), `notice` (a class containing toast, snackbar, notification, notice, message, alert, error or modal), `heading`, `button`, `link`, each `{ type, tag, role?, text }` with the visible text (or aria-label) collapsed to at most 120 characters, only visible elements, each text once per item and not again while the element shows the same text. At most 20 candidates of a kind and 3000 checked nodes per item, at most 20 entries (`appeared_more` counts the rest). The texts are redacted like every other item (a JWT or a bearer token in page text becomes `<redacted:N>`; the vectors are the `items` section of `test/fixtures/browser-redact-vectors.json`). The old `landmarks` field (always empty in practice) is gone.
- **Older extensions.** The hello lists `features` besides `methods` (1.0.4: `open.record`, `record.types`, `record.max_body`, `record.agent_actions`, `record.dom_text`). The bridge refuses an option an extension would silently ignore: `PARAM_FEATURES` in `services/browser-bridge.js` (`tabs.open` `record`; `record.start` `types`, `drop_other_types`, `max_body_bytes`) answers `UNKNOWN_METHOD` "The extension is older than this command (version 1.0.3 does not support record start --types): reload it in chrome://extensions" and nothing reaches the browser.
- Tests: `extensions/chrome/test/worker.test.cjs` (mocked Chrome: the order create about:blank → attach → Network.enable → navigate, the filters, agent items before their input, secret values), `page.test.cjs`, `extension.test.cjs` (real headless Chromium: one load of the page, the Document request, cut and omitted bodies, a person's click on an SVG icon with its labelled parent, one agent click, appeared texts with caps and redaction), `test/browser-bridge.test.js`, `test/tcli-browser-cli.test.js`, `test/browser-redact.test.js`.
