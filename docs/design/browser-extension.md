# Browser extension

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

A Chrome extension (Manifest V3, `extensions/chrome/`) that agent sessions drive with `tcli browser ...`, so a model can open and operate web pages in the person's own, logged-in Chrome, read the page and its network traffic, and record how a site works (the material of the site capability library, `tcli site`). Three parts: the extension (`extensions/chrome/`, its own tests), the core described here (the server bridge, pairing, the tcli relay, `tcli browser`, recordings, the Settings part), and the site library (its own section). This section holds the shared contract (v1) in compact form; anything not fixed by it is a decision of the part that owns it, listed under "Core decisions".

- **`tabs.reveal { origin }`** (extension 1.0.3, the one method beyond the 25 of v1; in `METHODS` of `services/browser-bridge.js`): brings the tab of a T-Agent page to the front for the desktop window's Open session (`POST /api/attention/widget/open-terminal`). The tab is a top-level page of that exact origin (no `pane` parameter); the active tab of the last focused window when it is one, else the one used last (`lastAccessed`). It reads no page, so it needs no handed tab. `{ focused: true, tab_id }`, or `{ focused: false }` when there is no such tab; an origin that is not `http(s)://host[:port]` is `BAD_PARAMS`. An older extension does not list it in its `hello`, so the bridge answers `UNKNOWN_METHOD` and the caller falls back.

```
tcli browser (terminal) --HTTP, hook token--> /api/tcli/browser/* --+
                                                                    |  services/browser-bridge.js
Settings page --login--> /api/browser-ext* ------------------------+--> pairing, tokens (system_state browser_ext_v1)
                                                                    |    commands c_<n> with timeouts, events
extension options page --one-time code--> POST /api/browser-ext/pair|
extension service worker <==WebSocket /api/browser-ext/ws
```

## Focus and closing

Extension 1.0.5 (`features`: `open.keep`, `close.auto`, `shot.inactive`, `dialog.answer`, `tab.used`, `reload`). The person never loses their focus to T-Agent, and the tabs an agent opened go away when it is done. 1.0.6 (`open.window`, `record.tabs`) gives `open --record` its own window in front and lets a recording follow the tabs its page opens. 1.0.7 leaves no group behind: Chrome keeps the group of a closed tab as a saved tab group in the bookmarks bar (it forgets a group only when ungrouping empties it), so T-Agent's own closing (`closeTab`: `tabs.close`, and the tab of a failed recording start) ungroups the tab first; a tab the person used was already ungrouped, and a handed tab is only released.

- **T-Agent's window.** `tabs.open` puts every tab it opens into one Chrome window of T-Agent's: `chrome.windows.create({ url, focused: false, state: 'normal' })`, created behind the person's windows and never minimized (a minimized window's pages are not drawn). Its id is kept in `storage.session` (`agent_window`, like `owned`) and the window is reused while it exists and holds a tab T-Agent owns; else (the person closed it, moved the tabs away, or only their own or released tabs are left in it) the next open makes a new one. Chrome closes it when its last tab closes; T-Agent never closes a window. Later tabs are created in it with `active: false`. The "T-Agent" group is made in that window with `createProperties.windowId`: without it `chrome.tabs.group` makes the group in the "current" window (the person's) and moves the tab there, which is what took tabs into the person's window before. Handed tabs stay where they are.
- **No focus taken.** Only four commands activate a tab or focus a window: `tabs.activate`, `tabs.open` with `active` (`--active`; the tab still goes into T-Agent's window, which is then focused), `tabs.open` with `window: 'front'` (a recording's own window, below) and `tabs.reveal` (the desktop window's Open session). Checked and left as they are, because they never activate or focus: navigation (`tabs.update` with `url`, `reload`, `goBack` / `goForward`, `history.back()` in the page), `tabs.group` / `tabGroups.update`, `scripting.executeScript` (all worlds), `debugger.attach` (Chrome's yellow bar appears in every window but takes no focus), CDP input, `tabs.remove` (Chrome activates a neighbour inside that window only). A page may still open a popup window of its own (`window.open` after a trusted click), which Chrome shows in front: that is the page's doing and is not prevented.
- **Visible screenshot.** `page.screenshot` without `full_page` or `target` attaches the debugger for the moment (like `wait --idle`) and takes `Page.captureScreenshot` of the viewport, so the tab need not be active and its window need not be in front; the size is the viewport times the device pixel ratio, as before. Only when the debugger cannot attach (`DEBUGGER_BUSY`: DevTools is open) and the tab is the active one of its window does `chrome.tabs.captureVisibleTab` take it; an inactive tab then fails with that error. A tab that draws no picture in 15 s answers `TIMEOUT` with the advice to activate it.
- **Page dialogs.** While the debugger is attached (net capture, a recording, and the short attaches of `shot` and `wait --idle`), `Page.javascriptDialogOpening` is answered at once with `Page.handleJavaScriptDialog` (`capture.js`): an alert and a beforeunload are accepted (the page goes on, a navigation or a close proceeds), a confirm and a prompt are dismissed (false / null: nothing is agreed to on the person's behalf). So Chrome never waits on the dialog and never brings the tab forward. Each dialog `{ at, type, message (redacted, at most 500 characters), url, handled: 'accepted' | 'dismissed' }` is kept per tab (at most 20) and comes with the tab's next command result as `dialogs` (once); it is also a console line `dialog: <type> <message> (<handled>)` (level `dialog`, in `page.console` and in a recording's console items). tcli prints one `dialog: confirm "Delete all?" (dismissed)` line per dialog on stderr. Without the debugger a dialog is Chrome's own: it blocks the page until someone answers it, and a command on that page waits until it times out.
- **The person's tab.** A T-Agent tab the person uses leaves T-Agent's care: when they activate it in a window that has the focus (`chrome.tabs.onActivated`, checked 300 ms later; not T-Agent's own activations, which are quiet for 1.5 s, and not when a tab of that window closed or moved out in the last 1.5 s, when Chrome picked the neighbour itself), or when they click or type in it (a small watcher injected in the isolated world of each owned tab's page reports the first trusted `pointerdown` / `keydown`, at most every 500 ms; events during a T-Agent command and 1 s after it are the command's own CDP input). The tab is ungrouped, dropped from `owned` and stays where it is; the extension sends `tab.used { tab_id, how: 'activated' | 'input' | 'ungrouped' }` and T-Agent never closes it. A recorded tab is the exception (the person's actions are what a recording is for): it stays T-Agent's but becomes kept, `tab.used { kept: true }`. Taking a tab out of the group or out of T-Agent's window also releases it (`how: 'ungrouped'`).
- **The recording's own window** (extension 1.0.6, `features` `open.window`). The person usually acts in a page while it records, so `tcli browser open <url> --record` sends `tabs.open { ..., record, window: 'front' }`: the tab gets a new window of its own, `chrome.windows.create({ url: 'about:blank', focused: true, state: 'normal' })`, in front, normal size, never minimized, and the recording starts there as in "Recording from the first load". `--record --background` sends `window: 'back'` (`focused: false`) for a recording the agent drives itself. One window per such open: it is never T-Agent's shared window (`agent_window` stays as it was), so no later `open` reuses it, and a later `open` without `--record` still goes to the shared window behind. The tab is grouped in its own window and is an owned tab like any other: after the recording stops, a tab the person used stays theirs (kept, as for any recorded tab) and an unused one closes by the rules of "Closing T-Agent's tabs" (2 minutes after the turn ends, the terminal closed, 30 minutes idle); Chrome closes the window with its last tab, and T-Agent never closes a window itself (a tab the person opened there keeps it). The window's first activation is T-Agent's own (quiet), not the person's use. The answer adds `window { window_id, focused, own: true }`, and tcli prints "Opened a new window in front for the recording: the person can use the page while it records." (or "Opened its own window in the background for the recording."). `window` without `record`, or another value, is `BAD_PARAMS`; `--background` without `--record` is a usage error; an extension before 1.0.6 refuses `window` (`PARAM_FEATURES`). `record start` on an existing tab is unchanged: no new window.
- **Keep.** `tabs.open { keep: true }` (`tcli browser open --keep`) marks an owned tab that T-Agent never closes by itself (`kept` in `storage.session`; `keep: true` in its tab info, `[group, keep]` in `tcli browser tabs`). The agent says so to the person. A normal `close` still closes it.

### Closing T-Agent's tabs

The bridge keeps the care of the tabs (`services/browser-tab-care.js`, memory only), for an extension that lists `close.auto`. Each command result from 1.0.5 carries `tab { tab_id, how, keep? }` beside `result` (also with an error), the tab the command used; a tab with `how: 'group'` belongs to the terminal (task id + terminal id of the tcli request, `req.terminalContext`) that used it last. `tabs.close` and `TAB_NOT_FOUND` forget it, so do `tab.closed`, `tab.released` and `tab.used` (`kept: true` makes it kept instead). A tab a recorded tab opened (`tab.opened`, 1.0.6) is cared for from then on with its opener's terminal and turn state (`care.opened`; no terminal when the opener has no entry, e.g. a handed tab, so only the 30 minutes apply). A tab is closed with `tabs.close { tab_id, auto: true }` (the extension refuses with `TAB_NOT_ALLOWED` a tab that is handed, kept or not owned) when:

- its terminal's Claude or Codex turn ended (`onAgentTurnEnd` of `routes/terminal.js`: the activity went from running to done or idle; each listener gets `(agent, { task_id, terminal_id })`) and the tab has had no command for 2 minutes: at once when that is already so, else when the 2 minutes are over; a new command on the tab cancels it until the next turn end;
- its terminal was closed, deleted or restarted, its task's terminals were closed, or its shell ended (`onTerminalEnded` of `routes/terminal.js`): at once;
- in any case, 30 minutes after its last command.

Never closed: kept tabs, handed tabs, tabs the person used. A close that is due while the browser is offline (`BROWSER_NOT_CONNECTED`, `BROWSER_TIMEOUT`) waits in a list per browser (at most 200) and is sent when it says hello again. The hello of 1.0.5 lists `owned_tabs [{ tab_id, keep? }]` (at most 500): T-Agent forgets the tabs it cares for that are not in it and adopts the ones it does not know (after a T-Agent restart), without a terminal, so the 30 minutes apply. Closing never takes the focus. `bridge.tabCare()` gives the state for tests. An extension before 1.0.5 is not cared for: its tabs stay until closed.

### The extension updates itself

Chrome does not reload an unpacked extension when its files change, so an old version kept running after T-Agent updated `extensions/chrome/`. The hello of 1.0.5 says `install_type` (`chrome.management.getSelf().installType`; `development` when loaded unpacked). When it is `development` and the version in this install's `extensions/chrome/manifest.json` (read at each hello) is newer than the hello's, the bridge sends `{ type: 'reload', version }`: at most once per browser and reported version in 10 minutes, and not again after 3 tries for the same versions (the extension then runs from another folder). The extension itself reads its own folder's `manifest.json` (Chrome serves an unpacked extension's files from disk) and reloads only when that is newer than the running version and it has not tried that version in the last 10 minutes (`last_reload` in `storage.local`), and only once no command and no recording runs (it waits for them). Before `chrome.runtime.reload()` it writes the owned, handed and kept tabs and its window to `storage.local` (`reload_state`; `storage.session` is cleared by a reload) and takes them back when it starts within 2 minutes. An extension before 1.0.5 ignores the message: it must be reloaded once by hand in `chrome://extensions`; `tcli browser status` says so when the connected version is older than the folder's (`extension_version` in the status).

## Recording

A recording (`record.start`, or `tabs.open` with `record`) attaches the debugger to the tab and injects the page recorder (`installRecorder` in `extensions/chrome/page.js`). Items go out in `record.items` batches (at most 200 per batch, every second and at the stop), redacted by the extension (`redact.js`) and again by the server (`services/browser-recordings.js`), one JSON line each. Kinds: `request`, `response`, `ws`, `console` (from the debugger), `click`, `input`, `change`, `submit`, `key`, `hover`, `scroll` (actions), `nav` (address changes, from `chrome.tabs.onUpdated`) and `dom`.

- **Recording from the first load** (extension 1.0.4; `tcli browser open <url> --record [record options]`). `tabs.open { url, active, record: { network, dom, bodies, types, drop_other_types, max_body_bytes } }` creates the tab on `about:blank` (an HTTP page cannot be scripted before it exists, but the debugger can attach to about:blank), joins it to the T-Agent group, attaches the debugger and starts the recording there, writes a `nav` item `{ source: 'agent', action: 'open', from: 'about:blank', to: url }`, and only then navigates. So the first document request and everything after it are recorded once, with no reload. It answers when the tab has committed the page: `{ tab, recording_id, options }` (the bridge registers the recording with the task and terminal, as for `record.start`). A late `about:blank` from `onUpdated` does not end the recording (`openingUntil`). The page recorder goes in when the debugger reports that the main frame committed a document (`Page.frameNavigated`, with `injectImmediately`) and again at DOMContentLoaded and at load; it runs once per document and recording (a second call does nothing). On a fast page the HTML is parsed before the recorder gets in, so the recorder's first `dom` item also lists what the document already shows, marked `initial: true`.
- **A recording follows the windows the page opens** (extension 1.0.6, `features` `record.tabs`). A tab whose opener is a recorded tab joins the same recording: a popup window (`window.open`, an OAuth or payment popup), a `target="_blank"` link, a page that opens a new tab, and the popups of those (at most 10 tabs per recording, the first included; past that one `tab` item `{ recorded: false, reason }` notes it, once). Chrome reports them by `chrome.tabs.onCreated` with `openerTabId` (tabs in the opener's window) and by `chrome.webNavigation.onCreatedNavigationTarget` (`sourceTabId`; the only report of a popup window, whose tab Chrome gives no opener tab); the same tab joins once. A joined tab is owned at once (`joined` in `storage.session`, tab id → opener; `allowed()` lets T-Agent's commands use it, `how: 'group'`, although a popup window has no group), stays where Chrome put it (never moved or grouped), gets the debugger and the page recorder with the recording's options, and its own activation (Chrome focuses a popup) is quiet for 3 s. Every item of a recording now has `tab` (the same as `tab_id`), and the first item of a joined tab is `{ kind: 'tab', action: 'opened', tab, opener, url }`; `{ kind: 'tab', action: 'closed', tab, opener }` when it closes. A joined tab that closes, goes to a page that cannot be recorded or loses the debugger only leaves the recording; the recording ends with the tab it started in, and `record.stop` (by id, or on any of its tabs) stops it and detaches from all of them. The extension sends `tab.opened { tab_id, opener_tab_id, recording_id, url }`: the tab care gives the tab its opener's terminal and turn state ("Closing T-Agent's tabs"), so it closes by the same rules, and one the person used (click, typing) is kept like the recorded tab. Redaction is the same. The first load of a popup usually starts before the debugger can attach, and no CDP command on the opener reaches a new window (`Target.setAutoAttach` on a tab reports its frames and workers, not its popups; tried in real Chromium). So until the debugger is attached, `chrome.webRequest` records the joined tab's requests: `request` and `response` items with `req_id` `wr-<id>`, `via: 'webRequest'`, `body_omitted: 'early'` (no bodies, no request headers), types mapped to the CDP names (`xmlhttprequest` → `Fetch`). Its events for a tab that no recording knows yet wait 3 s (they can come before `onCreated`); the listeners exist only while a recording runs, so the worker is not woken by the browser's requests. A request near the moment the debugger attaches may show twice (once with `via: 'webRequest'`). Version 1.0.6 adds the `webNavigation` and `webRequest` permissions (granted at the self reload of an unpacked extension). `tcli browser record items --tab T` and `record requests --tab T` keep one tab; `record show` lists the tabs, and the request lines get a tab column when they come from several tabs ("Reading recordings" in docs/design/tcli.md).
- **Type and size filters** (1.0.4; `record start` and `open --record`: `--types T` (`types`, CDP resource types in any case: Document, Stylesheet, Image, Media, Font, Script, TextTrack, XHR, Fetch, Prefetch, EventSource, WebSocket, Manifest, SignedExchange, Ping, CSPViolationReport, Preflight, Other; `--type` is the same), `--drop-other-types` (`drop_other_types`, needs `types`), `--max-body N` (`max_body_bytes`, 0 to 2 MiB). Defaults are as before: every type, bodies up to 2 MiB. With `types`, a request of another type keeps its `request` and `response` items but without bodies (no `post_data`, `body`, `body_base64`, frame data; `body_omitted: 'type'`), so the timeline stays whole; with `drop_other_types` it has no items at all. When the recording attached the debugger itself, the bodies of other types are not even fetched (`body_types` in the capture options of `capture.js`); a capture `net start` runs keeps its own rules and the filters apply to the recording's items only (`shapeNetwork` in `background.js`). A body over `max_body_bytes` is cut: `body_truncated: true` (or `post_data_truncated`, or `truncated` on a frame), and `response.body_bytes` / `request.post_data_bytes` hold the size before any cut (also in `net get`). `record.start` answers `{ recording_id, tab_id, url, options }`; the options are kept in the recording's summary (`options`, `record show` prints them as `filters`).
- **Sources.** An action of a tcli command is one item with `source: 'agent'` and `command` (`input.click` → `click` with `button`, `count`; `input.type` → `input` with `value` (the typed text; `<redacted:N>` when the target is a password or a secret-named field), `clear`, `submit`; `input.press` → `key` (a printable key without Control or Meta is `<redacted:1>`); `input.select` → `change` with `values`; `input.hover` → `hover`; `input.scroll` → `scroll` with `dx`, `dy`; `modifiers` when given), with the resolved `target`, written before the input is sent so the requests it causes come after it. The address changes during a tcli `go`, `back` or `forward` (and its redirects) are `nav` items with `source: 'agent'` and `action`; a reload, or a `go` that leaves the address as it was, is one such item of its own. The person's actions are recorded by the page recorder with `source: 'user'` (`synthetic: true` when the page's own script made the event); other address changes (a followed link, a redirect, the person typing an address) have no source, nor do network, console and DOM items. No double items: the recorder leaves out the events of a command, which the page script marks while it dispatches them (`__tagentAgentBusy`) and the worker marks around debugger input (`agentWindow`: `__tagentAgentUntil`, 10 s before, 150 ms after); the Enter of `type --submit` is part of the `input` item.
- **Targets.** `click`, `input`, `change` and `submit` items (and agent items) keep `target { tag, role, name, text, selector, rect }` and add `type` (inputs), `sensitive: true` (a password or secret-named field) and `nearest`: the nearest meaningful element going up from the target, itself included, at most 10 levels and never `<body>`: the first that is interactive (a link, a button, a form field, an ARIA widget role, `tabindex`, `onclick`) or labelled (`aria-label`, `aria-labelledby`, `title`, `alt`, an SVG `<title>`); when the walk has left a run of `cursor: pointer` elements that started at the target, the top of that run; else the first element with a visible text of at most 80 characters. `nearest { tag, depth, role?, aria_label?, title?, alt?, name (the accessible name, about 80 characters), text (visible text, trimmed, at most 80), selector }`; the selector prefers `#id`, then a unique `data-testid` / `data-test` / `data-qa` / `data-cy` / `aria-label` / `name` / `title`, then an `nth-of-type` path.
- **DOM change items** (every 500 ms when something changed): `summary { added, removed, attrs }` as before, and `appeared`: what showed up, in this order of kinds: `dialog` (`dialog`, `role=dialog|alertdialog`, also one that opened by an attribute change), `alert` (`role=alert|status`, `aria-live` regions, `output`; also text put into one), `notice` (a class containing toast, snackbar, notification, notice, message, alert, error or modal), `heading`, `button`, `link`, each `{ type, tag, role?, text }` with the visible text (or aria-label) collapsed to at most 120 characters, only visible elements, each text once per item and not again while the element shows the same text. At most 20 candidates of a kind and 3000 checked nodes per item, at most 20 entries (`appeared_more` counts the rest). The texts are redacted like every other item (a JWT or a bearer token in page text becomes `<redacted:N>`; the vectors are the `items` section of `test/fixtures/browser-redact-vectors.json`). The old `landmarks` field (always empty in practice) is gone.
- **Older extensions.** The hello lists `features` besides `methods` (1.0.4: `open.record`, `record.types`, `record.max_body`, `record.agent_actions`, `record.dom_text`). The bridge refuses an option an extension would silently ignore: `PARAM_FEATURES` in `services/browser-bridge.js` (`tabs.open` `record`; `record.start` `types`, `drop_other_types`, `max_body_bytes`) answers `UNKNOWN_METHOD` "The extension is older than this command (version 1.0.3 does not support record start --types): reload it in chrome://extensions" and nothing reaches the browser.
