# Failover and one login

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

When the engine of the page is down, the page still opens, says which engine is down and offers the other linked engines; a login on one linked engine opens the others without the code; the Mac app moves to a linked engine by itself; the other engine keeps listing the offline engine's tasks, dimmed. The rule behind it: "One experience on every device and engine" in `AGENTS.md`. Mockup: Failover.

## One login for linked engines

Code: `services/sign-in-handover.js`, `routes/sign-in-handover.js`, the `/handover` route in `routes/auth.js`, `public/js/auth.js` (the login page), `scripts/h5-shell/sign-in-handover.mjs` and `SignInHandover.jsx` (the page). Tests: `test/sign-in-handover.test.js` (every refusal), `test/sign-in-handover-e2e.test.js` (two engines in one process over real HTTP, a cookie jar per origin), `test/h5-sign-in-handover.test.js`, `scripts/test-login-handover-browser.cjs`, `scripts/test-h5-sign-in-browser.cjs`.

- **Only between engines joined by a service link**, never a plain remote Engine: the key comes from the link's two tokens, and both sides look the link up among their live links.
- **Made on A only by a POST of a logged-in page** (`POST /api/sign-in-handover { target: <B's instance id>, nonce_hash }`, behind the `/api` gates: the session and the same-origin check of every state-changing route). No GET makes one; a cross-site page cannot (403), nor a logged-out browser (the login gate's 404). Before signing, A asks B over the link (`GET /v1/sign-in-handover`, link tokens only: B's switch and B's web addresses) and checks that B's `/v1/info` lists `sign-in:handover`.
- **The token** is `base64url(payload).base64url(HMAC-SHA256)`, payload `{ v: 1, iss: A, aud: B, lnk: <link id>, jti, iat, exp (iat + 60 s), lvl, nh }`. The key: HKDF-SHA256 over the two link tokens' SHA-256 hashes (sorted), label `t-agent sign-in hand-over v1`, info `link|<link id>`. Each side holds one token and the other's hash, so only the two ends of the link can make it; reading one side's database without its session secret is not enough (the other token is stored encrypted).
- **Bound to the browser that asked**: the page makes a random 32-byte nonce and sends only its SHA-256 (`nh`). The nonce travels with the token in the URL fragment of the navigation to B (`<B's address><page path>#handover=<token>&n=<nonce>`): a fragment reaches no server, no access log and no Referer. Someone who reads A's answer (A over plain HTTP) still lacks the nonce. Where `crypto.subtle` is missing (a page on a LAN address over HTTP is no secure context) the page uses its own SHA-256 (checked against Node's).
- **Redeemed on B's login page**: a logged-out visit of B's `/` or `/h5` leads to B's login entrance (the fragment survives the redirect), `public/js/auth.js` takes the fragment off the address at once, and, only when this browser is not signed in on B already, posts `{ token, nonce, return_to }` to `<login path>/handover` (the login's own same-origin rule). B refuses (logged with the code, never the token or nonce): a malformed or tampered token or a wrong nonce (`HANDOVER_INVALID`), a link that is revoked, removed or whose issued token was revoked (`HANDOVER_LINK_REVOKED`), another target (`HANDOVER_WRONG_TARGET`), expiry (`HANDOVER_EXPIRED`, 30 s of clock difference allowed for `iat`), a second use (`HANDOVER_USED`: the ids are stored in `sign_in_handover_used_v1` until they expire, in one transaction, so a restart or two parallel requests cannot use one twice), the switch off (`HANDOVER_OFF`), B not in authenticator mode or without an authenticator (`HANDOVER_NOT_AVAILABLE`), and A's login not made with a code (`HANDOVER_CODE_REQUIRED`). 20 refusals from one address in 15 minutes give `AUTH_RATE_LIMITED`. Then B sets its own normal session cookie (the same `saveLogin` as a code login: HttpOnly, SameSite Strict, Secure when it must be).
- **B's stricter rule still asks**: a hand-over stands only for a login that used an authenticator code. A local-only login of A (access mode "local", no code) is never handed over, and A refuses to make one; a B in local mode accepts none (it is reachable only from its own machine, where it needs no login). A session that came from a hand-over is not a recent verification: replacing B's authenticator asks for B's own code (`authenticatedAt` 0). A session made from a hand-over may hand over again to B's own linked engines (each of them asked for a code too).
- **The switch**: Settings → Devices, "Accept sign-in from linked devices" (`#h5-sec-sign-in`), device scope, on by default (`system_state` `sign_in_handover_v1` `{ accept: false }` only when off), for this device and, in a linked device's tab, for that device through `/api/device-settings/<id>/sign-in-handover/settings`. A company computer accepts from and hands over to its linked engines like any other machine: the hand-over moves no personal data, only a login of the same person.
- **"Sign in on K01 too"**: a text button on the row of each linked device that lists the capability and accepts (one that does not says "K01 does not accept sign-in from linked devices"). The click opens a tab at once (a later window would be blocked), tries K01's remembered addresses without credentials, asks for the token and sends the tab to K01; the row says "Signed in on K01 in a new tab" or why not. Never done without the click: no hidden sign-in in the background. The point is to have K01's cookie (30 days) before T01 goes down, because a stopped T01 cannot hand anything over.
- **Not done**: no single session shared between engines (each engine keeps its own cookie and expiry; logging out on one does not log out the others), no hand-over from an engine that is down, no hand-over to a plain remote Engine, no CORS opening of any route. The Home Screen app on an iPhone keeps its own cookies apart from Safari, and a navigation to another origin opens there in Safari's in-app sheet; whether a login made there lasts depends on iOS (not verified on a device).

## The page while its engine is down

Code: `public/sw.js`, `lib/service-worker.js`, `public/offline.html`, `public/js/offline.js`, `public/css/offline.css`, the start of `public/js/h5.js`. Tests: `scripts/test-offline-view-browser.cjs` (two real HTTP servers, the real worker), `test/offline-view.test.js`.

- **The service worker** handles only visits of exactly `/` and `/h5`: they go to the network as before and the answer passes as it is (the page, the login redirect, an error page). When nothing answers, or a proxy answers 502, 503 or 504, the visit gets `/offline.html` from the worker's cache. The cache holds only the offline page and the files it loads by their plain URLs (`offline.css`, `offline.js`, `local-keys.js`, `i18n.js`, `i18n-zh-ui.js`, `favicon.svg`); those go to the network first too. No API answer and no page of the engine is ever cached or shown from it, so nothing stale passes for live data. The full MUI shell is not booted from a cache: its first screen needs the engine's answers, and the offline page needs nothing from it (like the login page, plain HTML styled with the theme's values). `server.js` sends `/sw.js` with the hash of the offline files written in (`lib/service-worker.js`), so a change of any of them installs a new worker and cache. `/sw.js` stays behind the login gate.
- **The view** (mockup): "T01 can't be reached", "Your tasks on K01 are still running. Continue there; this page comes back by itself when T01 answers.", a contained "Continue on K01" per linked engine whose remembered address answers a request without credentials (`/health`, no-cors: only "it answered" is learnt; an HTTPS page cannot try an HTTP address), and "Try again". With none answering: "No other device answers either. …". The page asks its own engine's `/health` every 5 s while visible and on "Try again", and loads again once it answers. "Continue on" opens that engine at the same page path; there the browser is signed in when it has that engine's cookie, else that engine asks for its code.
- **What it remembers**: `ta-linked-engines` (`public/js/local-keys.js`, cache of shared state): this engine's name and the linked engines' addresses, written by `h5.js` 4 s after the start (top page only) from `GET /api/sign-in-handover/peers`; an engine the answer has no address for keeps the ones known before. The server keeps them too (`linked_web_addresses_v1`, from each online peer's `GET /v1/sign-in-handover`: its LAN and remote addresses of app.json, never loopback; the joiner adds the initiator address it joined at).

## Tasks of an offline engine

- `GET /api/remote-servers/:id/tasks` of a linked engine keeps the list that passed in short (`services/linked-last-tasks.js`, `system_state` `linked_last_tasks_v1`: id, name, group and order of each task, at most 500, written only on a change). When the engine does not answer, the 502 carries it as `last_known { at, tasks }`.
- The page (`h5.js` `loadSource`) uses it for a linked engine that has not answered in this page load. Every row of an offline engine is dimmed (disabled text colour) and says "offline" under its name; the rows known only from `last_known` cannot be opened (no actions, no session list, the tag does nothing). Above the list: "T01 is offline. Its tasks are shown as they were and open again when it is back." (`.h5-offline-note`, one per offline engine with rows). When the engine answers (the 30 s offline poll or a reload) the rows are its live ones again.
- Shown: the task names, their places in the shared order and the device tag. Not shown: sessions, documents, files, activity, archived tasks, anything new since the last read. Tests: `scripts/test-h5-offline-rows-browser.cjs`, `test/linked-last-tasks.test.js`.

## The Mac app and the Home Screen app

- The Mac app reads `linked` of app.json (the server writes the remembered addresses there) and, when this Mac's server stops answering and the person did not stop it, tries them in order and shows the first that answers, with one line in the title ("On K01 while this Mac's T-Agent is not running"). When this Mac's server is back the window stays ("… is back: View → Return to This Mac"); only View → Return to This Mac goes back. See "Another engine while this one is down" in [mac-app.md](mac-app.md).
- The Home Screen app is the page itself: the worker and the offline view above.
