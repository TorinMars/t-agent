# Mind maps

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

A mind map editor inside the one page (`/` and `/h5`), independent of tasks and terminals: maps belong to nobody's task, and opening one touches no task state. Every map has one layout, a tree that grows to the right of the root; the keyboard follows XMind; no XMind name, logo, artwork or theme file is used.

**Why this shape.** One page, not a second app: the terminal stays connected underneath, and the same Back gesture, login and update flow apply. Lazy load: `public/js/mindmap.js` (2.6 KB) is the only part that loads with the page, so a visit that never opens a map pays almost nothing; the editor is the bundle `public/js/mindmap-ui.js`, fetched when the view is first opened (`npm run build:mindmap`, the same way as the chat). Its styles are inside the bundle as text, so no stylesheet is added to the first paint. Independent: the view has its own API (`/api/mindmaps`), its own element (`#h5-mindmap`) and no reference to tasks.

**One list, from this engine's copy.** Maps are the person's own documents: every normal linked engine keeps a copy of every map ("Mind maps on every engine" below), so the list is this engine's own copy and works when another engine is offline. The view still gets `sources` from `h5.js` (for each service of `listedSources()`, the task list's services in its order, a device turned off in "Show in task list" left out: `{ key, label, base, online, instanceId }`, `base` being `/api/mindmaps` or `/api/remote-servers/:id/mindmaps`); until the services and the hidden devices are known it passes none and the view says "Loading...". `publishSources` calls `syncMindmapSources`, which gives the open view a new list (`setSources`) only when it really changed. Which of them the view reads (`listedSources` in `app.js`) follows the `sync` field of this engine's list answer: at first this engine alone; with the sync on (`sync.enabled`) this engine and only the linked engines too old to keep a copy (`sync.older`, their instance ids: their maps are read from them as before, with their own tag); without the field (the sync is off with `MINDMAP_SYNC_ENABLED=false`, or an older server) every service, the way it was before copies. In the view:
- One list, the last edited first, no group per service ("Mind maps in one list" in [entry-symmetry.md](entry-symmetry.md)). A row of this engine's copy carries the engine it was **edited on** last (`by` / `by_name` of the summary): the task list's tag (the name cut to 8 characters, the colour of that engine's instance id), with the title and label "Edited on <name>"; shown when more than one engine keeps the maps (`sync.engines`) or another service is listed, so one engine alone looks as it always did, and every engine's page shows the same tags (this engine is named like the others). A row of an older engine has that engine's tag (where it lives). A service read itself that cannot list its maps now has one line under the list (its name, and "Loading...", "Offline" or the error with Try again). Each service is read on its own (`loadSource`): a slow or offline one neither delays nor blanks the others, a late answer of an older read is ignored, and a list already shown stays while it is read again. A 502 (`REMOTE_OFFLINE`, `REMOTE_CONNECTION_FAILED`) marks it offline; a 501 `MINDMAPS_UNSUPPORTED` is left out. Rows are keyed by service and id (`data-ref="<source key>|<id>"`); a redraw keeps the focus on the same button of the same row.
- Every request of an open map goes to the service it came from (`state.src`): autosave, the check after a 409, Reload, Save as a new copy and the draft. With the sync that is always this engine. When the page hears that an older engine's service is back, a waiting save is sent at once (`saver.wake()`); opening a map on one that does not answer says "This service is offline: <name>".
- **No "Create on" for maps.** With the sync a new or imported map is made on this engine and is on every engine a moment later, so the choice is gone (`createTargets` is this engine only). Without the sync the old rule stays: "Create on" (the shared `h5-create-on`, the first machine by name otherwise) when more than one service can take a map. Exports are local downloads, unchanged.
- **A map that changed elsewhere.** While the view is shown the page asks this engine every 10 s (and when the page becomes visible again) for the open map's `GET /api/mindmaps/:id/head` (`{ revision, updated_at, by, by_name }`, no content), and reads the list again every third time while the list is shown. A larger revision with no unsaved edits here (the saver clean, no topic or title being edited, no dialog) reloads the map and says "Updated to the version saved on <engine>". With unsaved edits it shows a banner under the header, "A newer version was saved on <engine>." with the text button "Reload the newer version" (`#mm-newer`; it throws the edits here away); keeping on typing ends in the usual 409 dialog, which offers to save them as a new copy. A save of ours on its way is waited for first, so our own save is never offered back. A map deleted elsewhere closes with "This map no longer exists" when nothing here is unsaved.
- **A company computer whose home is away** lists its cache with a banner above it: "<home> can't be reached. These are the maps opened on this computer lately; changes are kept here and move to <home> when it is back." plus "<n> changes wait." (`sync.cache_only`, `home_online`, `waiting`). Opening a map it does not have says "This map is kept on <home>, which can't be reached right now" (503 `MINDMAP_HOME_OFFLINE`).

**Mind maps on every engine** (`services/mindmap.js` the files, `services/mindmap-merge.js` the rules, pure, `services/mindmap-sync.js` the transport, `routes/mindmap-sync.js`; the pattern of the Learn sync, "Sync across linked devices" in [learn-english.md](learn-english.md)). Every normal machine joined by service links, a chain included, keeps its own full copy; there is no home between normal machines. Plain remote Engines never take part.
- **Identity.** A map keeps its id (a random UUID made by the engine that created it) on every engine, so the ids of existing maps are already the shared ids and nothing needs mapping on the server; same-named maps from two engines are two ids, so two maps. There are no public share links of maps and no `?map=` address (checked 2026-11-20); the only references the page keeps are the drafts, keyed `h5-mindmap-draft:<id>` for this engine and `h5-mindmap-draft:<source key>|<id>` for a map opened on another service before copies: with the sync a map of this engine's copy also takes a draft kept under any listed service's key with its id (`draftKeys`), and clearing clears them all.
- **Storage.** Still one file per map in `<data folder>/mindmaps/`, plus `sync`: `{ vv, at, by, by_name, seq, conflict_of? }` in each file, `mindmaps/sync/state.json` (`{ seq, clock, names }`: the change counter, the hybrid clock and the engine names seen) and `mindmaps/sync/tombstones/<id>.json`. No database table and no schema change. `vv` is a version vector (`{ <instance id>: n }`, one more for this engine at each save here), so "descends from" never forgets, however long an engine was offline; `at` is the time on the folder's hybrid clock (`max(now, newest seen + 1)` ms), `by` / `by_name` the engine that made the change. `revision` (what the page saves with) stays a number per engine that goes up with each change of the title or content here; a version that descends from what is here takes the sender's revision when larger, so a company computer's offline saves keep their numbers on its home.
- **Merge** (`decide`). A version that descends from the one here replaces it; the same or an older one changes nothing. Two versions saved apart from the same base (concurrent vectors): the later `at` (a tie to the greater instance id) is the map, with the joined vector; the other is kept next to it as "<name> (conflict from <engine>)" (cut to 200 characters keeping the suffix), with an id made from a hash of the map's id and the losing vector, so every engine that sees the conflict makes the same copy, stored once. Both ending at the same content keep one map and no copy. A delete is a tombstone with a vector one past the map's: it removes the map where it has seen that version, and an edit the deleting engine never saw keeps the map and brings it back there (data is never lost to a delete made apart). Tombstones are kept 30 days (`TOMB_DAYS`) and then purged (at start and every round); an engine away longer can bring a deleted map back. A peer's entry is checked like a page's save (id, title, 8 MB, times, vector) or dropped. The map limit (2000) holds for creates here, not for maps arriving from peers.
- **Change numbers and pages.** Every entry written in the folder, here or from a peer, gets the next `seq` (except on a company computer, below). Each machine keeps per link how far it has the peer's numbers (`have` in `system_state` `mindmap_sync_peers_v1`; a peer whose newest number is lower, a restored folder, is read again from 0). A round pulls the peer's entries after its `have` and pushes its own after the peer's, a page at a time; a page is cut by bytes, 2 MB of map JSON (`PAGE_BYTES`; asked between 64 KB and 16 MB), always at least one map, so an 8 MB map goes alone. A receiver applies only what changes something and gives it new numbers, so a chain reaches every engine and an echo stops after one page.
- **When.** A create, save, rename or delete here pushes 3 s after the last change (at most 15 s after the first, so a long typing session still travels); also when a link comes online, at start and every 5 minutes; a round that failed (a link reset while it comes up) is tried again once 15 s later. Failures are logged once per link and reason by code (`[mindmap-sync] sync with <name> failed: <code>`).
- **Transport.** `GET /v1/info` must list `mindmaps:sync` (an older peer is marked `supported: false`, skipped, and named in `sync.older` for the page). Link tokens only (403 `LINKED_ONLY`). `GET /v1/mindmap-sync` → `{ instance_id, public_key, company, max_seq, have }`; `POST /v1/mindmap-sync/pull { instance_id, public_key, after, max_bytes }` → `{ instance_id, sealed }` (a page `{ maps, tombstones, after, next, more }`), with `ids` instead the current entries of those ids, with `list: true` every map's summary; `PUT /v1/mindmap-sync { instance_id, public_key, sealed }` → `{ applied, have }`. Pages travel only inside AES-256-GCM envelopes (the settings sync's format with room for a large map) with a key derived by HKDF from the link's settings-sync key (info `t-agent mindmap-sync v1`) and the additional data `t-agent mindmap-sync v1|<push|pull>|<sender>|<link id>`. `SETTINGS_SYNC_ENABLED=false` or `MINDMAP_SYNC_ENABLED=false` turns it off on one service (no capability, no rounds, 404 on the route, the page lists every service as before). `/v1/mindmaps` stays for older engines that read this one's maps.
- **Company computer** ("Company computer" in [linked-device-settings.md](linked-device-settings.md)). Mind maps are personal data. A company computer with a normal machine linked works through its home (the online normal machine with the oldest link, as for Learn; the last one in `mindmap_home_v1`): it never pulls the whole set; its own creates, saves and deletes get change numbers and are pushed 0.2 s later; the list (`GET /api/mindmaps`) first pushes, then reads the home's summaries (`list: true`) with its own waiting changes on top, and drops from its cache what the home no longer has; opening, the head, a save and a delete of a map first bring that map up to date from the home (`ids`, at most 4 s each step) and then work on the copy here, which takes the home's revision when nothing waits here, so the page sees the same numbers either way. What it reads from the home gets no change number (it is never passed on). After the home has its changes, maps not opened or edited here for 14 days and the handed-over tombstones leave the folder (no tombstone: the home keeps them). While the home is away it lists, opens and edits its cache, queues new maps and saves, and says so (above); a map it never opened is 503. Normal machines never sync with it (their round stops after its `/v1/info`; its sync routes answer 409 `MINDMAP_COMPANY_COMPUTER`). With no normal machine linked it keeps its maps as a normal machine would.
- **Migration.** The first time a folder is read, a map file without `sync` gets `{ vv: { <this engine>: 1 }, at: its updated_at, by: this engine }` and a change number; the first round with each peer then sends them, so the maps of every engine become one set (ids differ, so nothing is merged by name). A map put back from `trash/` by hand next to its tombstone counts as a change here and travels again.
- **Known limits.** Two engines' clocks far apart make the one ahead win conflicts more often. A conflict copy's title is in English (it is stored content, made on the server). The page learns of a newer version within 10 s, not at once. A company computer's list needs the home for maps it has not opened; offline it shows its cache only.

**Editor library: `mind-elixir` 6.0.0 (MIT).** Measured with esbuild (minified / gzip) in a spike that really built both candidates: `mind-elixir` 102 KB + 20 KB CSS / 33 + 5 KB; `simple-mind-map` 521 KB / 152 KB. In real Chromium `simple-mind-map` closed the text editor on Enter during composition, threw a page error in one of the two layouts tried, and registers its touch handling on `window` (it would also read touches meant for the terminal). Its transitive dependencies are acceptable (MIT / BSD), and it has a .xmind parser, but the size and the composition bug decided against it. `mind-elixir` has no .xmind support, so the small converter is ours (`scripts/mindmap/xmind.mjs`) on `fflate` 0.8.3 (MIT, 12.7 KB minified for what is used, against 97 KB for `jszip`, and it unpacks into a buffer of the declared size, see below). The whole bundle is 197 KB minified, 67 KB gzip. Both are dev dependencies at exact versions.

**The page.** `#h5-mindmap` is a fixed full-window element above everything but the Material UI modals (`z-index: 1250`); on a wide screen it also covers the sidebar, so a map has the whole window and no second navigation exists at the same time (`--h5-terminal-left` is not needed). The entry is a button beside Settings at the bottom of the task sheet; on a phone it closes the sheet first. While the multi-column view is shown, every entry opens its Mind maps tab instead (below), also the button of a column's own task sheet (the pane posts `mindmaps`); a column never shows a map (the mind map columns of 2.133 / 2.134 were removed, see "Multi-column view" in [page-shell-and-columns.md](page-shell-and-columns.md)). Height: `fitMindmapView` in `h5.js` follows the rule of `fitViewport` (`visualViewport.height` is believed only while something that raises a keyboard is focused, which is why `[contenteditable="plaintext-only"]`, the topic editor, was added to `EDITABLE`). While the view is open: `h5.js` sends no key to the terminal and Cmd/Ctrl+K does nothing (an explicit `mindmap` check in both handlers); keys reach the view first because its listener is on `document` in the capture phase, and any key that still lands in the terminal's textarea is taken back; the Back gesture walks view, editor, dialog (`mindmapLayers` in the store, `extra()` in `entry.jsx`); the silent reload waits (`pageBusy` in `Update.jsx`). Text the person wrote is `translate="no"`, so the interface translator never rewrites it.

**Mind maps tab.** In the multi-column view the navigation rail's "Mind maps" tab is a whole mind map page right of the rail: the same view, mounted by h5.js in the tab's element (`#h5-columns-maps`, `MindMap.mount(host, { embedded: true, active })`; `split` in `app.js`) instead of `#h5-mindmap`. The element is placed by the tab (`position: absolute; inset: 0`, `role="region"`, no modal). Layout (`.mm-split`): the list on the left (`#mm-list`, 280px, the 1dp surface): "Mind maps", Import and New map; a search field (`#mm-search`, "Search mind maps": the maps whose title contains the text, any case, on every service; Escape clears it; "No maps match" when a service has none); "Create on" when it applies; the maps of every service in one list, as in the full-window list (name, last edited, size; Rename and Delete show on hover or focus with a mouse, always on touch). The open map fills the rest; its row is marked (`data-current` on the row, `aria-current` on its button, the primary tint and a 3px primary edge) and its title follows the editor's. With no map open the editor area says "Open a mind map from the list, or create one." and its header keeps only the fold button. There is no Close and no Back to the list (the rail is the way out); the editor's header has, after the title and the save state, "Hide the map list" / "Show the map list" (`#mm-list-toggle`, `outdent` / `indent` like the page's sidebar fold, `aria-expanded`, `aria-controls="mm-list"`), Export and More. The folded list is the same on every device and engine (`h5-mindmap-list-folded` = `1` in the shared page state, [shared-page-state.md](shared-page-state.md)). Opening another map from the list first leaves the open one (its edits saved, the usual short wait), then opens the new one; New map and Import do the same. The open map's own row renames through the editor (the title is saved with the map, so no second revision races the autosave), and deleting it closes the editor first, without a last save. Escape in the editor (no topic edited, no dialog) moves the keyboard to the open map's row instead of leaving the map; Escape in the list does nothing. Keys: the editor's and the view's listeners are on the document, as in the full window, but in the tab they act only while the tab is shown (`setActive`) and only on events whose target is inside the view or the page's body (`owns`), so the rail's arrow keys, a column header's keys and anything typed while the Columns tab is shown never reach the map; the same holds for copy, cut and paste and for an open dialog's keys. Hidden, a topic being edited is committed and the map saved at once; the open map, the list and the search stay. Saving, drafts, conflicts, the keyboard shortcuts and touch are the full-window view's. The view mounts without taking the focus (it stays on the rail); opening a map focuses its canvas. The page's silent reload waits while the tab is shown (`pageBusy` in `Update.jsx`).

**Editing.** `mind-elixir` draws the map; `scripts/mindmap/editor.js` adds the shortcuts and actions, `touch.js` the finger gestures, `app.js` the list, the bars, the dialogs and saving. Touch never reaches the library: it would start a topic drag only after a long press, and a drag on a topic must move it. A tap selects, a tap on the selected topic or a double tap edits, a drag on a topic moves it (onto a topic = child, near its top or bottom edge = sibling), one finger on empty canvas pans, two fingers pinch. The editor is opened inside the `click` that follows the tap (a Promise or a timer would lose the user gesture and iOS would not raise the keyboard). The library's insert and delete calls run synchronously, inside the gesture, because no `before` hook is registered.

**One layout.** Every map is drawn with the library's right-only direction (`RIGHT_ONLY` in `doc.mjs`), whatever the source says: new maps, stored maps with both sides, left-only or an invalid direction, and any `.xmind` structure class. There is no layout setting and no key for one (the library's Ctrl+arrow layout keys are in the handler `editor.js` removes). The library also records a side per first-level topic: `direction` on the topic, and it writes one on new and moved first-level topics. `sanitizeDoc` drops it from every topic on the way in (the server's data, drafts, clipboard, `.xmind`) and `plainDoc` drops it on the way out, so nothing stale can be drawn or stored; the tree order of the children stays, so old left-side topics take their place among the others. An existing map changes on disk only at its next edit: opening it sends no save and raises no revision. No path can make a left branch: every add, paste and drag goes through the library's insert, which uses the document's direction, and undo and redo restore documents that were sanitized. A mouse drag cannot drop on the root (a library rule), a finger drag can, and both end up on the right. Fit shows the whole map and centres what is drawn (the library's centring is right for one side too, and a map much taller than the canvas just becomes small). Actual size is ours: the root is at the left end, so a map wider than the canvas starts at the left edge rather than centred, which would leave the root off the screen.

**Saving.** Autosave (`saver.mjs`): debounced 1 s, one request at a time, with the latest revision, flushed on leaving the map, `visibilitychange` to hidden and `pagehide` (with `keepalive` when the body fits in the 64 KB browsers allow). A failed request retries with a delay growing to 15 s, for as long as the map is open, so an update restart costs nothing; a retry already waiting is not pushed back by more typing. A copy of unsaved edits is kept in `localStorage` (up to 1.5 MB) so a page that dies loses nothing; opening the map restores it, or, if the map moved on meanwhile, offers it as a new copy. Drafts are per service and map (with the sync, see "Identity" above): `h5-mindmap-draft:<id>` for this machine (the key it always had, so a draft from before sharing still comes back) and `h5-mindmap-draft:<source key>|<id>` for a connected service; the draft itself also holds `source` and `id`, and it is used only when they match the map being opened (a draft without `source` belongs to this machine). So a draft of a map on service B is never applied to a map of this machine, even one with the same id and title. Nothing of the maps is kept in `sessionStorage`. A 409 `MINDMAP_CONFLICT` is first checked against the stored map: if the service already holds exactly what was sent (a save whose answer was lost, typically in a restart), it counts as saved. A real conflict stops saving and offers reload or save as a new copy; nothing is overwritten. 400 and 413 stop too and say why.

**.xmind.** `parseXmind` reads the current format (`content.json`) and the old one (`content.xml`); `buildXmind` writes `content.json`, `metadata.json` and `manifest.json`. **Not verified in the real XMind application**: the format was checked against the file layout and a local round trip only. Treated as untrusted: file size is limited (64 MB) before anything else, only those named entries are unpacked and each is limited to 16 MB by its declared size (fflate unpacks into a buffer of that size, so a false size cannot use more memory), JSON is parsed then rebuilt topic by topic with limits on count (20000) and depth (200), and notes and labels are text. `doc.mjs` `sanitizeDoc` runs on everything that reaches the editor (the service's data too): `dangerouslySetInnerHTML`, `image`, `style` and unsafe links are dropped, and the library's `markdown` option is a function that only escapes HTML, since its arrow and summary labels are drawn with `innerHTML`. Clipboard topics are sanitized the same way.

Kept on import: topics, tree structure, order, plain notes, labels, http/https/mailto links, markers (shown as a symbol when one is known, the id is always kept and re-exported), folded branches, relationships with their titles, summaries. Lost, and reported in the message after the import: other sheets than the first, images, boundaries, callouts, floating topics and links inside the workbook. Also lost, and not reported, because no content goes with them: colours and fonts, and the file's structure class (any structure, such as both sides, left, fishbone or org chart, is accepted and opens as a tree to the right; the export always writes `org.xmind.ui.logic.right`). Audio notes are lost too.
