# Links opened by programs: open where the person is

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

Programs in a T-Agent terminal run on the engine. When Claude Code, Codex or any CLI opened a web link (on its own, or after a click on a link inside its full-screen view), the browser of the engine machine opened, not the one of the device the person was using (a phone, another computer through a service link). Now a clear web link goes to the page that shows that terminal and opens there. The engine side (shims, environment) is "Links opened by programs" in [terminals.md](terminals.md); this file has the cause, the delivery, the page and the platforms.

## The cause (checked 2026-11-19)

- A small experiment with a fake `open` / `xdg-open` / `$BROWSER` first in `PATH`: Node's `child_process` running `open <url>` (what the `open` npm package does on macOS) and Python's `webbrowser` with `BROWSER` set both called the fakes. So a stand-in earlier in `PATH` catches them.
- Claude Code 2.1.328 (a Bun single-file binary, read with a byte search, never run): its browser opener runs `$BROWSER <url>` when `BROWSER` is set, else `open <url>` (the macOS build; a Linux build uses `xdg-open`), through a spawn that looks the command up in `PATH`. Links clicked inside its own screen (it tracks the mouse) are dispatched by Claude Code itself to the same opener (http/https and a list of app schemes; `file:` goes to `open -R`). It also bundles the `open` npm package (`open` on macOS, `xdg-open` elsewhere). On a Linux engine without `DISPLAY` it did not try to open at all unless `BROWSER` is set: the shim's `BROWSER` now makes it try, and the link reaches the page.
- Codex 0.170.0 (Rust, read the same way): the `webbrowser` crate 1.2.4. On macOS it opens through LaunchServices / `NSWorkspace` (`objc2-app-kit`), runs no `open` command and ignores `$BROWSER`, so **a link Codex opens on a macOS engine cannot be caught** and still opens on the engine. On Linux the crate tries `$BROWSER` first, then `xdg-open` and others, so a Linux engine catches it.
- OAuth logins (`claude` / `codex login`) send the browser to a URL whose `redirect_uri` is a server on the engine (`http://localhost:<port>/callback`); on another device that callback cannot work, so such links are left to the engine (below).

## Delivery

```
program --open/xdg-open/$BROWSER--> shim --POST /api/tcli/open-link (hook token)--> engine server
engine server --{type:'open-link', id, url, agent} on the terminal socket--> page showing the terminal
page --{type:'open-link-result', id, shown}--> engine server --{delivered}--> shim (exit 0, or run the real open)
```

- Relay (`routes/open-link.js`, mounted with the other tcli relays before the gates): the terminal's hook token in `X-T-Agent-Task` / `-Terminal` / `-Token`, only from this machine (`lib/terminal-relay-auth.js`). Body `{ url }`, 16 KB at most. 400 `INVALID_URL` unless http(s) with a host, at most 4096 characters, no white space or control characters. Not offered, answered `{ delivered: false, reason }`: `local-only` (the host is loopback: `localhost`, `*.localhost`, `127.x`, `::1`, `0.0.0.0`; a dev server only works on the engine) and `local-callback` (a query parameter named like redirect / callback / return holding a loopback URL). Rate limit: 5 links per terminal in 10 s, then 429 `TOO_MANY_LINKS`. Links are never logged.
- `offerLink` in `routes/terminal.js`: the terminal has one attached socket at a time; the link goes there as a binary control message, only to a page of the binary protocol (`proto=2`; an old page would print the JSON). The page must answer within 2 s (`LINK_OFFER_MS`). No socket, an old page, `shown: false`, no answer or a socket that closes: `{ delivered: false }`. A T01 page attached to a K01 terminal through a service link has its socket end at K01's server (`services/remote-terminal-proxy.js` passes frames through unchanged), so it is covered the same way.
- Whatever is not delivered, the shim opens on the engine with the real command: the behaviour from before (the user's decision).

## The page

- `public/js/open-link.js` (`OpenLink`, a pure module, also `require`d by the unit test): `valid`, `programName` (Claude / Codex from the terminal's agent kind, else "A program"), `environment()` (`app`, `standalone`, `platform`, `iosMajor`), `target(url, env)` and `open(url)`.
- `h5.js` "Links opened by programs": the page takes a link only when that terminal is in the foreground by the presence rule (`foregroundOf`: the terminal shown, not under the chat, the page visible and used in the last 5 minutes), the same "only the shown terminal acts" rule as the copy bar; otherwise it answers `shown: false` at once and the engine opens it. Taken in the Mac app: opened at once through its handler. Taken elsewhere: the link bar.
- The link bar (`Terminal.jsx` `OpenLinkBar`, `#h5-open-link-bar`, `state.openLink`): the copy bar's look and layout (`.h5-clipboard-*`, the `notice` blue, white text, the copy bar's slide-in, pulse and countdown line), the link icon, the title "Claude wants to open a link" / "Codex wants to open a link" / "A program wants to open a link", the URL on one line in monospace (cut with an ellipsis, whole in `title`), then Copy, Dismiss and Open (the white filled button). Open calls `OpenLink.open` inside its click (the user activation a browser needs for a new window). Copy writes the URL ("Link copied"). Dismiss, and Escape while the focus is in the bar (never from the terminal: Esc belongs to the program there), close it. It goes away by itself after 30 s (`LINK_TTL_MS`; a link is less urgent than a copy and the person may be reading), held while a mouse is over it or the focus is in it. Several links: a queue of at most 5; the bar shows the first with "+N" in its title, and Open / Copy / Dismiss move on to the next. The links of a terminal that is hidden go away with it. Touch mode: 44 px targets (theme rule). When the copy bar shows too, the link bar sits below it.

## Platforms

- **Mac app** (T-Agent.app): its web view blocks `window.open` without a click (`javaScriptCanOpenWindowsAutomatically = false`), so the page posts the URL to `window.webkit.messageHandlers.tagentOpen` and the app opens it in the default browser at once ("Links from the page" in [mac-app.md](mac-app.md)). An OSC 8 link the person clicks in the terminal goes the same way after "Open this link?".
- **Desktop browser with the T-Agent extension: not done.** The extension has no content script on T-Agent pages and no `externally_connectable`; it talks only to the server it is paired with, and the server cannot tell which paired browser (on which machine) a page belongs to, nor reach the extension of a K01 page's browser from K01. So the page cannot reliably ask the extension of its own browser to open a tab; such a browser gets the bar like any other.
- **Other browsers** (computer, normal phone tab): the bar; Open uses `window.open(url, '_blank', 'noopener,noreferrer')`.
- **iPhone / iPad Home Screen app** (`navigator.standalone` or `display-mode: standalone`): Open (and a tap on an OSC 8 link) navigates to `x-safari-https://…` / `x-safari-http://…` on iOS 17 and later and on iOS 15, which opens Safari instead of the in-app browser view that a Home Screen app otherwise uses for other origins. Research: the scheme is undocumented; it was macOS-only and is reported to work on iOS 15, 17 and 18 but not 16 ([Christian Tietze, Safari URL scheme](https://christiantietze.de/posts/2023/05/safari-for-mac-url-scheme), [Apple Developer Forums](https://developer.apple.com/forums/thread/737700)); it opens Safari, not the person's chosen default browser (no web API names the default browser); no source confirms it from a Home Screen app, and older notes say a Home Screen app could not open Safari at all and every external link opens in its in-app browser ([firt.dev, iOS 12.2](https://firt.dev/ios-12.2/)). iOS 16 and unknown versions keep `window.open` (the in-app browser). Not tried on a real iPhone.
- **Android installed app** (WebAPK, `display-mode: standalone`): Open uses `window.open('intent://<host><path>#Intent;scheme=https;S.browser_fallback_url=<the link>;end')`. With no package, Android resolves the view intent to the default browser; Chrome launches intents only inside a user gesture ([Chrome: Android Intents](https://developer.chrome.com/docs/android/intents)) and loads the fallback when it cannot launch; an intent that resolves to Chrome itself stays in Chrome ([Chromium external_intents](https://chromium.googlesource.com/chromium/src.git/+/main/components/external_intents/)). It opens in a new window, so even then the installed app is never navigated away. Google says links outside a WebAPK's scope "should be opened in the browser" ([web.dev: WebAPKs](https://web.dev/articles/webapks)), but in practice Chrome shows them in a Custom Tab over the app; the intent asks Android for the default browser instead. Not tried on a real Android phone.
- **Normal mobile browser tabs** keep `window.open`.

## Out of scope

File links in the terminal (`terminal-file-links.js`) are unchanged; links in T-Attention, the agent chat and Markdown views are not part of this.
