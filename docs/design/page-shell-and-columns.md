# The page (/ and /h5)

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

One page for computers and phones since 2.88.0: `public/h5.html` with `public/css/h5.css`, the controller `public/js/h5.js` and the React / Material UI shell. Layout by width and input mode by pointer are in part G of the architecture ([architecture-features-and-page.md](architecture-features-and-page.md)).

- `scripts/h5-shell/entry.jsx` synchronously mounts React into `#h5-root` before the existing phone scripts run, preserving the element IDs used by voice input and agent activity. Build with `npm run build:h5-shell`; the bundled `public/js/h5-shell.js` and `public/js/chunks/` are shipped with the application (see "Page bundles and chunks"). MUI, Emotion and the icon package are build-time development dependencies. The user selected the default MUI dark theme rather than a custom Material Design 3 theme.
- `store.mjs` exposes `window.H5UI` (`get`, `set`, `subscribe`, `share`, `actions`). `public/js/h5.js` owns task loading, sessions, sockets, uploads, translation and viewport handling; it updates store state instead of drawing the shell. React components own headers, lists, drawers, terminal keys, notices and dialogs. The terminal, voice input and agent chat keep their existing implementations.
- **Page store** (`scripts/test-h5-render-count-browser.cjs`, `test/h5-store.test.js`): a change is drawn only where it shows. `set(patch)` keeps the state and tells no listener when every key of the patch already has that value (Object.is); values are never changed in place. Each part subscribes to its own slice (`use-store.mjs`: `useStore(ui, selector, equal)` on `useSyncExternalStore`, `useStoreKeys(ui, keys)` for named keys with a shallow compare): the header, the terminal area, the bottom rows (T-Attention and the file sheet only as the count and flags its buttons show), the task drawer, the task list and the column strip read theirs themselves; App reads only the layout flags and which sheets are open, and hands each sheet or dialog its keys (`Part`; the settings sheet takes the whole state). `h5.js` passes the task list and `sources` through `ui.share(before, next)`, which keeps every part equal to the one before (deeply, plain data only) as the same object; task rows are `React.memo` and the drag props of `useListDrag` are one stable object, so a pushed activity change of one task draws that task's row alone, a repeated snapshot draws nothing, and typing in the task search or the draft box draws no row. Measured with 20 tasks on a computer: one activity push drew 20 rows and every part of the page before, 1 row (and the list and the bottom rows) after; a repeated snapshot 2 commits and 20 rows before, no commit after; typing four letters in the task search 100 rows before, none after. Two things that used to rely on the page being drawn again for any change now say so: the popup of a session row (TermMenu.jsx) also reads the task list and the sidebar, so it closes when its row goes away; the file sheet (Design.jsx) leaves MUI's modal stack when it closes rather than when its slide ends, so a file of the tree opened while the sheet still slides away lies on top again. The render counter (`countRender`) counts only when a test gives the page `window.__h5RenderCounts`.
- The 900px breakpoint is shared by the shell and controller: the phone's modal task drawer (min(320px, 100vw - 56px)) becomes a permanent 304px sidebar right of the navigation rail (see [page-navigation.md](page-navigation.md)). Settings open on the right; dialogs and drawers use MUI focus handling and Escape/backdrop dismissal. Drawer padding respects device safe areas. The chat remains outside the React root; the image file input is inside the Upload image button (since the fix after 2.87.8).

**Loading** (`scripts/test-h5-load-browser.cjs`). Every script of `h5.html` is deferred: `defer`, and the shell is `type="module"`, which a browser defers by itself and runs in its place in the same list, after its chunks have arrived (in this order: `i18n.js`, `toast.js`, `client-auth.js` (one combined request), the Chinese dictionaries, xterm, then the shell, the controller scripts (one combined request) and `h5.js` last), so the page is painted as soon as its two style sheets arrive (the chat's comes with the chat bundle), with an inline dark style and a static skeleton inside `#h5-root` (the header bar, and the sidebar edge on a wide screen, at the shell's sizes; the shell's first React render empties `#h5-root`). The load test compares the skeleton's header and sidebar with the shell's, so a change of the header height must change the skeleton too. At start `h5.js` asks for everything at once instead of in rounds: the Engine list, the tasks and groups of the remembered Engine (assumed until the list says it is gone, then this machine's tasks are loaded), and for the remembered task its `/terminals` and its chats (`/agent/conversations`, or `/info` on an Engine). It also opens the WebSocket of the remembered terminal at once and keeps what arrives; `open` takes that socket when the terminal shown is that one (the history it got is replayed in order), and it is closed with code 1000 when the task or the terminal is gone or another one is shown (and after 20 s unused). Early answers are used once, by the same URL, within 20 s.

## One page: routes, login and manifests

- **Routes** (`server.js`): `/` and `/h5` both call `sendClientPage` with `public/h5.html` (the file name is kept: other branches and tests name it, and a rename would only add churn). `sendClientPage` replaces the page's manifest link by address: `/h5` → `/manifest-h5.json` (start `/h5`, what iPhone Home Screen apps were added with), every other address → `/manifest.json`. `/web`, `/index.html` and `/h5.html` answer 302 to `/`, with the query kept. `PHONE_USER_AGENT` is gone: every user agent gets the same page.
- **Manifest**: `manifest.json` has no `display_override` (no `window-controls-overlay`), `background_color` / `theme_color` `#121212` (the MUI dark background).
- **Login and return**: `routes/auth.js` answers `redirect: '/'` (was `/web`) and `setup?return_to=/`; `services/client-auth.js` `safeReturnTo` keeps `/h5` and maps everything else (`/web` included) to `/`; `public/js/auth.js` returns to `/h5` only when `return_to=/h5`, else `/`; `public/js/client-auth.js` sends `return_to` `/h5` or `/`; `lib/login-gate.js` still leads `/`, `/web`, `/h5` to the login entrance. `scripts/h5-shell/Settings.jsx` uses the address the page was opened at (`pagePath()`: `/` or `/h5`) for the logout, the access-mode switch and "Replace authenticator". The "Desktop version" link in the task list is gone.
- **Login keeps the query**: `lib/login-gate.js` adds the request's query to `return_to`; `safeReturnTo` (`services/client-auth.js`) and the same rule in `public/js/auth.js` accept only a same-origin path that is one of the page addresses (`/`, `/web`, `/h5`; anything with `//`, a backslash, another origin or another path gives a bare `/`), map `/web` to `/`, keep the query (re-encoded by `URL`, at most 2000 characters, fragment dropped). So `/web?openChat=x` → login → `/?openChat=x`, and `return_to` can never lead off the site. `public/js/client-auth.js` also sends the query when a login expires while the page is open. Tests: `test/login-gate.test.js`, `test/client-auth.test.js`, `test/client-auth-http.test.js`, `test/access-mode-page.test.js`, `test/client-auth-page.test.js`.
- Logged out, the pages lead to the login entrance: a GET / HEAD of exactly `/`, `/web` or `/h5` (`PAGE_ADDRESSES` in `lib/login-gate.js`) is answered with a redirect to `<login path>?return_to=<page>` (with the page's query since 2.88.1) for every device, so a device that has never logged in no longer sees a bare, unstyled `Cannot GET /h5` page, and the login brings the person back to the page they asked for. Look-alike addresses (`/h5/`, encoded forms) and every other address stay a plain 404. The page loads `client-auth.js`, so a login that expires while the page is open sends the person to the login entrance and back to `/h5` or `/` (with the query since 2.88.1). Tests: `test/login-gate.test.js`, `test/client-auth-http.test.js`, `node scripts/test-session-redirect-browser.cjs`.
- Wrong page address: for a logged-in browser page visit (GET/HEAD asking for `text/html`) to an address nothing serves, the last handler (`createUnknownPageRedirect` in `lib/login-gate.js`, mounted after the static files) redirects to `/`. Logged-out requests are never redirected, so the hidden login entrance stays hidden and they keep getting the plain 404; `/api`, `/auth`, `/v1`, `/share`, `/hooks`, `/terminal`, `/js`, `/css`, `/vendor`, `/icons`, the login path and non-HTML requests also keep the 404. Tests: `test/login-gate.test.js` and `test/client-auth-http.test.js`.
- Service worker (`public/sw.js`, sent by `server.js` with the hash of the offline files, `lib/service-worker.js`): visits of `/` and `/h5` go to the network; only when nothing answers (or a proxy answers 502 / 503 / 504) the cached `/offline.html` says which engine is down and offers "Continue on <engine>". It caches nothing else. See "The page while its engine is down" in [failover-and-one-login.md](failover-and-one-login.md). A page opened with `#handover=…` while already signed in drops the fragment.
- Home-screen app: a browser tab cannot hide its address bar and toolbar, so `/h5` is installable as a standalone web app (`manifest-h5.json` with `start_url` `/h5`, dark colours, plus the `apple-mobile-web-app-capable` meta tags). Opened from the home-screen icon (browser share menu → Add to Home Screen) it runs without the browser bars; the layout already follows `visualViewport` and the safe-area insets. `/` uses `manifest.json`.

## Wide layout and keyboard on a computer

- Input mode (`scripts/h5-shell/entry.jsx`): `matchMedia('(hover: hover) and (pointer: fine)').matches && !matchMedia('(any-pointer: coarse)').matches` is `pointer`, else `touch`; no user agent. It follows both queries' `change` events and is kept in the store (`input`) and on `<html data-input>`. `H5UI.media.wideQuery` is the one `(min-width: 900px)` query object; `h5.js` uses it. `hasKeyboard`: set by the first trusted `keydown` (not composing, not `Unidentified`) while the visual viewport is at its tallest height for this width (no on-screen keyboard); it turns on the keyboard shortcuts below in touch mode too (iPad with a keyboard) and changes no touch bar. An iPad with a trackpad reports a coarse pointer and stays `touch`.
- Touch only (`h5.js`): `fitViewport` keyboard detection (`keyboardOpen`), `holdTerminalSize` pinning, `scheduleKeyboardReset`, `settleViewport` and the 500 ms keyboard timer. In pointer mode `keyboardOpen` is always false and `--h5-height` follows `innerHeight`, so a shorter desktop window refits the terminal (a real PTY resize) instead of being taken for the on-screen keyboard and pinning the terminal to its old height (the bug this fixes). The bottom-area press protection (`data-hold`, `setPointerCapture`) is skipped for `pointerType === 'mouse'`. Screen Wake Lock is touch only. The iOS image label and `inputmode="none"` stay.
- Pointer layout (`Terminal.jsx`): no function key row (`#h5-keys`); the mouse handle is drawn as on a phone (it scrolls and pulls out the mouse ball; "The mouse handle" in [page-terminal-mouse-ball.md](page-terminal-mouse-ball.md)), also in each column of the multi-column view (each column is the page in an iframe), and xterm shows its own scrollbar (the wheel strip of 2026-11-27, 16px beside the box with xterm's scrollbar hidden, is gone); no terminal / draft keyboard buttons; the draft box is always shown as one line and grows with its text as on the phone. Its resting line has its own room in the layout; only the growth beyond one line is `--h5-bar-extra` (`syncBar`), so focusing the box never resizes the terminal. The action row is compact 40px buttons: image, saved commands, voice, design document, next session, then send and translate-and-send at the right end. Terminal font 13px (11px on touch). Icon buttons show the browser's native tooltip from their `title` (`named` in `common.jsx` sets the same `aria-label` and `title`); the voice button's title is set by `voice-input.js`. Voice is click to start / click to stop on pointer and hold to talk on touch (`attach({ hold })` takes a function now). Cmd+C with a selection and Ctrl/Cmd+Shift+C copy (`terminal-clipboard.js`, attached in both modes; see "Program copy (OSC 52)").
- Keyboard (pointer, or `hasKeyboard`): a terminal that is shown takes the focus unless something editable has it; a click on the terminal focuses it; a `keydown` with nothing editable focused (no dialog, temporary drawer, copy view, chat or side panel focused; not a lone modifier, not Cmd, not Ctrl on non-Apple systems, not F-keys) is sent to the terminal and focuses it (from a focused button only characters, so Enter / Space / Tab / arrows keep working there); Escape in the draft box focuses the terminal and keeps the text; Cmd+K (Apple) / Ctrl+K (others, not inside the terminal where it is the shell's kill-line) focuses the session search, unfolding a folded sidebar first. Cmd+Shift+O (Apple) / Ctrl+Shift+O (others, also inside the terminal) opens the New session dialog for the task shown (see "Create dialogs"). In the multi-column view, Ctrl+Alt+Left / Right (Ctrl+Option on a Mac, also inside a column's terminal, which never receives it) moves the focus to the previous / next column and scrolls it into view, and Ctrl+Alt+Shift+Left / Right moves the focused column one place left / right (see "Multi-column view"). Draft box shortcuts are unchanged: Cmd/Ctrl+Enter = translate and send, Option/Alt+Enter = send as typed, plain Enter = new line, IME-safe. After a successful send the focus stays in the draft box (the user's rule, 2026-11-19; until then the terminal took it), so the next message can be typed at once; Escape or a click on the terminal gives the keys to the terminal. The same holds on a phone (see "Draft box" in [page-terminal-and-bottom-bar.md](page-terminal-and-bottom-bar.md)).
- Wide layout (900px and up): a header button folds the permanent sidebar away and back (`#h5-sidebar-toggle`, `outdent` / `indent` icons, `aria-expanded`; `h5-sidebar-collapsed` of the shared page state, the same on every device and engine and followed when changed elsewhere ([shared-page-state.md](shared-page-state.md)); a pane keeps its own in this browser; `html[data-sidebar-collapsed]` sets `--h5-sidebar-width: 0`). The task name in the header unfolds it too. The folded sidebar is a real layout change, so the terminal refits and a PTY resize is sent. The T-Attention panel is a side sheet that floats over the right of the page (480px, 8px from the window's edges, elevation 16, no scrim; a press outside closes it and does nothing else; "Panel" in `page-attention.md`): it changes no layout, so nothing refits. The design document, the file viewer and the file tree are modal sheets from the top, as on a phone (see "Design sheet and file viewer"): they change no layout. Not resizable.
- Width: Under 900px the page fills the window (a phone, or a narrow window or portrait tablet) and the task drawer slides over it (`--h5-drawer-width`, min(320px, 100vw - 56px)), with settings opening as a panel on the right from 600px. From 900px (a computer, a landscape tablet) the task list is a permanent 304px sidebar (`--h5-sidebar-width`) right of the 72px navigation rail (`--h5-nav-width`): it has no close button, does not block the page beside it and keeps the list of terminals visible while one is open; the terminal or chat fills the rest, the settings panel opens on the right with the page dimmed (a click beside it closes it), and the keys and the translate row are limited to 960px and centred. `h5.js` (`isWide`, `syncLayout`) uses the same `(min-width: 900px)` query as the CSS, so resizing the window or rotating a tablet switches between the two without a reload. Hover feedback is added only where a mouse exists (`@media (hover: hover)`).

## Multi-column view

A wide screen (900px and up) can show several sessions side by side: a row of columns, each a complete copy of the page (its own terminal and a compact one-row bottom area, see "Compact bottom area of a column" in page-terminal-and-bottom-bar.md) under one header that the top page draws, and the person switches back to the normal view with the same button. A navigation rail on the left switches between two tabs: "Columns" (the row of columns) and "Mind maps" (a whole mind map page).

- Why iframes: each column is an `<iframe>` of the page itself in pane mode, `/h5?pane=<id>`. The whole page is reused as it is (task list, sessions, keys, translate-and-send, uploads, voice, copy and paste), so a column can never lack a feature of the page or drift from it. The cost is one copy of the page's scripts per column, which a computer can carry. The session cookie works in the frame because it is the same origin (`SameSite=Strict` cookies are sent to same-site frames).
- Why the top page keeps the shared parts: the top page stays the one place for the activity feed, the notices and the reminder sound, the update check and the silent auto-update reload. Four columns must not mean four notifiers, four sounds for one event or four updaters. The one updater (`UpdateButton`, `#h5-update`) is in the navigation rail, which stays above the strip. When an auto-update reload happens, the whole top page reloads and the strip comes back from storage. What a pane leaves out is the pane mode's work (in `h5.js` and the shell, by the other half of this feature).
- Switch: the Columns (or Mind maps) destination of the navigation rail enters the view and Sessions leaves it (see [page-navigation.md](page-navigation.md)); only while the screen is wide (`H5UI.media.wideQuery`) and never on a page that is a pane or is framed (`canOfferColumns`: no `pane` parameter at all, and `window.top === window`), so a column never opens columns of its own. The choice is kept per device in `localStorage` `h5-columns` = `{ on, ids, tab }` (read and written in try/catch; `tab` is `columns` or `maps`, anything else or nothing is `columns`) and restored before the first render (`startColumns` in `entry.jsx`). Below the breakpoint the strip and the switch go away and the normal view returns; the stored choice stays, so a wide screen shows the strip again.
- Strip (`scripts/h5-shell/Columns.jsx`, rules in `columns.mjs`): `#h5-columns`, fixed over the whole window (z-index 1250: above the app bar and the permanent drawers, below MUI dialogs and the notices): the navigation rail (`#h5-columns-nav`) and, right of it, the Columns tab (`#h5-columns-tab`: a thin app bar `#h5-columns-bar`, see "The bar" below, and the row `#h5-columns-strip`) and the Mind maps tab (`#h5-columns-maps`), one above the other. Up to four columns (`.h5-column`, `data-pane-id`) share the strip's visible width evenly; with more, each one is exactly a quarter of that width and the row scrolls sideways (see "Sideways scrolling" below). A column is never narrower than 340px, so a narrow window fits fewer than four and scrolls earlier (`flex: 1 0 <min>px`, `min-width: <min>px`, also on the strip as `--h5-column-min`); nothing is squeezed. Each column is its header (see "Column header" below) above its iframe; between columns a plain 1px divider (the theme's `divider`); the widths are never dragged. The first use opens `floor(strip width / 340)` columns, at least 2 and at most 4 (`defaultCount` of `stripWidthOf(innerWidth)`, the window less the 72px rail: 4 from a 1432px window, 3 from 1092px, else 2); "Add column" adds one at the end and scrolls it into view; at most 12 (`MAX_COLUMNS`, also the most `readLayout` / `writeLayout` keep). The last column cannot be closed (its close button and menu item are disabled): leaving the view is Sessions in the rail.
- Update in the navigation rail: the page's one updater (`UpdateButton`, `#h5-update`) sits near the bottom of the navigation rail, above Settings, in both views (before the redesign the view had a second button, `#h5-columns-update`, for a header updater hidden under the strip). Its dialog (MUI, portaled to `body`, z-index 1300) shows above the strip and the rail and gives the focus back to the button. `UpdateButton` still writes its dot to the store (`state.updateDot`) and registers `ui.actions.openUpdate(returnTo)` for the phone header's More menu. The silent reload also waits while the Mind maps tab is shown (`pageBusy`: a reload would close the open map).
- The bar (`#h5-columns-bar`, the colour of the page's own app bar, 40px; 48px in touch input mode; the top of the Columns tab, right of the navigation rail): "N columns ▾" (`#h5-columns-list`, an outlined button, `aria-haspopup="menu"`) which opens the column list (`#h5-columns-list-menu`, a MUI Menu): every open column in the order shown, also those scrolled out of view (`.h5-columns-list-item`, `data-pane-id`, `data-state`): its state dot, device tag, task · session and a state word (focused / needs you / running / idle); choosing one scrolls it whole into view and moves the keyboard into its frame (`showColumn(id, { focusFrame: true })`; the menu then gives the focus back to nothing). Then "N running" (`#h5-columns-summary`, only when some run) and, when any column needs the person, an outlined warning chip "1 needs you" / "N need you" (`#h5-columns-needs`, the project's `Pill`) that goes to the first such column the same way. At the right end "+ Column" (`#h5-columns-add`, a text button, `aria-label` = `title` "Add column"). There is no tab strip and no "Equal widths". The parts that read the state of the columns (`ColumnSummary`, `ColumnHeader`) subscribe to `attention` and `terminalActivity` themselves and are mounted only while the strip is shown, so an activity push in the normal view draws nothing of the strip.
- Column header (`ColumnHeader` in `Columns.jsx`, `.h5-column-head`, `data-pane-id`, `data-state`, `data-focused`): drawn by the top page at the top of each column, right above its iframe (inside `.h5-column`, so it follows the column's place, width and slides), 38px with a mouse and 44px in touch input mode. It is a `role="group"` labelled "<task>, <session>, <state>[, focused]" (`headerLabel`, e.g. "SELF-TAGENT, main dev, needs you"). From the left: the drag grip (Ant Design `holder`, pointer input only, "Drag to reorder"), the state dot (`columnStatus`, the same state as the rail's tiles: the theme's success / warning / disabled colours), the device tag of the pane's task (the same `DeviceTag`; a remote service the pane's list does not tag comes as a device without a colour), and "Project · session ▾" (`.h5-column-switch`, the task in 600 weight, the session in the secondary colour after a "·", cut with an ellipsis; "Column N" before the pane spoke, "Choose a task" when it shows none; `aria-haspopup="dialog"`, `aria-expanded` from the pane's `sheet`), which shows or hides that column's task sheet (the job of the pane's former ☰: `tasks` with `toggle`). On the right: while the column needs the person a warning chip "Needs you" ("Needs selection" / "Needs acceptance" while its terminal waits at that kind of question, `data-waiting`; the same words in the column list, the rail tiles and the session header), an orange tint over the header and an orange 2px top line; else, while its terminal runs, the agent's name (Claude / Codex) as a hint. Then the actions (`.h5-column-act`, `aria-label` = `title`): the terminal width (`columnWidth`, "Wide terminal", `aria-pressed`; a click switches Fit <-> Wide, a right click offers Fit to screen / 200 / 500 / 1000 / 2000 columns with the current one ticked, `#h5-column-width-menu`; disabled while the pane shows no terminal), Maximize (`maximize`, `toggleMaximize`; "Restore columns" with `restore` while maximized), "⋯" (`taskMore`, "Column actions") and close (`close`). With a mouse the actions show on hover, on keyboard focus inside the header or while its menu is open (`display` toggled by CSS, the hint gives way); the focused column always shows "⋯" and close. In touch input mode "⋯" and close are always shown with 44px targets and the width and maximize buttons are not drawn (they are in the menu). The focused column has a 2px primary top line and a lighter header (the MD2 dark elevation overlay of 4dp instead of 1dp, `getOverlayAlpha`), instead of the old 1px outline; while a column is focused the other columns' iframes are dimmed with `filter: brightness(0.9)` (120ms; normal terminal text stays far above 4.5:1). A click on the header itself (not a button) focuses the column and moves the keyboard into its frame.
- Column menu ("⋯", `ColumnMenu`, `#h5-column-menu`, a MUI Menu): "Switch task or session…", the terminal width ("Wide terminal", or "Fit the terminal width" while wide), "Maximize" with its keys (⌘⇧↩ on Apple systems, Ctrl+Shift+Enter elsewhere; "Restore columns" while maximized), a divider, "Rename session", "Restart session" (both only while the pane shows a terminal), "Reload column", a divider, "Close column" (error colour). Everything a header button does is there, so nothing needs a hover. Items that act inside the pane and need the keyboard (switch, rename, restart) move it into the frame and the menu gives no focus back to the top page (a focus taken back would blur the rename field and cancel it).
- Header actions in the pane: the header is the top page's but what it acts on is the pane's page, so `ui.actions.columnAction(id, event, options)` focuses the column, for `tasks`, `rename` and `restart` also its frame, and posts `actionMessage(event)` (`columns.mjs`): `{ type: 't-agent-pane', event: 'tasks', toggle? }`, `{ ..., event: 'width', mode?, cols? }` (no mode: switch Fit <-> Wide), `'rename'`, `'restart'`, `'reload'`. It waits for the frame's page like `open`. The pane's side is under "Pane mode" (Messages).
- Reordering by dragging a header (`useTabDrag` in `scripts/h5-shell/tab-drag.jsx`, the feel of the lists' `useListDrag` along x, sharing its timings): a finger held still for 400ms on a header (not on its action buttons) picks the column up (`navigator.vibrate(10)`); a finger that moves more than 8px before that scrolls the strip, and a short tap is a tap. A mouse picks it up after 400ms held or a move of 4px. While dragging, a lifted copy of the header (`.h5-column-head-float`, `position: fixed` in `#h5-columns`) follows the pointer along the strip, the column's place is dimmed with a dashed outline (`data-drag-slot`) and a 3px primary line (`.h5-column-drop-line`, in the strip) shows where it lands; the columns themselves do not move until the drop, and the iframes take no pointer events meanwhile (`html[data-column-drag]`), so the pointer is never lost to a page under it. Near an edge of the strip it scrolls. The drop saves the new order at once (`moveColumnTo`), the copy settles where the column lands and the columns slide there (below); Escape puts it back ("Reorder cancelled" in the live region); the click after a drag is swallowed; a long press shows no context menu. The strip cancels `touchmove` while a header is picked up.
- Moving the columns without reloading them: `ids` is the order the person sees (the column list, columns, keys, storage), but the columns' elements never follow it. Moving an `<iframe>` element in the DOM reloads its page (a terminal connection, a scroll position and a draft would be lost), and a keyed React list moves elements when the order changes. So the strip renders the columns in the order they were created (`mountOrder` in `columns.mjs`: the ids already there in their old order, new ones at the end; a fresh page creates them in the stored order) and shows each at its place with the CSS `order` property (a closing, hidden column gets 999). The strip is `position: relative`, so a column's `offsetLeft` is its place in the strip's content: reveal, the in-view underline and the slides read it. After every commit `useFlipX` (`tab-drag.jsx`) compares the order of the boxes that stayed (by their `offsetLeft`) with the last one; when it changed, each box slides from where it was seen to its new place with a Web Animation of `transform` (180ms ease-out; a change that comes during a slide starts from where the box is seen). Nothing slides while a header is dragged; an element with the keyboard focus that lost it gets it back. Boxes that came, went or changed width do not slide. `prefers-reduced-motion: reduce` makes the copy and the columns jump. The tests check that every pane's `contentWindow` and a mark set in it survive drags and key moves, and that the DOM order of `.h5-column` never changes.
- Moves are said in a polite live region (`#h5-columns-live`): "Column moved to position N of M".
- Navigation rail: since the single-view redesign the page's one rail (`NavRail`), shown above the view at its left edge; see [page-navigation.md](page-navigation.md). ### Pane mode

A column of the multi-column view is the whole page in an `<iframe>` of `/h5?pane=<id>` (`id` matches `[a-z0-9]{1,16}`). `scripts/h5-shell/pane.mjs` decides it once, in `entry.jsx` before anything is read from storage: a valid id AND `window.top !== window`. An invalid id, or a top-level `/h5?pane=...`, is the normal page; without a pane nothing changes. In a pane `window.H5Pane` is set (`{ id, prefix, key(name), post(event), engaged(), forget() }`) and `H5UI.get().pane` is the id (null otherwise).

- **Own selection.** What this view shows is stored under `pane:<id>:<key>`, so panes never overwrite each other or the normal view; device-wide preferences keep their shared keys. Which keys are the person's on every device and engine (the shared page state) and which stay in the browser: "Key audit" in [shared-page-state.md](shared-page-state.md). The key audit of a pane (localStorage unless marked):

| Key | Where | In a pane |
| --- | --- | --- |
| `h5-source` | `h5.js` store | per pane |
| `h5-task:<source>` | `h5.js` store | per pane |
| `h5-terminal:<source>:<task>` | `h5.js` store | per pane |
| `h5-terminal-width`, `h5-terminal-wide-cols` | `h5.js` store (header wide-terminal button) | per pane (each column sets its own terminal width) |
| `h5-sidebar-collapsed` | `entry.jsx` | per pane (wide layout only; a pane of 900px or more has its own); the top page's is the shared page state's |
| `terminal-client-id` (sessionStorage) | `terminal-owner.js` | per pane: the frames of a tab share its sessionStorage, and two columns must be two terminal clients, so the second one gets the normal "in use" prompt instead of silently replacing the first one's socket |
| `h5-terminal-width-noted` | `h5.js` store (`SHARED_KEYS`) | shared (a one-time hint for the device) |

  Not stored at all, so nothing to split: the expanded rows of the task list, the search and the All / Running / Pending filter, the translate box draft, the chat draft. Hidden devices, the font size of the terminal and automatic update are server settings or fixed. A new pane with nothing stored starts on the task list with nothing selected.
- **One feed, one notifier, one updater: the top page's.** HTTP/1.1 allows about 6 connections per origin, so a pane opens no long-lived stream: the terminal activity uses its polling fallback (`streamLimit()` is 0 in a pane; `FALLBACK_POLL_MS`, only while the page is visible), and T-Attention runs `passive` (`startAttentionFeed`: no `/api/attention/stream`, no reads of its own, no notice or sound; the actions stay for Settings). The agent chat that is shown keeps its event stream (it is what the pane shows). Terminal WebSockets are unchanged (WebSockets do not count against the limit). No updater, so no update polling and no silent reload: the top page reloads, which reloads its frames. No Attention button (`Terminal.jsx`). No plan usage reads (`startPlanUsage` runs on the top page only, see [plan-usage-page.md](plan-usage-page.md)). No page header at all (`Header.jsx` draws nothing in a pane, also when the pane is narrow enough for the phone layout): the top page draws the column's header and acts on the pane by messages (see "Column header" and "Messages"). `fitAgentView` puts the chat at the pane's top then.
- **Layout.** A pane judges its own width: `(min-width: 900px)` and `fitViewport` read the iframe's viewport, so a column under 900px (at least 480px; 636px with 13px Menlo) gets the phone layout, while the input mode (`(hover: hover) and (pointer: fine)`) is still the computer's: pointer mode, no on-screen keyboard buttons, Enter translates and sends, a click focuses the terminal. `--h5-height` is the iframe height (`innerHeight` in pointer mode).
- **Focus.** A pane takes no focus by itself until the person pressed a pointer or a key in it (`H5Pane.engaged()`, `state.paneEngaged`): otherwise every column would pull the focus into its frame as it loads. `focusTerminalSoon` waits for it, and the task sheet a new pane opens on does not auto-focus (`disableAutoFocus`). A click in the pane focuses its terminal as usual; a window focus is told to the parent only after that.
- **Focused column.** The bottom area of a pane is the compact one row ("Compact bottom area of a column" in page-terminal-and-bottom-bar.md), whose buttons show only in the focused column, so the pane must know whether it is that column (`state.paneFocused`). It cannot learn it alone: the top page's `columns.focus` also moves without the pane's window getting the focus (a click on the column's header, a new column, the column list, an open request, a column closed), and the pane's window keeps its active element when it loses the focus. So the top page tells it: `put` in `Columns.jsx` posts `{ type: 't-agent-pane', event: 'focused', on }` to the column that lost the focus and to the one that got it whenever `columns.focus` changes, and answers each pane's `ready` with its current state. The pane also sets it to true at once, before that answer, on a press in it, on its window's focus once the person used it, and when the focus comes into its draft box (`ui.actions.paneUse`, which also posts `focus`); a column that was not the focused one always posts `focus` then (the 200ms de-duplication applies only to a column that already was). Without a top page that answers (a test parent), a pane becomes focused on the first press and stays so.
- **History.** A frame's history entries are joined with the top page's, so a pane's `history.go` could move another column or the top page. A pane does not start the back layers (`back.mjs`); Escape and the close buttons close what is open.
- **Messages.** To the parent, always `parent.postMessage(message, location.origin)`: `{ type: 't-agent-pane', paneId, event: 'ready' }` once every script has run (DOMContentLoaded), `'focus'` on a pointer press in the pane or when its window gets the focus (once per press), and `'title'` with `{ title, session, device?, target?, agent?, sheet?, width? }` (the task and session names, empty when none; the device of the shown task when the task list tags its row: `{ name, instanceId, local, offline }`, `deviceOfRow`, else the remote service's name as a device without an instance id; `sheet: true` while the task sheet is shown (the drawer, or the sidebar not folded on a wide pane); `width` `{ mode, cols }` while a terminal width is known), which the column's header draws, after `ready` and on every change; `'mindmaps'` when the person opens the mind maps in the pane (the Mind maps button of its task sheet: the top page shows its Mind maps tab; a pane never shows a map itself). From the parent: `{ type: 't-agent-pane', event: 'focused', on }` (see "Focused column" above; same checks as below). `{ type: 't-agent-pane', event: 'forget' }` (an optional `paneId` must match) is accepted only when `event.source === window.parent` and `event.origin === location.origin`; it removes every `pane:<id>:` key from localStorage and sessionStorage and answers `'forgotten'`. `{ type: 't-agent-pane', event: 'open', sourceKey, taskId, terminalId?, conversationId? }` from the parent (same checks; `sourceKey` is a source key such as `local` or `remote:3`) opens that task and terminal as a tap on its row would, or, with `conversationId` and no `terminalId`, that agent chat of the task as a `?openChat=` link does (`openChatFromLink`, this machine only) (`ui.actions.paneOpen` in `h5.js`, after the services are known; an unknown service, task or chat is ignored quietly). The top page uses it for a `?openChat=` link it handles while the columns are shown. The actions of the column's header come the same way and with the same checks (`readAction` in `columns.mjs`, `runAction` in `pane.mjs`), and each counts as the person using the pane (`engaged`): `tasks` (`ui.actions.paneTasks({ toggle })`), `width` (`setTerminalWidth({ mode, cols })`, or `toggleTerminalWidth()` without a mode), `rename` (`paneRename`: the task sheet opens and the menu state is set to the rename field of the terminal shown, as the row's "Rename" does; nothing under a chat), `restart` (`paneRestart`: `restartTerminal` of the terminal shown, with its `confirm`), `reload` (`ui.actions.refresh`). A message posted to a frame that is removed at once may never arrive: the top page can also call `forgetPaneKeys(id)` from `pane.mjs` itself (same origin, same storage).
