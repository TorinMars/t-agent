# The page: task list and sessions

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

## Task list and sessions

- **Task list look** (`scripts/h5-shell/TaskDrawer.jsx`: the top of `Panel`, `TaskRow`, `Sessions`; MD2, the 304px list of the single view and the phone drawer). Top: the "Tasks" title (h6) with "New task" at its right (a text button with a plus, `#h5-add-task`, opens the New task dialog; it used to sit below the list), the search field (`#h5-task-search-input`, small outlined field on a faint fill with a search icon and a clear button `#h5-task-search-clear`; Escape in it clears it), then MD2 choice chips with counts: All, Running N, Needs you N (`.h5-task-filters`, `data-filter` all / running / pending, `aria-pressed`; the chosen chip is a 16% primary tint, the others outlined; 28px, 32px on a touch screen with a 44px hit area). A count is the number of sessions of the listed tasks in that state (the sum of `task.running` / `task.pending`, from the activity feeds; no number when 0). The less used list actions, Expand all (`#h5-expand-all`) and Collapse all (`#h5-collapse-all`), are a menu (`#h5-task-list-menu`) behind "List options" (`#h5-task-list-more`) at the end of the chips. On a phone the close button `#h5-close-tasks` ends the title row. Task rows: the engine tag, the name as the person typed it (no capitals forced, weight 500, 14px; 16px on a touch screen), at most two lines with an ellipsis (`-webkit-line-clamp: 2`, the full name in the title's `title`), the "N sessions" line once known, and at the right a status dot (orange when a session needs the person, else green when one runs; none when all are idle). On a computer the row's "+" (New session) and "⋯" take that place only while the pointer is over the row's line or the keyboard focus is in it (`:hover`, `:has(:focus-visible)`; opacity only, so nothing moves and Tab reaches them); on a touch screen the row has one "⋯" (44px) and no "+": its menu starts with New session. Both "⋯" (task and session) open the same MUI menu under the button (`#h5-session-menu`, `TermMenu.jsx` `SessionPopup`; `ui.actions.taskMore(ref, anchor)`); the task menu lists only what can be done (a Move step that cannot run is left out instead of disabled). The bottom sheet (`#h5-term-menu`) is still used for a call without an anchor. Session rows (40px, 44px on a touch screen): the 28px glyph tile of the kind (Claude, Codex, `>_`) with a status dot on its corner, the name, and a status line "Running" (green), "Needs you" (orange; "Needs selection" / "Needs acceptance" while the agent waits at that kind of question, `data-waiting`, "Two waiting kinds" in `docs/design/terminals.md`) or "Idle" (grey), the colours of the column headers (`success`, `warning`, `text.disabled`; the line in the light shade); the kind is read out before the state (hidden text). The state comes from h5.js `sessionState` (`status` on each row of `ownSessions` / `peekSessions`): the same feed snapshot as the filters (`running`, also a running sub-agent; `done` = needs you), so no new request; while a service's activity is not known the line names the kind ("Claude session", "Terminal") as before. No duration is shown (the activity has no start time) and there is no "Exited" state (the terminal list does not say whether a shell ended). A change of one terminal's state still redraws only its task's row (`scripts/test-h5-render-count-browser.cjs`). Selected: the shown session's row, or the shown task's row when that session is not listed under it (collapsed), has the MD2 selected look: primary at 12% with a 3px primary indicator inside the left edge (`SELECTED_SX`, also on the rename field); the whole row line has the hover tint. Task rows have no dividers; an open task (with its sessions) has one below it. Regression: `scripts/test-h5-one-list-browser.cjs` ("Task list look"). Older notes below describe the rows before this change where they differ.
- Phone task sidebar redesign (earlier; partly replaced by **Task list look** above) (`scripts/h5-shell/TaskDrawer.jsx`, `public/js/h5.js`). Tasks are one list with no status group titles: the engine tag (or, with an older server and this machine alone, a chevron), the title, and an "N sessions" line once the task's sessions are loaded; every task can add a session (`ui.actions.addSession` selects a task that is not shown, then opens the New session dialog). Only terminals are listed: agent chats have no row, no count and no entry in the Session menu, and the list does not read them (`GET …/agent/conversations` is only read for a notification link). A task whose sessions are all chats counts as a task with no sessions. `pending` on the conversation rows of `services/agent-chat.js` (`publicRow`) stays for the API. The search box and the filter chips filter the tasks and the sessions of open tasks only (closed tasks are not loaded). Not done: counts for collapsed tasks, grouping by project.
- Phone task sheet: a tap on a task opens and closes the list of that task's sessions (`expandedId`, `toggleTask`; one task is open at a time, `aria-expanded` on the row), and a tap on a session goes there and closes the sheet. The sheet opens with the sessions of the task that is shown. The sessions of a task that is not the selected one are read when its list is opened (`loadPeek`: its terminals, and on a remote Engine what it can do, for the actions of the rows) and listed with the same `⋯` button (`peekSessions`, `openOtherMenu`: Rename, Open, Restart in the working directory for a terminal, Delete; see "Actions on a session of another task" below); a task with no sessions shows "Open this task". A tap on such a session selects the task and shows that terminal (`wantedTerminal`, remembered as the terminal of the task). A new task is still selected at once. Regression: `scripts/test-h5-browser.cjs`.

Each row has the "⋯" of a session row (`.h5-recent-more`, "Terminal actions"; shown on hover or focus on a computer, where it takes the place of the time, always on a touch screen at 44px): `ui.actions.recentMore` opens the same `SessionPopup` as `rowMore` (Copy text, Rename, Reopen / Open, Move up / down, Restart, Delete); for a task that is neither shown nor open in the list it first reads the task's terminals, then calls `openOtherMenu` if the button is still there. - **One task list, no Engine switch** (`h5.js`, `TaskDrawer.jsx`). The tasks of this machine and of every enabled connected service (plain remote Engines and linked services alike) are one list; there is no user-facing switch of Engine. Internally each `source` (`LOCAL`, `remoteSource(...)`) keeps its own list (`tasks`, `groups`, `status`: new / ready / offline). `source` itself now only means the service of the shown task, set by selecting a task (this machine when none is shown); everything else starts from the row it was tapped on.
  - Identity: task ids repeat between services, so `expanded`, `peeks`, the menus (`menuTask`, `menu.task`, `menu.rename.task`), the `taskDialog` (`sourceKey`) and the archived rows are keyed by `taskRef(source, id)` = `<source key>|<task id>`, and the shell hands that ref back on a row. A bare id (T-Attention's way back) is this machine's. An action started from a row goes to that row's service whichever task is shown: `taskMore`, `+`, expand and peek, rename, working directory, delete, archive and restore, the "Move to" of a group, agent sessions. Warm terminals, early sockets and `actionsRunning` are per source and task too.
  - Loading: `loadTasks` reads every listed source in parallel (`loadSource`), and the shared order (`loadOrder`); each fails on its own, a slow or offline one neither delays nor blanks the others, and a later read makes an older one stale (`loadSeq`). An offline service adds no rows if it never answered (a linked engine: the rows this engine last read, dimmed and not openable, see "Tasks of an offline engine" in [failover-and-one-login.md](failover-and-one-login.md)), and keeps the rows it had (dimmed, with a muted tag and "offline") if it went offline in use, with one info line per offline engine above the list. While a service is offline a slow poll (`OFFLINE_POLL_MS`, 30 s, only while the page is visible) brings its tasks back without a reload; a failed feed reads the list at once (at most every few seconds), which is how a service going offline during use is noticed. A terminal open on an offline service follows the existing reconnect text.
  - List: one flat list of every listed device's tasks in the shared order (see **Task order** below); no section or header per device. The devices themselves are in the one order of devices, by name, this machine among them ("Devices in one order" in [entry-symmetry.md](entry-symmetry.md)), which places the tasks not in the shared order yet. Each row (`.h5-task`, `data-ref`, `data-source`) starts with its engine tag whenever the order can be changed (also with this machine alone: its engine name, e.g. "T01") or more than one device is listed (`tagged` in `renderTasks`). Only an older server (no `/api/task-order`) with nothing but this machine has no tags; its rows keep the expand chevron.
  - The header area names the device of the shown task on the session-name line (`#h5-task-service`, `Header.jsx`). Whenever the list tags its rows, it is the same engine tag as the task's row: the `DeviceTag` component itself, taken from the selected row of `taskList.tasks` (so name, 8-character cut, colour from the instance id, 20px pill, border and font are the row's), always in its closed look (never the open ring), on this machine's tasks too, followed by the session name; the button's vertical padding drops to 2px with the tag, so the header keeps its height, and at 320px both stay on one line (the session name is cut first). Without a tag (one device and no sorting, or a shown task whose device the list does not show, e.g. a hidden one) a remote service is named in plain text as before and this machine not at all.
  - New task: when other services exist the New task dialog has "Create on" (`#h5-new-task-on`), the online services in the one order of devices; it starts on the machine a task was last made on (`h5-create-on`, shared page state, with "The machine you chose last time" under it), else the first by name, never the page's own engine ("Create on" in [entry-symmetry.md](entry-symmetry.md)); the remote path hint depends on that choice. It is the only place a service is chosen.
  - Search, the All / Running / Needs you filters, the active count (`state.activeCount`) and the next-session action of a column cover all listed services. Running and Pending are decided from the feeds (`task.running` / `task.pending`; they used to look at session rows that carried no such state, so they matched nothing).
  - Feeds (`feeds`, one per listed service with its own backoff, `syncFeeds`): none for a service that is hidden, offline or gone, stopped while the page is hidden. Each stream is a long-lived `fetch` to this origin and HTTP/1.1 allows about 6 connections, so at most `MAX_STREAMS` (3; 16 on HTTP/2 or HTTP/3, from `nextHopProtocol`) stay live, this machine and the service of the shown task first; the other sources poll every `FALLBACK_POLL_MS` (30 s). Terminal ack and unread states follow the feed of the terminal's service.
  - Archived section: the rows of every listed service that can archive, read when opened; the row names its service when it is not this machine, and Restore and Delete use that row's service. The guards (`noArchiving`, rows must have `archived_at`) are per source.
  - Remembered selection (`h5-source`, `h5-task:<key>`) and deep links: on reload the remembered service and task, if it is listed and answers within `REMEMBER_WAIT_MS` (5 s); else the remembered task of this machine or another listed service, else no task; never an error. A fallback does not overwrite what was remembered. `?openChat=` opens this machine's chat directly; `?openTerminal=<engine>:<task>:<terminal>` opens that terminal on that service (see "Page link to a terminal" under "T-Attention desktop window (macOS)"). The early socket is dropped when the selection does not turn out to be its task.
  - **Which devices are shown** ("Show in task list", `Engines.jsx`, one switch per device when there is more than one, for a linked service too): `GET /api/task-list/hidden-devices` -> `{ hidden: [sourceKey, ...] }`, `PUT { hidden: [...] }` -> the same (`routes/task-list-prefs.js`, one key in `system_state`, no schema change, per owner, so the phone and the computer agree; `INVALID_HIDDEN_DEVICES` for anything but an array of at most 200 keys `local` / `remote:<id>`, `LAST_DEVICE_VISIBLE` when it would hide every existing device). It is display only and is not `remote_servers.enabled`: a hidden device stays connected and in Settings, and keeps its linked-service sharing. It is left out of the list, the search, the filters, the count, the next-session button and the Archived section, and gets no feed. This machine can be hidden too; the switch of the last visible device is disabled. The shown task of a device being hidden stays open until the person opens something else; on the next load the selection falls back as above. A new device is visible by default; a removed device is ignored and dropped on the next save. An older server answers 404: nothing is hidden and the switches do not appear.
- Phone header: the name of what is shown (the open chat, otherwise the current terminal) stands under the task name in small text (`#h5-session-name`, `renderSessionName` in `h5.js`, called from `renderTabs`). The line keeps its height when there is no name, so the header never changes height (the chat view is placed under it once, in `fitAgentView`). `AgentChat.mount` has a new `onTitle(title)` option, called when a chat is renamed or gets its first-message title, so the header follows without a reload. - Session menu: the `+` on the right of the selected task row opens a Session menu: Claude session, Codex session (terminals running the agent; no agent chat is offered here) and New Terminal (a plain phone terminal). A session kind expands to "New Claude/Codex session" plus the sessions that were run in the task's working directory (newest first, titled by their first prompt); choosing one creates a terminal whose shell first types `claude` / `codex` or `claude --resume <id>` / `codex resume <id>` (`POST …/terminals` with `{agent, session_id, title?}`; the command is held in memory and typed once when the PTY is spawned). Sessions come from `GET …/tasks/:id/agent-sessions?agent=claude|codex` (`lib/agent-sessions.js`: `~/.claude/projects/<dir>/*.jsonl`, and `~/.codex/sessions/**/rollout-*.jsonl` filtered by `cwd`); the Engine API and the remote proxy expose the same endpoint. An old engine ignores `agent` and opens a plain terminal.
- No terminal until the person creates one: every path that makes a task (`POST /api/tasks`, `POST /v1/tasks` and through it the remote proxy, the bulk import) records the new task in `task_default_terminal_removed` in the same transaction (`lib/task-default-terminal.js`), so a new task and a task whose `default` was deleted are the same case: `default` is not listed, `assertTerminal` answers `TERMINAL_NOT_FOUND`, and neither a socket (1008) nor an Engine ticket (404) starts a shell, also for an older client or a stale tab that names `default` or names nothing. A shell only starts for a terminal that exists. Tasks made earlier are not changed: they keep `default` and an attach still starts its shell. An older Engine behind a new Client still makes tasks with `default`. Creating a task has no option to start an agent; an agent session is created from the New session dialog like a terminal. The page: `showNoTerminal` in `h5.js` (no terminals in the list, or the last one was deleted) forgets the remembered terminal of the task, drops the early socket and the warm views of the task, and shows "This task has no terminal yet" with a New session button (`#h5-empty-new`, `emptyCreate` in the store), which opens the same New session dialog as the `+` (over the page: neither the phone's task sheet nor a folded sidebar is opened for it). `createTerminal` waits for the list being read, so an empty answer cannot wipe a terminal just created. Controls that act on a terminal say "The terminal is not connected" or do nothing.
- **Create dialogs** (`NewSessionDialog` and `NewTaskDialog` in `scripts/h5-shell/TaskDrawer.jsx`, drawn by `App.jsx` outside the task sheet). Creating a session and creating a task both open a modal MUI `Dialog` in the style of the task dialogs (`TaskDialogs.jsx`), so the back gesture (`back.mjs`), Escape and a tap beside it close them, and the keyboard handlers of `h5.js` send no key to the terminal while one is open (`modalOpen`). Both fill only the visible area (`height: var(--h5-height)`, which follows the visual viewport, `fitViewport`), so with the on-screen keyboard up the dialog sits above it; both follow the one dialog pattern ("One dialog pattern" in `page-dialogs.md`): New session is a centred `xs` dialog (16px margins on a phone), New task an `sm` form that is full screen under 600px; the fields scroll while the title and the buttons stay, and the focused field is kept in view when the keyboard opens or closes. Their first field takes the focus, as in the other dialogs. While one is busy its buttons are disabled and it does not close (the back gesture is ignored until it is done). Regression: `scripts/test-h5-create-dialogs-browser.cjs` (390x844 and 320x568 touch with a smaller fake visual viewport, 1440x900; `SCREENSHOTS=<dir>` saves both dialogs at 390px).
  - New session: opened by the `+` of a task, by "New session" in the empty terminal area (`newSessionFromEmpty`) and by Cmd+Shift+O / Ctrl+Shift+O (below). The `+` of a task that is not selected selects it first and keeps the phone sheet open under the dialog (`selectTask(…, { stay: true })`); the `+` of a collapsed task expands it. The dialog is titled "New session", names the task and, when it is not on this machine, its service; then the optional "Name (optional)" field (`#h5-new-name-input`), the choices as an MD2 simple-dialog list, edge to edge (`#h5-term-menu-actions`, each a `ListItemButton` rendered as a `button`: Claude session, Codex session, New Terminal; a session kind's sub-list, with Back, replaces them in place under its own overline heading) and Cancel (`#h5-term-menu-cancel`). State: `menu.naming` with `menu.task` (the ref, so the task of the row on its own service), `sub`, `taskTitle`, `service`, `busy`, `error` (`showSessionMenu` in `h5.js`). A choice (`startSession`) keeps the dialog open and busy ("Creating…") until the terminal is made (`createTerminal` resolves to true, or rejects with the server's error, which the dialog shows as "Could not create the terminal: …"); then the dialog closes, the terminal opens and the phone sheet closes, as before. Another task becoming the selected one or the task leaving the list (`leaveTask`) closes it; an answer for a dialog that was closed is dropped (`creating`). The name is kept while moving between the lists (Claude session, Back) and is cleared when the dialog closes; Enter in the field runs the highlighted choice of the first list, or the first entry of a sub-list (New Claude/Codex session); see Keyboard below. The name goes to `POST …/terminals` as `title` (local, Engine `/v1` and the remote proxy, which forwards `title`), validated like a rename (`cleanTitle` in `routes/terminal.js`: control characters and runs of whitespace become one space, trimmed, at most 40 characters, else 400 `TERMINAL_TITLE_TOO_LONG`; any script, Chinese and emoji included, is kept). An empty or blank name keeps the default `Terminal N` / `Claude N` / `Codex N`. A resumed session takes the name too. For an agent chat it goes to `POST …/agent/conversations` as `title` (the chat keeps it; the first message only names a chat that is still "New chat").
  - New session keyboard (`NewSessionDialog`, `menuPick` and the Cmd/Ctrl+Shift+O handler in `h5.js`). Cmd+Shift+O on Apple platforms, Ctrl+Shift+O elsewhere (`APPLE`, as Cmd/Ctrl+K) opens the dialog for the task shown, on its own service (`addSession(taskRef(source, task.id))`). It listens in the capture phase before xterm, so it works with the focus in the terminal (Ctrl+O alone stays the terminal's), and calls `preventDefault` and `stopPropagation`, so the browser's own Cmd/Ctrl+Shift+O (the bookmarks manager in Chrome and Firefox) does not run when the browser lets the page have the key. It does nothing with no task shown, while another dialog, a menu, the copy view or the mind map view is open (the phone's task sheet does not count), and on a key repeat; while the New session dialog is already open the key is only kept from the browser. There is no multi-column pane mode, so nothing pane-specific applies. In the dialog the first list is Claude session, Codex session, New Terminal (items with `pick`; each has a `quick` run in `menuQuick`); one is highlighted (the selected list row, `Mui-selected` and `aria-selected`), Claude session first on every new list. The name field has the focus when the dialog opens (by any route). In the field, Up and Down move the highlight with wrap-around while the focus stays there (`role="combobox"` with `aria-activedescendant`, the choices are `role="listbox"` with `role="option"`); Enter makes a NEW session of the highlighted kind with the typed name or the default one (`menuPick`: Claude and Codex do not open their sub-list). Tab moves the focus into the choices as one stop (roving `tabIndex`: only the highlighted option is 0); there Up and Down move the highlight and the focus with wrap-around, Enter makes the focused kind, Shift+Tab goes back to the field with the text kept, and the next Tab reaches Cancel (then MUI's focus trap wraps). The focus ring (a 2px outline inside the row) is apart from the highlight. A press on a choice (pointer, or Space on a focused one) works as before: Claude / Codex session open their sub-list, where Enter in the field runs New Claude/Codex session and there is no highlight. During IME composition (`isComposing` or keyCode 229) Enter and the arrows do nothing. The hint "Enter to create · ↑↓ to choose" (`#h5-new-session-keys`, hidden on a touch screen) is shown under the first list, and the `+` of a task has the title "New session (⌘⇧O)" on Apple, "New session (Ctrl+Shift+O)" elsewhere (aria-label "New session"). Regression: `scripts/test-h5-new-session-keys-browser.cjs` (1440x900, a macOS-like and a Win32 platform, the real key combination through Playwright; whether a real Chrome window gives the key to the page before its bookmarks manager cannot be seen headless).
- Terminal actions: each terminal row has a `⋯` button that opens a popup right under that button (`SessionPopup` in `scripts/h5-shell/TermMenu.jsx`, a MUI `Menu` with `#h5-session-menu`; `menu.anchor` in the store is the button). It is right-aligned to the button, 44px per item on a touch screen, and stays inside the screen with an 8px margin. When it does not fit below and there is more room above, it turns over above the button; the visible area is the visual viewport, so the on-screen keyboard counts as the end of the screen, and what fits on neither side scrolls inside its maximum height. It has no title and no Cancel (the list is named after the session for screen readers). It fades in and does not grow: its items are in their final place from the first frame, because a press on an item that moves between mouse-down and mouse-up is lost. It closes on a tap beside it, Escape, the back button (it is a modal, so `back.mjs` finds it), choosing an item (also when a confirmation is answered with Cancel), a scroll of something that holds the button, a drag or wheel beside it, the task sheet closing, the sidebar folding, and its row going away; a terminal printing beside the list does not close it. The actions of a task (`⋯` of a task row) open the same popup (see **Task list look**). Regression: `scripts/test-h5-session-menu-browser.cjs`. The actions: Rename (`PATCH {tasksBase}/{task}/terminals/{id}`), Reopen (reconnect, starts a new shell if it was closed), Restart in the working directory and Delete (both `POST {tasksBase}/{task}/terminal/control` with `restart-workdir` / `delete`, after a confirmation; the `default` terminal can be deleted too: the server records that in `task_default_terminal_removed`). Works for local and remote engines alike.
- Selecting another task: the task left keeps its sessions and count at once (from the list of the selected task, when that was read) and is read again; a list that has no answer after 10 seconds says "Could not load the sessions", a late answer still replaces that, and the next open of the list reads again. An older read of a list never overwrites a newer one (`loadPeek`, `selectTask`, `loadTerminals`; `scripts/test-h5-peek-after-switch-browser.cjs`).

### Shared task order

The task list has one order, the same in every browser of this service and on every linked service (whose list holds the same tasks). Code: `services/task-order.js`, `routes/task-order.js`.

- **Keys.** A task is `<instance id>:<task id>`, the instance id being the Engine's own identity (`engine_identity` `instance_id`, reported as `engine_id` in `/v1/info`), because the `remote:<id>` row ids differ between machines. `GET /api/system/version` has `instance_id` (this machine), and every row of `GET /api/remote-servers` has `instance_id`: what its `/v1/info` last reported (remembered by the name sync of `services/remote-info.js` in `system_state` `remote_engine_instances_v1`, `{ "<row id>": "<instance id>" }`), else the peer's id in the link record, else `null`.
- **Storage.** `system_state` `task_order_v1`: `{ "<login>": { order: [key, ...], updated_at } }`, `updated_at` in milliseconds; no schema change. `tasks.sort_order` is not touched.
- **Page API.** `GET /api/task-order` -> `{ order, updated_at }` (`updated_at` 0 when never set); `PUT { order }` -> the stored value. Behind the session and same-origin gates of `/api`, per owner, like `routes/task-list-prefs.js`. Each key must match `^[A-Za-z0-9-]{1,64}:\d{1,12}$`; duplicates are dropped keeping the first; at most 5000 distinct keys; otherwise 400 `INVALID_TASK_ORDER`. `updated_at` becomes now, and at least the previous value + 1, so a change made after a sync always beats the synced list even when the clocks disagree.
- **Keys nobody here can see stay.** Keys of the stored list that a new list lacks (a task hidden from this service by per-task visibility, on a hidden device, offline, on a third service, deleted) are kept after the key that came before them in the old list, at the start when none did. Over 5000, such kept keys are dropped from the end, where the oldest tasks are; a key the new list sent is never dropped. Archive and delete leave keys in place.
- **New and restored tasks.** The server inserts nothing: the page treats a task that is not in the order as new and places it first.
- **Between linked services.** Last writer wins on `updated_at`. After a local `PUT` the stored list is sent, after the answer, to every online linked peer (`PUT /v1/task-order`, 5 s, best effort), and a newer list in a peer's answer is kept here. When a link changes while online (it came up, was renamed) the peer is read at once (`GET /v1/task-order`), and every online peer is read every 5 minutes: the newer list is kept, and ours is sent when ours is newer. Both go through the link's row as every other link call does (`request` with the row's base URL and token, so A reaches B through the tunnel and B reaches A directly). A peer's list is stored merged in the same way and never sent on, so there is no loop; a peer's keys of a third service are kept. A peer without the route (404) is ignored. A 401 marks the link revoked, as elsewhere.
- **Limits.** Two lists made at once on two services within the same millisecond keep whichever arrives second on each side until the next change. Keys kept from an older list on one side are not sent back to the other side until the next change made there.
