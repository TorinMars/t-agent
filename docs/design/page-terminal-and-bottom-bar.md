# The page: terminal and bottom bar

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

## Terminal on the page

- **Warm terminals** (`public/js/h5.js`, `WARM_MAX = 3`, `warm`, `showWarm`, `hideShown`, `disposeSession`). The 3 most recently shown terminals stay connected: the hidden ones keep their xterm (hidden with the `hidden` attribute, `data-terminal-id` / `data-task-id` on `.h5-xterm`) and their socket, so their output keeps arriving and switching back shows them at once (measured 1.8 ms from the click, against 9 ms plus the socket and the replay for a new one). Only the shown terminal acks, sends input and sends its size (`sendResize` and `refit` do nothing for a hidden one, so a hidden view never resizes the PTY); showing a warm one fits it and sends its size once, and opens its socket again when it was lost. Opening a 4th closes the least recently shown one. A hidden terminal that another device takes over (close 4009 / 4010) is closed without the "use it here" prompt; shown again, it connects normally and asks then. Restart and Delete also close a hidden warm view of that terminal. After 60 s on a hidden page (`WARM_IDLE_MS`) every socket is closed; the shown terminal keeps its view and connects again when the page is shown. Memory is bounded: 3 xterms with `scrollback: 5000` each. Engine switch and task change keep the terminals warm (the key is Engine, task, terminal).
- **xterm listener leak** (`disposeTerm` in `h5.js`): xterm 5.5 never disposes its screen-DPR monitor (`_core._coreBrowserService._screenDprMonitor`), which kept a window `resize` listener and a `matchMedia` listener for every terminal ever opened: 2 listeners per switch (measured: 466 to 486 after 10 switches). It is disposed after the terminal now (a private field; nothing happens if a later xterm renames it). Measured with five terminals and 10 or 30 switches: 529 listeners and 657 DOM nodes before and after. Test: `scripts/test-h5-warm-terminals-browser.cjs` (CDP `Performance.getMetrics` `JSEventListeners` after a forced GC).
- Terminal "done" ack (`h5.js`): `POST {tasksBase}/{task}/terminal/ack { terminal_id }` when a terminal is shown while the page is visible, when the page becomes visible again, when a chat over the terminal is closed, and when the shown terminal turns `done` while visible (from the pushed activity, see "Terminal activity push" under "Terminals"). Same task base as every other call, so local, Engine and proxied tasks work alike; the server ignores the ack unless the state is `done`.
- Keyboard and terminal size: when the visual viewport shrinks by more than 8px from its tallest height (the on-screen keyboard), the terminal keeps the height it had before and is shifted up (`translateY`) so its bottom rows stay visible above the keys; the top rows are clipped. The shift is capped by the cursor row (`TerminalViewport.keyboardShift`, updated on every cursor move), so a shell prompt near the top of the terminal stays visible instead of being pushed out of sight. Its size does not change, so no `resize` reaches the PTY and a full-screen program does not redraw. When the keyboard closes the terminal goes back to its place. Rotating the phone measures the full height again. iOS Safari can report the final keyboard height without a last `resize` event (for example when focus moves from the terminal to the translate box), which left a blank band under the translate row; the page therefore measures again on `visualViewport` `scroll`, on every focus change (at 0, 100, 250, 500 and 1000 ms) and every 500 ms while the keyboard is open.
- A wrong, small height reading (touch mode): a phone in iOS standalone mode was seen with the page about 200px tall, the terminal box at height 0 and the key rows right under the header; what iOS reported is not known, only that layout. A shrink now counts as the keyboard only while something that raises one has the focus (`raisesKeyboard` in `h5.js`: text inputs, textareas, selects, contenteditable and iframes, not the terminal's textarea with `inputmode="none"`, read-only fields or checkboxes and the like). With nothing like that focused the page height is `Math.max(visualViewport.height, innerHeight)`, `keyboardOpen` is false and that height is the new `fullHeight`, so a bad reading cannot look like a keyboard later and a real change (a shorter window, the Safari URL bar) is still followed. A short grace (`KEYBOARD_CLOSE_MS`) keeps the terminal pinned after a blur while a keyboard that also shortens the window (Android, `interactive-widget=resizes-content`) goes down. The same follow-up measurements (`settleViewport`) also run on `visibilitychange` to visible, `pageshow` and `orientationchange`; one schedule at a time, a new event replaces it. The chat view (`fitAgentView`) follows the same rule. A terminal box shorter than `TERMINAL_MIN_HEIGHT` (48px, about three rows) is treated as collapsed: `refit` and `sendResize` leave the size alone, so the PTY never gets one or two rows, and a size refused that way is sent once the box has room. Test: `scripts/test-h5-viewport-collapse-browser.cjs`. Real iOS behaviour cannot be reproduced in the test, which stubs the readings.
- Touch scrolling, vertical (restored after v2.90.0, which had removed the wheel strip and scrolled by a pan on the whole terminal; that vertical scrolling felt slow on a phone). The wheel strip below is the vertical scroller. A drag on the terminal body is not turned into wheel events: in the normal buffer it scrolls the history with xterm's own touch handling (`touch-action: pan-y`; xterm's `touchmove` moves `.xterm-viewport` by the finger's travel in px and cancels the event, so the browser does not scroll as well; no momentum), and in the alternate buffer (Claude Code, Codex, vim, tmux) the body does not scroll: nothing is sent to the program. Press-and-hold never starts text selection or the callout menu on the phone terminal (`user-select: none`); terminal text is copied with a double / triple tap or the copy view (see "Copy").
- Sideways pan (`public/js/terminal-gestures.js` `TerminalGestures.attach`, wired in `h5.js` `attachGestures`). One handler on each terminal element (`.h5-xterm`). A one-finger pan that starts on the terminal element (not on the strip, which is a sibling above it) picks its axis from its first 10px of travel (`axisOf`: the larger of |dx| and |dy|; an exact diagonal is vertical) and keeps it until the finger is lifted.
  - Horizontal: the wide terminal moves sideways 1:1 (see "Terminal width (Fit / Wide)" below); in Fit mode nothing moves. Only then is `touchmove` stopped (capture phase, before xterm's listener) and cancelled, so the pan does not scroll the history. Always the page's view, never sent to the program.
  - Vertical: the handler lets the touch go at once and never touches its events, so xterm and the browser see the same touch as before the handler existed: the moves before the 10px decision and after it. Moves up to the decision are not held back (holding them would let the browser start its own scroll beside xterm's: a double scroll), so a sideways pan can move the history by up to about one row while its axis is not decided yet.
  - Left alone: a touch that travels less than 10px (tap: focus, the double / triple tap selection, a file link tap; the 500 ms long press that opens the copy view, whose own 8px slop cancels it first); a second finger ends the pan; a pan while the copy view is open or right after the long press that opened it; the key row, row 2 and the header (outside the terminal element). A sideways pan never ends in a click: `touchend` is cancelled after it (no click, no compatibility mouse events, so a program in mouse mode gets no stray click) and the link and tap handlers ignore a tap within 600 ms of a sideways pan (`recentlyPanned`).
  - Position indicator (`showScroll`, `.h5-scroll-indicator`): a 3px bar at the bottom (sideways position), shown only while the user pans and faded out 0.7 s after; `pointer-events: none`, `aria-hidden`; never a control. The vertical position is the wheel strip's thumb.
  - With the strip: the strip is a sibling of the terminal element at `z-index: 2` inside `.h5-terminal`, so it is not moved by the Wide transform (it stays 2px in from the right edge of the visible box) and a pan on it never reaches this handler; in Wide mode the rightmost 42px of the box therefore scroll vertically and do not pan sideways, while the strip is drawn (`bar` or `spring`). The spring's wheel events are `.xterm-screen` wheel events with no sideways delta, which this handler leaves to xterm.
  - Tests: `scripts/test-h5-terminal-gestures-browser.cjs` (real CDP touches at 390 x 844: the strip is there, the body is `pan-y`, a body pan scrolls the normal buffer once and sends the alternate buffer nothing, axis lock of diagonal pans, a tap is no scroll, the strip in Wide mode), the pan-on-a-link case in `scripts/test-h5-file-links-browser.cjs`, the strip in `scripts/test-h5-browser.cjs` and `scripts/test-h5-wheel-stuck-browser.cjs`, the math in `test/terminal-gestures.test.js`.
- Wheel strip (a scrollbar; before it was an invisible drag strip where dragging down showed older output, which users read backwards): a 40px-wide, full-height hit area (`#h5-wheel`, drawn in `scripts/h5-shell/Terminal.jsx`, touches handled in `public/js/h5.js` `bindWheelStrip` with pointer events, so mouse and touch both work) on the right edge of the terminal, down to its bottom edge, 2px in from the screen edge so the browser edge-swipe gesture is not blocked. Touch mode only (pointer mode draws none). It is absolutely placed over the terminal's right margin, so it never changes the columns (checked in `test-h5-browser.cjs`). Only a 4px track and thumb are drawn (6px thumb while touched), dim when idle and brighter while a finger is on it (class `active`, faded out 0.7s after release); the strip keeps `touch-action: none`. Its mode is `data-mode`, set by `syncWheel` from the shown terminal's buffer:
  - `bar` (normal buffer with scrollback): thumb size = strip height x rows / (rows + `baseY`), at least 32px; thumb position = `viewportY / baseY` of the free room. Dragging the thumb is absolute, 1:1 like a desktop scrollbar: the grabbed point stays under the finger and the view goes to the matching line (`term.scrollToLine`), so down = newer, up = older. A touch beside the thumb that travels more than 8px drags too (the thumb centre jumps under the finger). A tap (under 8px and 400ms) on the track above the thumb is one page up, below it one page down (`term.scrollPages`, which moves rows - 1 lines). A tap on the thumb is handed to the element under it (links stay clickable there). There is no flick momentum: a scrollbar does not coast. The thumb follows scrolling done elsewhere: `term.onScroll`, `onLineFeed`, `onResize`, `buffer.onBufferChange`, the DOM `scroll` event of `.xterm-viewport` (xterm 5.5 fires no `onScroll` for its native scroll, which is what a drag on the body does), the terminal's resize observer, window resize, terminal switches and every store change (the strip can be re-mounted), all coalesced into one redraw per frame.
  - `spring` (alternate buffer: Claude Code, Codex, vim, tmux; the page cannot know the program's position): a 32px thumb rests in the middle, with self-drawn chevrons above and below it (`chevronUp` / `chevronDown`, 14px). A drag anywhere on the strip pulls the thumb with the finger (up to 42% of the strip height from the middle); pulled down scrolls down (newer), pulled up scrolls up (older): the same meaning as the bar. Speed grows with the pull: 8 lines per second per terminal row of pull beyond a 6px dead zone, at most 200 lines per second, counted by real time (`performance.now()`, every frame, every move, every 250ms check and on release), so slow frames do not slow it. The steps are wheel events on the xterm screen (one per line, up to 200 per step), which xterm forwards as mouse wheel reports or, without mouse mode, up/down arrows. They point at the middle of the visible terminal (the centre of `.h5-xterm`, at the strip's middle height), not at the strip: a program that scrolls the pane under the mouse (opencode, see "Mouse wheel over a program" below) has its main content there, while the strip's own x is over its right-most columns (opencode's sidebar on a wide terminal, which does not scroll the messages, so the spring never scrolled opencode). Claude Code and Codex ignore the column of a wheel report. Released, the thumb springs back to the middle (CSS transition with a small overshoot) and the scrolling stops; no momentum. A tap on the spring is handed to the element under it (a program's links stay clickable).
  - `none` (no terminal shown, or a normal buffer without scrollback): nothing is drawn, `pointer-events: none`, `aria-hidden`.
  The buffer type is read on every move: a thumb drag that meets a switch to the alternate screen becomes a spring pull from that point, and a spring pull whose program leaves the alternate screen keeps scrolling with `term.scrollLines`. Accessibility: `role="scrollbar"`, `aria-orientation="vertical"`, `aria-label` "Scroll"; in the bar mode `aria-valuemin` 0, `aria-valuemax` = `baseY`, `aria-valuenow` = `viewportY`; in the spring mode 0 / 100 / 50. Tuning constants are named at the top of the wheel code (`WHEEL_THUMB_MIN`, `WHEEL_SPRING_RATE`, `WHEEL_SPRING_DEAD`, `WHEEL_SPRING_MAX`, `WHEEL_STALE_MS`, ...). The strip never gets stuck when the browser swallows the end of a touch (an Android system gesture, an app switch, a dialog over the strip, a re-mounted strip, a second finger): a new touch on the strip always takes over from a drag that is still open (so a second finger drives and the first one is ignored); a drag ends without a tap on `lostpointercapture`, a hidden page (`visibilitychange`), `pagehide`, window `blur`, a switched or closed terminal and a strip that is no longer in the document (checked on every move and every 250 ms while a finger is down), and the spring thumb goes back to the middle; when no pointer event came for `WHEEL_STALE_MS` (3 s) the strip dims and the spring stops (a held, perfectly still finger therefore stops scrolling after 3 s; its next move brings both back); and every element that got the `active` class loses it, also an old, detached strip. Tested by `scripts/test-h5-wheel-stuck-browser.cjs` (self-healing, spring) and the wheel part of `scripts/test-h5-browser.cjs` (thumb size and position, drag direction and 1:1 follow, page taps, following native scroll and new output, hidden without scrollback, the spring's direction, speed, dead zone and spring back, tap pass-through, columns unchanged), with in-page pointer events that wait on state rather than fixed delays. It does not take focus, so the on-screen keyboard stays as it is. It exists only in the terminal view (the agent chat view covers it). A mouse wheel or trackpad over the strip (a touch screen that also has a mouse or trackpad, an iPad with a trackpad: input mode `touch` draws the strip) goes to the terminal under it at the same point (a capture `wheel` listener in `bindWheelStrip` cancels it and dispatches the same wheel to `document.elementFromPoint` with the strip ignored), so xterm scrolls or reports the cell under the pointer and a sideways wheel moves the wide terminal; before, the strip took the wheel and its 40px (the last five or six columns) did nothing. A pinch (`ctrlKey`) stays the browser's.
- Terminal width (Fit / Wide) (`h5.js` `setTerminalWidth`, `widthPref`, `refit` -> `TerminalViewport.fit(term, addon, host, minCols)`, `layoutWide`, `followCursor`). Why: programs such as Claude Code and Codex wrap their own output at the PTY's column count, so on a narrow phone one sentence becomes several real lines, which the copy view cannot join (it already joins xterm's soft wraps). Two modes, one setting per device (localStorage `h5-terminal-width` = `fit` | `wide`, `h5-terminal-wide-cols` = 200 | 500 | 1000 | 2000, default 200; a value stored by an older page (120, 160) or anything else falls back to 200, `TerminalGestures.wideCols`; not per terminal kind):
  - Fit: the columns that fit the screen (below), as before.
  - Wide: the PTY gets the chosen columns, never fewer than what fits (`columnsFor`; at most 2000, the server's limit: `routes/terminal.js` ignores a `resize` with more than 2000 columns or 1000 rows, and `TerminalViewport.fit` never asks for more); the rows still fit. An Engine older than this limit (it allowed 1000 columns) ignores a resize to 2000: its PTY keeps the size it had, so the program keeps wrapping at that width while the page lays the screen out at 2000 columns; nothing breaks, and 200 / 500 / 1000 work there as before. The `.xterm-screen` is laid out at cols x cell width and moved sideways with `transform: translateX()` inside `.h5-xterm.h5-wide` (`overflow: hidden`); xterm reads mouse, selection and link positions from that element's bounding box, which includes the transform, and the helper textarea (IME, `terminal-ime.js`) moves with it, so taps, the double / triple tap selection, file links, copy on select and the IME keep working at any offset. xterm's vertical viewport keeps the visible width.
  - Moving sideways: a one-finger horizontal pan (above); on a computer a sideways wheel or trackpad swipe and Shift+wheel (the vertical wheel stays xterm's). The cursor (where the user types) is followed: input (typing, the key row, the on-screen keyboard, a paste: every `send` except mouse reports) scrolls it into view with 4 cells of margin, and output keeps it in view while the user has not panned it away (`s.follow`: after a sideways pan or wheel it is true only if the cursor is still visible; the next input sets it again). Never during a pan. Mouse reports are not input here (`TerminalGestures.isMouseReport`: SGR, urxvt and X10 reports, also several in one chunk): a wheel step, a click or a motion report points at a cell the person sees, so it leaves the view where it is. Before, every report counted as typing: opencode turns on any-motion reports (1003), so after Shift+wheel had moved the screen to the right, the next mouse move or wheel sent the view back to opencode's input box on the left, and the wheel on the right side seemed to do nothing.
  - Mouse wheel over a program (opencode 1.19.6, checked with the real binary in a temp home under node-pty and @xterm/headless): opencode turns on 1000, 1002, 1003 and SGR 1006 and scrolls the pane under the reported cell. On a terminal wider than about 120 columns it draws a sidebar of about 42 columns on the right (title, context, LSP); a wheel report over the sidebar scrolls nothing, the same in any terminal. Over the message pane, up to its last column, it scrolls the messages. The page reports the cell under the pointer in every layout: pointer Fit and Wide at any offset, the columns view, a mouse wheel over the strip; the strip's spring reports the middle of the visible terminal. Test: `scripts/test-h5-tui-wheel-browser.cjs` (real terminal routes and PTY, a fake TUI that shows the last wheel report and the motion count it read).
  - Switch, computer: the `#h5-term-width` button in the page header (library `column-width`, `aria-pressed` while Wide, blue while Wide; `aria-label` = `title` says the current width, "Terminal width: Fit to screen" / "Terminal width: 200 columns"). One tap toggles Fit / Wide (Wide with the chosen columns). A long press (500 ms; the menu opens from the click that follows the lift, on the button before the menu's backdrop exists, or 400 ms after the lift when the browser sends no click; opening it on pointerup let that click hit the new backdrop and close the menu) or a right click opens `#h5-term-width-menu` (`WidthMenu` in `Header.jsx`): Fit to screen, 200 / 500 / 1000 / 2000 columns, radio items (`menuitemradio`, `aria-checked`) with the current one ticked (Ant Design `check`) and selected.
  - Switch, phone: the app bar has no room for it (see "Session header" in [page-navigation.md](page-navigation.md)), so it is the first item of the header's More menu while a terminal is shown (not a notebook): `#h5-term-width`, "Terminal width: Fit to screen" / "Terminal width: 500 columns" with the `column-width` icon (blue while Wide) and a › (`treeChevron`). It replaces the More menu with the same `#h5-term-width-menu` at the same place, starting with a Back row (`#h5-term-width-back`, back to the More menu) and a divider; one tap on a choice sets it and the focus goes back to More. No toggle and no long press on the phone. The copy view shows `#h5-copy-wrap-hint` "Lines are wrapped at N columns" with a "Widen terminal" button while the terminal is in Fit mode and narrower than 100 columns, so the user can switch where the problem is seen.
  - Only new output changes: text that is already hard-wrapped stays wrapped (full-screen programs such as Claude Code redraw on the resize). The first switch on a device says so in a notice.
  - Several viewers: unchanged. The server lets one client own a terminal at a time (close 4009 / 4010, `terminal-owner.js`) and only the shown terminal of that client sends its size (`sendResize`); hidden warm terminals never resize the PTY and refit with the current setting when shown. So the PTY always has the width of the device that uses it now; taking a terminal over on another device resizes it to that device's mode.
  - Cost of a wide screen (measured in headless Chromium at 390 x 844 x3, xterm 5.5 DOM renderer, 40 rows, 13px, a full 5000-line history): drawing a full screen of text and one step of the sideways pan stay within two animation frames (about 33 ms, the measuring floor) at 80, 200, 500, 1000 and 2000 columns; the resize itself takes about 23 / 37 / 65 / 118 ms at 200 / 500 / 1000 / 2000 columns, and the history grows the page's memory by about 11 / 29 / 54 / 112 MB (xterm keeps every line at the full width). The server's snapshot (`lib/terminal-snapshot.js`, 500 lines) grows the same way, about 12 MB per terminal at 2000 columns. So 2000 columns stays usable; its price is memory, not drawing.
  - Tests: `scripts/test-h5-terminal-gestures-browser.cjs` (the copy view hint and Widen to 200, the first notice, the phone's More > Terminal width ticking the current width and setting 500 / Fit / 500, PTY resize to 200 / 500 / back to fit, a 150px pan moves 150px, clamping at the right end, diagonal lock, output does not pull a panned-away view back, input brings the cursor back, output past the right edge is followed, remembered after a reload, Shift+wheel and a sideways wheel at 1440 x 900), `scripts/test-h5-phone-header-browser.cjs` (the phone's item and list: label, ›, tick, Back, Escape, 2000 and 500 columns reaching the socket, the screen wider than the view; the computer's button name and ticked menu, 1000 columns), `test/terminal-gestures.test.js` (columns, the choices and the fallback of 120 / 160 to 200, offset clamp, follow offset, axis lock, hint), `test/terminal-viewport.test.js` (`minCols`, at most 2000), `test/terminal-multiple.test.js` (the server takes 2000 columns and ignores 2001 columns or 1001 rows).
- Terminal width (`TerminalViewport.fit` / `columns` in `public/js/terminal-viewport.js`, called by `refit` in `h5.js`, local and remote terminals alike): FitAddon gives the rows; the page counts the columns itself as the most columns whose drawn screen (`Math.round(cols * cell)`, xterm's glyph width from `_charSizeService`, fallback the drawn screen divided by the columns) fits the host width less the room a scrollbar really takes now (`offsetWidth - clientWidth` of `.xterm-viewport`). An overlay scrollbar (phones, macOS) takes nothing; a classic one keeps its width, read live, so a scrollbar change after start is followed. Why: xterm 5.5 measures the scrollbar once and uses 15px when it measures 0, and FitAddon took that off, so a phone lost 2 to 3 columns (about 20 to 30px blank on the right; 58 instead of 61 columns at 412px). Now less than one cell stays blank. The column count does not depend on the current columns (0.05px slack for a layout width just short of a pixel), so it never flips and a size change is one PTY resize. Limitation: xterm's DOM renderer places glyphs with letter-spacing that Chrome keeps in 1/64px steps, so a long row may end up to cols/64 px past the screen (about 2.5px at 180 columns, inside the 4px margin or over a classic scrollbar). Regression: `scripts/test-terminal-width-browser.cjs` (360/393/412px at x2.625 and x3 touch, 1280/1440px pointer with and without a classic scrollbar), `test/terminal-viewport.test.js`.
- Cell grid (`public/css/h5.css`, `.h5-terminal .xterm`): xterm's DOM renderer draws each row as text and keeps it on the cell grid with a letter spacing it computes from a measured glyph width, while the mouse, the selection and the links use the grid itself. The measuring element inherits text styles from the page, so the terminal resets what would change a glyph's width: `letter-spacing` and `word-spacing` (the body has the 0.15px letter spacing of MUI's body1; inherited, it made every row 0.15px per column narrower than the grid, 2 to 3 characters at column 130, so a mouse selection ended left of the pointer; fixed in v2.136.1), and Chrome's CJK punctuation trimming and autospacing (`text-spacing-trim`, `text-autospace`). Test: `scripts/test-terminal-selection-browser.cjs` (the body's styles, long ASCII and CJK lines, a real mouse drag, DPR 1 and 2).
- Copy text: the phone terminal blocks text selection (the wheel strip and drag scroll), so a long press on the terminal body or the "Copy text" item of the terminal actions menu (the "⋯" of the open terminal's row in the task drawer; not shown for other terminals) opens a full-screen overlay with the terminal buffer as plain text (`buffer.active` lines, wrapped lines joined, trailing blank lines dropped; the whole scrollback in the normal buffer, only the screen in a full-screen program). The overlay uses the terminal's font and size (12px on a phone, 13px on a computer) with no letter spacing (it would otherwise inherit MUI's 0.15px and a full-width row would scroll sideways), 4px side padding and `white-space: pre`, so one terminal row is one line and the layout matches the terminal. The text is `user-select: text`, so the browser's long-press handles work; `Copy all` uses `navigator.clipboard.writeText` and falls back to selecting the text and `execCommand('copy')` on plain HTTP. Rows that soft-wrap are joined without losing a space in the last cell of the wrapped row (only the end of a logical line is trimmed). The view is live: while it is open, new output refreshes the text (debounced 400 ms, the scroll position is kept, and the view follows the bottom when it was at the bottom). If the user holds a text selection in the view, the text is not replaced; a "New output" chip appears and refreshes on tap. A search box under the title bar (Enter or "Next match") jumps to the next match, wrapping around, and marks it with the CSS Custom Highlight API (browsers without it select the match instead). A long press (500 ms, cancelled by more than 8 px of movement, a scroll or a lifted finger) on the terminal body opens the same view at the bottom; the key bar is not affected. The long press handles touch and pen only: a mouse never starts it (the pointerdown handler returns early for `pointerType === 'mouse'`, so xterm keeps its own selection), so the menu item is the entry for mouse users. There is no floating copy button any more.
- Select on the terminal (touch): a double tap selects a word and a triple tap selects the whole logical line (wrapped rows included) with xterm's own selection (`term.select` / `term.selectLines`; `user-select: none` stays, xterm draws the highlight), and copies it at once (see "Copy" below). A single tap elsewhere and any new output clear the highlight. It works only while the program is not tracking the mouse (`term.modes.mouseTrackingMode === 'none'`), so vim, tmux and Claude Code always receive the taps. Only touch and pen input is handled here; a mouse keeps xterm's own selection. The tapped cell is computed from the bounding box of `.xterm-screen` (which includes the 4px inset, any scale and the keyboard shift) divided by the column / row counts; the second half of a wide (CJK) character counts as the character. A double or triple tap on a file link selects and copies, it does not open the file. Limits: a word that wraps over two rows is cut at the row end; not tried on a real phone.
- Apple Chinese keyboard: xterm 5.5 ignores an `insertText` input event that is `composed` and follows a keydown, which is how iOS types a space, punctuation or a number with the native Pinyin keyboard, so those characters never reached the shell. `public/js/terminal-ime.js` (`TerminalIme.attach`) watches the terminal root in the capture phase and, 40 ms after such an event (a single space, punctuation mark, symbol or number, not composing), sends the character unless xterm emitted it in the meantime, so nothing is typed twice. Letters and composed text stay with xterm. A key press that had a `keypress` event is left alone: xterm sends a plain Space (keyCode 32, below its keydown range) and Option or AltGr characters on keypress without cancelling the key, so the browser's `insertText` input event comes after xterm has already sent the character, outside the 40 ms check. Tests: `test/terminal-ime.test.js`, `scripts/test-h5-space-key-browser.cjs` (one character per key press); not verified on a real iPhone.
- **Auto-paired punctuation of input methods**: WeType on macOS answers one press of `"` with the whole pair “” in one insertion and then a Left arrow key that puts the caret between the two. In xterm that broke three ways: the Left key reached the program (Claude Code draws its block cursor on ”), it arrived before the pair (xterm sends keyCode-229 text from a `setTimeout` diff of its helper textarea, the Left key at once), and the caret moved inside the helper textarea, so the next diff (`newValue.replace(oldValue, '')`) sent more than was typed (“”“”, “！”！“”). `public/js/terminal-ime-pairs.js` (`TerminalImePairs.attach`, capture-phase listeners on the terminal root, so they run before xterm's on its textarea) turns a full-width pair inserted in one go (“” ‘’ （） 《》 〈〉 「」 『』 【】 〔〕 ［］ ｛｝, `insertText`, not composing) followed by a plain Left key within 100 ms (`PAIR_WINDOW_MS`) into ONE character and drops the Left key. Quotes alternate per terminal: the first press gives “ (‘), the next ” (’), double and single quotes each on their own, starting again after an Enter, Ctrl+C or Ctrl+U sent from any path (`observe`, called by `send` in `h5.js`); brackets give the opening one only (the person types the closing one as before). The pair's `beforeinput` is cancelled, so the textarea never holds it; where it cannot be cancelled the `input` event is kept from xterm and the pair is taken back out of the textarea, and the caret is put back at the end. A Left key never overtakes the text of an input method's key: after a keydown with keyCode 229 or a `compositionend` whose text xterm has not sent yet (xterm sends it from 0 ms timers, which run late on a busy page; seen as ESC[D before a committed word), a plain Left key within 100 ms is kept from xterm and held (its ESC[D, or ESC O D in application cursor mode). Keys pressed after it queue behind it (data emitted while a keydown is dispatched, `window.event`). When the text comes (any data not from a key dispatch, through `forward`, which all of xterm's data and `TerminalIme`'s go through) it is sent first, then the held Left and the queue; when the pair comes instead (WebKit may deliver the Left key before the pair), the Left is dropped and the character is sent; after 100 ms without either the Left and the queue are sent. A Left key after the text arrived is ordinary and goes to xterm at once. Known limit, xterm's own and unchanged: a letter typed on a busy page right after a composition commit, before xterm's timers ran, makes xterm finish the composition at once from a stale end position (`_finalizeComposition(false)` in its CompositionHelper), which can send old text and the letter before the word. Unchanged: a pair without a Left key (a paste, which is `insertFromPaste`, or an input method that does not move the caret) is sent as it is, 100 ms later; an ordinary Left key is sent at once; a pinyin composition, an Enter that confirms a candidate, the page's own keyboard and the draft box are not touched. - **Send rules** (`submitBox(translateFirst)` in `h5.js`): the send arrow (`sendTyped`) sends the text exactly as typed: nothing trimmed or joined, line breaks as carriage returns; text with a line break or a tab, or longer than 200 characters (`PASTE_LINE_CHARS`), is one bracketed paste when the program has that mode on (`term.modes.bracketedPasteMode`, as Claude Code does), otherwise it is typed key by key. Only control characters a keyboard cannot type (C0 except tab and line breaks, DEL, C1, ESC) are dropped, so a text cannot end the paste early. Translate-and-send uses `POST /api/translate` (the translator keeps the lines) and writes the result with the same paste rule; when the translation fails nothing is sent and the text stays. Both are followed by one Enter after 120 ms. **Translation next to existing input** (the owner's rule, `sendTranslation`): when the terminal's input line already holds text, the translation goes on a new line after it and the same Enter then sends the whole input: with bracketed paste on, ONE paste of a carriage return plus the translation (`\x1b[200~\r...\x1b[201~`; Claude Code, Codex and zsh take a pasted line break as a new line in the input, not a submit); without it a line break would make a shell run the line, so a space and the translation (lines joined) are typed instead. An empty input line is unchanged: the translation, then Enter. The send arrow is not affected. The page cannot read a program's input buffer, so `public/js/terminal-input-line.js` (`TerminalInputLine.read(term.buffer.active)`, a pure function over the xterm buffer, `test/terminal-input-line.test.js`) reads the screen: the cursor row (`baseY + cursorY`) and its soft-wrapped rows (`isWrapped`) form the line, which must start with a prompt marker, and only what follows the marker counts. Markers: Claude Code `❯` (U+276F) and, boxed in older versions, `>`; Codex `›` (U+203A); shells the first `$ `, `% `, `# ` or `❯ `. The space after a marker is any whitespace cell, the no-break space U+00A0 included: Claude Code 2.1.323 draws its pointer as `❯` + U+00A0 (read from the installed binary, its prompt's mode indicator), and while only `" "` was accepted its input line was never recognised, so text already on it (typically the link the page types after an image upload) was read as empty and the translation went onto the same line and was sent with it. Claude Code and Codex draw multi-line input as separate rows, so when the cursor row has no marker the rows above are searched for a TUI marker, never past a horizontal border (the top of Claude Code's input box) and at most 40 rows; rows below count up to the box's closing border (Claude Code), otherwise only soft-wrapped ones (Codex keeps footer hints below its input). Box borders, padding and a right prompt at the end of the row are not text. Placeholder hints are not text: dim cells (SGR 2), palette color 8 (zsh-autosuggestions), and an inverse cell followed by a dim one. The installed Claude Code 2.1.322 draws its placeholder as `invert(first letter) + dim(rest)` with the `❯` pointer in a box with only top and bottom borders, and Codex 0.167.1 carries the `› ` prefix (read from the installed binaries; Codex's dim placeholder is from its public TUI source, not checked on a real screen). Limit: screen reading can be wrong. A line it cannot understand (no marker, the cursor on a border) counts as empty. A wrong "empty" sends the translation right after the existing text on the same line (the old behaviour); a wrong "has text" only adds one extra line break before the translation. `scripts/test-h5-translate-append-browser.cjs` checks both paths in real Chromium, including an image uploaded with the key bar (OSS mocked: the link plus a trailing space goes in as one bracketed paste) followed by a translation, on a desktop and at a phone's width where Claude Code breaks the link over several rows. A short line (at most 800 bytes of UTF-8, one PTY read) stays keys, so `/command` and `!` at the start still act as typed; a longer unbracketed line would be taken by Claude Code as a paste of its own ("[Pasted text #1]"). The draft box restricts no input (no `maxlength`, platform keyboard defaults) and stays editable while a translation runs; after a send only the sent text leaves the box. It grows with its text up to half of the visible viewport (whole lines, never below two), scrolls inside beyond that, and goes back to one line when it loses focus (the text stays). Voice input never sends by itself.
- Paste (`paste` in `h5.js`, `TerminalClipboard.readClipboard` in `terminal-clipboard.js`) makes exactly ONE clipboard read per tap, started synchronously in the tap's click handler (no await before it): WebKit, so Safari and every iOS browser including Chrome for iOS, allows a read only inside the user gesture and shows its "Paste" callout for each read; a tap elsewhere dismisses the callout and rejects the read. The page used to call `read()` for an image and then `readText()`, so on an iPhone the second read had no gesture left and always failed ("the browser denied clipboard access"). Now `read()` is preferred: the first image of the items goes to the upload, else `text/plain` of the same items goes through `term.paste` (bracketed paste kept); `readText()` is used only when `read()` does not exist, never after a refused `read()`. A second tap while a read is pending is ignored. When the read is refused, the callout is dismissed or there is no clipboard API (plain HTTP also shows "Paste needs HTTPS or localhost…"), the **Paste sheet** opens (`PasteDialog` in `Dialogs.jsx`, `state.pasteSheet`): a box at the top of the screen (so the on-screen keyboard does not cover it) with the hint "Long-press here and choose Paste", Cancel and Send. The system's own paste into the empty box is sent at once; typed text, or a paste next to other text, waits for Send; pasted images or files (up to 9) go to the upload. Closing it gives the focus back to the element that had it (usually the terminal's textarea). A native paste into the terminal's own textarea (iOS long-press on the terminal, Paste; Cmd+V on a computer) is xterm's own paste (text, once) or the upload (file items, `paste` listener on the terminal element). Test: `scripts/test-h5-paste-browser.cjs`. Image and file upload: see "Image and file upload (OSS)"; the link (several links joined by spaces) is typed into the original terminal with a trailing space and no Enter, or shown for copying when that terminal went away.

## Compact bottom area of a column

In a column of the multi-column view (pane mode, `state.pane`) the bottom area is ONE row instead of the draft box and the two rows (`CompactBottom`, `CompactTools`, `DraftPeek` in `scripts/h5-shell/Terminal.jsx`; `#h5-bottom[data-compact]`). Four columns used to draw four big inputs and 28 large round buttons, about 110 to 150px each, though only one column is used at a time. The single view's computer row is built from the same components (`CompactTools` in its `single` mode, see "Bottom bar"); the column keeps its own `column` mode, unchanged by it.

- **One row, one height.** `#h5-row` is 52px (56px in touch input mode), plus the 1px divider above it, in every column, focused or not. Nothing in it changes the layout when the focus moves: the buttons of an unfocused column are hidden with `display: none` inside the fixed row, so the terminal box, its rows and columns and the PTY size never change (`scripts/test-h5-pane-composer-browser.cjs` counts the resize messages). The buttons stay mounted: `h5.js` and `voice-input.js` hold the DOM nodes of `#h5-voice`, `#h5-image-picker`, `#h5-translate-button` and the form from the start.
- **The focused column** (`state.paneFocused`, see "Pane mode" in page-shell-and-columns.md for how the pane knows) shows, from the left: the draft box (`#h5-translate`, a 36px pill, 44px in touch mode, taking the free width; a 2px primary ring while it has the focus), Upload image or file (`#h5-image`, the same label around the real file input as on the page), Voice input (`#h5-voice`), More tools (`#h5-more`, "⋯", `aria-haspopup="menu"`, `aria-expanded`, `aria-controls`) and Translate and send (`#h5-translate-button`, a contained primary button with the send icon and the text "Send", `aria-label` "Translate and send", the title with its key). Icon buttons are 36px with a mouse and 44px in touch input mode.
- **More tools** (`#h5-more-menu`, a MUI Menu opening upward, list labelled "More tools") holds every tool that has no button of its own here, each doing exactly what its button does on the page: Saved commands (`#h5-more-commands`: the same list, `CommandsList`, with Paste text and the presets), Docs (`#h5-more-docs`: `ui.actions.openDesign`), Next running or pending session (`#h5-more-cycle`: `ui.actions.nextActiveSession`; its name ends with the count and a small count pill shows it), a divider, Send as typed, without translating (`#h5-more-send`: the form's `requestSubmit`, the same submit as the send arrow and Option/Alt+Enter; disabled while a translation runs; the key is shown on the right), and in touch input mode Terminal keyboard (`#h5-more-keyboard`, `menuitemcheckbox`). A chosen item runs after the menu closed (`setTimeout` 0), so the focus the menu gives back to "⋯" does not take it from where the action put it. While some sessions run or wait, "⋯" carries the same count as a badge and its name becomes "More tools (N)". The Docs entry of the saved commands list (`#h5-commands-docs`, for narrow phones) is left out there.
- **Keys of the draft box are those of the page**: Enter from a hardware keyboard translates and sends, Option/Alt+Enter sends as typed, Cmd/Ctrl+Enter and Shift+Enter insert a new line, an IME Enter is left alone (`keydown` on `#h5-translate-input` in `h5.js`, unchanged).
- **Unfocused columns** show only the quiet draft box: a fainter surface and the placeholder in the disabled text colour, no buttons. A press anywhere in the column, or the focus coming into the draft box (Tab from the top page), makes it the focused column and the buttons appear. A column with an unsent draft shows a small outlined "Draft" tag and the draft on one line, cut with an ellipsis (`#h5-draft-peek`, `aria-hidden`; the textarea keeps the text and is only made transparent under it), never the placeholder. `h5.js` publishes the draft's one-line form as `state.draftPeek` (`autosize` → `publishDraft`, pane mode only, at most 300 characters); only `DraftPeek` reads it, so typing draws nothing else. A press on the tag goes through to the textarea, and the whole draft is there again.
- **Multi-line drafts grow upward over the terminal**: the row is `align-items: flex-end` with a fixed height, so the draft box, growing with its text (`autosize`, up to half of the visible height, then it scrolls inside), overflows above the row. The layout never changes: `syncBar` counts only the growth beyond one line as `--h5-bar-extra` in a column (`COMPACT_ROW`) in both input modes, and `holdTerminalSize` moves the terminal up by it, never resizes it (no negative margin on `#h5-bottom` here, and no clip animation of the row, which would hide the box while it grows). A column that is not the focused one keeps its box on one line (`restingColumn()`: a window that lost the focus keeps its active element, so the focus alone cannot tell); the box grows again when the column is focused and the box has the focus. Chosen over a box that scrolls inside one line: the person sees what they type, and the terminal keeps its size.
- **States kept visible**: the buttons of a column stay shown while its voice input records (`.h5-voice.listening`) or its translation runs (`#h5-translate.translating`), also after the focus moved to another column, so the red pulse, the disabled send buttons and the pulsing box are never hidden. A translation that ends in a column the person left sends its text but does not take the focus back to that column (`submitBox` focuses the terminal only in the focused column).
- **Touch input mode** (a landscape tablet): the row is 56px, every button and the draft box at least 44px, More tools items 48px. The function keys (row 1) and the terminal's on-screen keyboard come from More tools > Terminal keyboard: the keys above the row and the keyboard below it, taking room in the layout as on the page (one refit when shown, one when hidden, never when the focus moves; the keyboard stays until it is turned off). Everything is reachable without hover. The draft keyboard key is not needed: the draft box is always shown.

## Next running or pending session

- The single view's switch button (`#h5-cycle`) opens the session switcher: see [session-switcher.md](session-switcher.md). The action below stays for a column of the multi-column view, as its "More tools" item (`#h5-more-cycle`).
- Next running or pending session (`ui.actions.nextActiveSession` in `h5.js`). Each call closes the on-screen keyboard (blurs the focused input) and goes to the next session of a cycle; the terminal is not resized beyond what normal switching does.
  - Members: only terminal sessions, that is plain shell terminals ("Terminal" in the task sheet, `agent` null) and the Claude / Codex terminals the app creates ("Session", `agent` `claude` / `codex`). Agent chats, their sub-agent views, documents and other rows are not members.
  - Running: the server's terminal activity state is `running` (`GET {activityBase}/terminal-activity`, the `lib/terminal-activity.js` signal), or the terminal has at least one running sub-agent (`GET {activityBase}/terminal-subagents`). Pending acceptance: the activity state is `done` (finished, not yet seen; showing the terminal acknowledges it). `activityBase` is `/api/tasks` locally and `/api/remote-servers/:id` for a remote Engine.
  - Running sub-agent (`runningSubagents` in `lib/agent-sessions.js`, `subagentSnapshot` in `routes/terminal.js`): only for a Claude terminal whose shell is alive and that is bound to a session (`task_terminals.agent_session_id`). Claude Code writes each sub-agent of session `<id>` to `~/.claude/projects/<task dir>/<id>/subagents/agent-<x>.jsonl`. A sub-agent runs while the last complete line of that log is not the final assistant message (`stop_reason` `end_turn` / `stop_sequence`) and the log changed in the last 15 minutes (a sub-agent killed with its parent never writes the final line). Read only: the session id and file names are checked, symbolic links and non-files are skipped, only the last 64 KiB of recent logs is read. Codex terminals have no sub-agent information. The home directory is the service user's, as for the session names.
  - Order: the task sheet order (the tasks in the shared list order, see "Task order", then the terminals of each task in `GET …/terminals` order). Both states come from the pushed activity stream while it is live, else they are read fresh on the tap. `state.activeCount` counts the members that are running or pending (tasks of the list only, the same set the cycle goes through); a column shows it as the badge on "⋯" and the pill of the item. The cycle starts after the current terminal and wraps; when the current one is not a member (or a chat is shown) it goes to the first. Empty: the notice "No running or pending sessions". Only the current one: "This is the only running or pending session". An Engine without `terminal-subagents` (older versions) still cycles by activity state.
  - Switching uses `ui.actions.openRow` with a terminal row, the same path as a tap in the task sheet (task selection, terminal attach, header names and remembered state stay right).
