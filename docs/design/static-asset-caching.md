# Static asset caching

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

Scripts and styles are named by their content (single-page load work, after v2.87.13; `lib/static-assets.js`, `test/static-asset-cache.test.js`, `test/static-asset-combine.test.js`, `scripts/test-h5-assets-browser.cjs`):

- **Content-hash URLs, long cache only for the exact hash.** `sendClientPage` rewrites every `/js`, `/css` and `/vendor` script or style of a page to `<path>?v=<first 16 hex digits of the SHA-256 of the file>`. A request whose `v` is the file's current hash gets `Cache-Control: public, max-age=31536000, immutable`; every other request (a plain URL, the old `?v=<app version>`, a wrong or an outdated hash, icons, manifests, `sw.js`) keeps `no-cache` (`sw.js` is sent by its own route with the hash of the offline files written in, `lib/service-worker.js`; its cache holds only the offline page, [failover-and-one-login.md](failover-and-one-login.md)) and is revalidated with its ETag (a `304` when unchanged). Any change to a file (a release, an update, a local edit without a version bump) changes its URL in the next page, so a client never runs a stale script; this is why v2.84.26 dropped the old version-based long cache (a file could change without a new version) and why the hash, not the app version, is used now. The hash is cached per file and recomputed when its size or modification time changes. The pages themselves stay `no-store` (login redirect). The login page (`routes/auth.js`, `sendFile`) is not rewritten.
- **Files loaded later get the same long cache.** `rewritePage` also puts one small inline script before the page's first style sheet: `window.TAAssets` (the hash of every script and style under `/js`, `/css` and `/vendor` that the page does not load itself, about 640 bytes today) and `window.TAAsset(path)`, which answers `<path>?v=<hash>` or the plain path for a file it does not know. Every lazy loader builds its URL through it: the chat bundle `agent-chat-ui.js` and `agent-chat.css` (`public/js/agent-chat.js`), `mindmap-ui.js` (`public/js/mindmap.js`), marked, `markdown.css` and mermaid (`scripts/h5-shell/Design.jsx`), and the Chinese dictionaries that `i18n.js` fetches itself. The chunks of the ES module bundles are not in the map (below). Without `TAAsset` (a page not served through `rewritePage`, as in most browser tests) the plain path is used and revalidated each time. Before this the chat and mind map loaders swapped the file name in their own `src`, so they sent the hash of `agent-chat.js` / `mindmap.js` and always got `no-cache`, and the Design loader sent no hash at all. The list of files is read at most every 5 s; the page's only Content-Security-Policy is `frame-ancestors`, so the inline script runs (a `script-src` policy would have to allow it and the combined parts below).
- **Small page scripts in one request.** Consecutive `<script defer src="/js/….js" data-combine></script>` tags of a page (two or more, only white space between) become one tag `/js/combined-<12 hex of the paths>.js?v=<hash of the combined content>`, built in memory (no build step, no minifier) and rebuilt when a file's size or modification time changes; it is cached and compressed like a file (gzip at build, brotli in the background queue, ETag `"<hash>-<coding>"`, `304`, `HEAD`; a range request gets the whole body). The combined script carries each file unchanged as a string and runs them in page order, each as a classic script element of its own (`script.text = source`, appended to the head and removed again), so top-level `const` / `let` / `function` stay global and shared as with separate tags, a file's exception or syntax error is reported and the files after it still run, `'use strict'` stays inside its file, and `//# sourceURL=<origin><path>` gives each part its own name and line numbers in stack traces and the debugger. What differs: `document.currentScript` is the part's element (no `src`; its `data-src` has the path), and microtasks queued by one part run after the whole run instead of between parts. `h5.html` marks 20 files in two runs (`i18n.js`, `toast.js`, `client-auth.js` in the head; the 17 helpers from `terminal-owner.js` to `mindmap.js` after the shell); `toast.js` and `client-auth.js` moved before the Chinese dictionaries for this (neither reads `I18n` when it runs). Not marked: the shell, `h5.js`, the vendor scripts and the dictionaries. A marked file must not read `document.currentScript.src` (`test/static-asset-cache.test.js` checks this). The files are still served one by one. The server registers the runs of `h5.html` at start, so a combined URL is known after a restart.
- **Chunks of the ES module bundles** (`public/js/chunks/<name>-<HASH>.js`, "Page bundles and chunks"): the modules import each other by those plain names (no `?v=`), and the name carries esbuild's hash of the content, so `cacheControl` answers `immutable` for a year for any file of that folder whose name ends in `-<8 capitals or digits>.js` (`isChunk`); they are compressed like every script and are left out of `window.TAAssets`. For each `<script type="module" src="/js/….js">` of a page, `rewritePage` reads the static `import` statements at the top of the file (followed through the chunks; a dynamic `import(` is not one; read again when the file changes) and puts a `<link rel="modulepreload" href="/js/chunks/…">` before the tag for each, so the browser fetches the shell and its chunks at once instead of one after another.
- **Chat style sheet with the chat.** `agent-chat.css` is no longer a render-blocking link of the page: `agent-chat.js` loads it together with the bundle (inserted right after `h5.css`, where its link was, so the cascade order is unchanged) and mounts the chat only when both have arrived (no unstyled chat; a failed load is tried again by the next chat). The agent marks drawn outside the chat (`.agent-logo`, `.agent-chat-mark`, `.agent-chat-bubble`) moved to `h5.css`; no other class of `agent-chat.css` is used outside `.agent-chat` (the word-translate popup only opens from a chat).
- **Measured** (`scripts/test-h5-assets-browser.cjs`'s setup, headless Chromium, real HTTP server, brotli copies ready; page plus scripts and styles of the first load): English 28 requests / 460 KB sent before, 10 requests / 450 KB after; Chinese 31 / 520 KB before, 13 / 509 KB after. A later visit asks for no script or style again, the lazy ones included (before, `agent-chat-ui.js` 280 KB brotli, `mindmap-ui.js`, marked, `markdown-view.js`, `markdown.css` and mermaid 5.5 MB raw were revalidated on every visit that used them).
- **Pre-compressed copies.** For `/js`, `/css` and `/vendor` scripts and styles, `staticAssets.precompressed` answers with a brotli (quality 11) or gzip (level 9) copy chosen from `Accept-Encoding` (`br` first; a coding with `q=0` is not used), with `Content-Encoding`, `Vary: Accept-Encoding`, an ETag `"<hash>-<coding>"` and the same `Cache-Control` rule. The copies are made in the background, one file at a time (Node's own `zlib`, no new dependency), for the files of `h5.html` and `index.html` at server start and for any other file the first time it is asked for; they live in memory (at most 48 MB, files up to 8 MB) next to the file's size and modification time, so nothing is written to the app directory or `~/.tagent`. Until a copy is ready, and for range requests, the `compression` middleware compresses on the fly as before. Brotli 11 is too slow for every request (about 1 s per MB), which is why it is done once; doing it at release time would add build output to the repository. Measured on the 28 files of `h5.html` (1412 KB raw): about 357 KB in brotli 11, 428 KB in gzip 9 and 429 KB with the middleware's default brotli.
- **Chinese dictionaries only for Chinese.** `i18n.js` keeps the language in the cookie `ta-lang=zh` as well as `localStorage['ta-lang']`; `sendClientPage` leaves the three `i18n-zh-*.js` scripts out of the page when the cookie is not there, so English readers skip three requests and about 44 KB (brotli 11). Switching the language writes the cookie before the reload, so the next page comes with them. A Chinese reader without the cookie yet (the first load after this change) gets the page without them: `i18n.js` then fetches them itself and translates the page again when they arrive.
