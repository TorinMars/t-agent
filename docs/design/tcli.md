# tcli (agent command line)

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

`tcli` (`scripts/tcli.js`, Node built-ins only, `bin` entry `tcli`) is the command line that Claude / Codex sessions in T-Agent terminals use for T-Agent features that need a server-side credential. It talks only to the T-Agent that started its terminal; that server makes the real calls, so no cloud key is ever in the session's environment or process. Commands are grouped (`tcli <group> <command>`, a small command table `GROUPS` in the script): `oss` (below), `browser` (`scripts/tcli-browser.js`, see "Browser extension"), `site` (`scripts/tcli-site.js`, see "Site library") and `notify` (`scripts/tcli-notify.js`, below); a group in its own module gets the script's HTTP and error helpers and runs its commands itself (`run(command, args, ctx)`). Code: `scripts/tcli.js`, `routes/tcli.js` (relay and Engine routes), `services/oss-files.js` (the bucket operations), `services/oss-agent-settings.js` (the switch), `lib/terminal-relay-auth.js` (the terminal credential, shared with the peer file relay).

- **Environment.** Every shell T-Agent starts with a known hook endpoint has `TA_HOOK_URL`, `TA_HOOK_TOKEN` and `TA_TCLI` (the absolute path of this install's `scripts/tcli.js`; set in `hookEnv` of `routes/terminal.js` and listed in `HOOK_ENV_KEYS`, so an inherited value is dropped). tcli calls `/api/tcli` on the origin of `TA_HOOK_URL` with its `task` and `terminal` query parameters and the token in `X-T-Agent-Task`, `X-T-Agent-Terminal` and `X-T-Agent-Token`. Without these variables it exits 2 with "tcli works inside a T-Agent terminal". The agent skill runs it as `node "$TA_TCLI" ...` (falling back to `tcli` on the PATH).
- **Relay** (`/api/tcli/oss/*`, `createTcliRelayRouter`). Mounted in `server.js` next to the peer file relay, before the body parsers, the session and the gates, so an upload is streamed as it comes. It takes a request only when it carries one of the `X-T-Agent-*` headers and comes from this machine (the same rule as the peer file relay: a loopback address or the server's own address, and no `X-Forwarded-For`, `Forwarded` or `X-Real-IP`); anything else goes on untouched. Missing headers: 401 `TCLI_AUTH_REQUIRED`; a wrong token, another terminal's token or an unknown task: 403 `TCLI_AUTH_INVALID`; an unknown route under `/api/tcli/oss`: 404 `UNKNOWN_ROUTE`. The stored configuration read is the single user's (`ensureSingleUser().login`), the one the Settings page shows.
- **Switch.** "Agent sessions can use OSS with tcli", one per Engine, on by default: `system_state` row `oss_agent_access_v1`, `{ enabled }`. `GET /api/oss/agent-access` → `{ enabled }`, `PUT` with `{ enabled: bool }` → `{ enabled }` (400 `VALIDATION_FAILED` otherwise), behind the browser login and same-origin rule like the other OSS settings. Off: the relay and `/v1/oss/files` answer 403 `OSS_AGENT_ACCESS_OFF`. The page's own image and file upload is not affected.
- **Bucket.** The bucket of "Image and file upload" (`services/oss-images.js`; `openClient(owner)` gives an ali-oss client and the non-secret parts of the configuration, or null when upload is not enabled → 409 `OSS_NOT_CONFIGURED`). Keys are relative to the bucket root (the upload prefix is not added): 1 to 1023 bytes of well-formed UTF-8, no leading `/`, no `..` segment, no control characters (400 `INVALID_KEY`).

**Routes** (the relay and the Engine routes have the same shapes; errors are `{ error, message }`, with `oss_code` when OSS gave one):

- `GET list?prefix=&delimiter=&marker=&max=` → `{ objects: [{ key, size, last_modified, etag, storage_class }], prefixes, next_marker, truncated }`. `delimiter` is `/` (default) or empty (recursive); `max` 1 to 1000 (100).
- `GET stat?key=` → `{ key, size, last_modified, etag, content_type, content_disposition, meta }`; 404 `NOT_FOUND`.
- `GET object?key=` → the bytes with `Content-Type`, `Content-Length`, `ETag`, `Last-Modified`, `X-Content-Type-Options: nosniff`; an object over 2 GiB is 413 `TOO_LARGE`.
- `PUT object?key=` → `{ key, etag, size, content_type, url, url_expires_at }`: the raw body, streamed to OSS with `putStream`. The size comes from `Content-Length` or `?size=` (the tunnel of a service link drops `Content-Length`); neither is 411 `LENGTH_REQUIRED`, both and different is 400; the bytes must match it (400 `INCOMPLETE_BODY` when fewer arrive). At most 1 GiB per object (413 `TOO_LARGE`): ali-oss multipart upload needs a file or buffer, not a stream, and one PutObject is enough for agent files. The content type is the request's when it is a plain, harmless MIME type; types a browser would run or render as a page from the bucket's domain (HTML, SVG, XML, JavaScript, CSS ..., the `ACTIVE_TYPE` rule of the page upload) and anything malformed are stored as `application/octet-stream`. The type is always sent, so the SDK never guesses it from the key. `url` is the public address when one is set (each key segment percent-encoded), else a signed GET URL valid for an hour.
- `POST copy` `{ src, dst }`, `POST move` `{ src, dst }` (copy, then delete the source; the same key is 400). A copy of an object stored with an active type gets `application/octet-stream`, its disposition and metadata kept.
- `POST remove` `{ keys: [...], confirm: true }` → `{ deleted, failed }`: 1 to 1000 keys with `deleteMulti` (OSS also reports a key that did not exist as deleted); without `confirm: true` 400 `CONFIRM_REQUIRED`.
- `POST sign` `{ key, expires = 3600, method = 'GET' }` → `{ key, method, url, expires_at }`: 60 to 604800 seconds, `GET` or `HEAD` only (a signed PUT would bypass the active-content rule).

**Secrets.** The AccessKey secret stays in the ali-oss client inside the server. Upstream error messages are never passed on (some repeat the request, the AccessKey ID and the signed string): only the OSS error code (letters and digits, such as `AccessDenied`) is kept, as `502 OSS_REQUEST_FAILED` with `oss_code`; a missing object is 404 `NOT_FOUND`. A signed URL names the AccessKey ID in `x-oss-credential`, as the page's upload links do; the ID is not a secret.

**Linked provider.** When this Engine has no OSS of its own (upload not enabled) and `services/linked-capabilities.js` `providerFor('oss')` gives a linked service, the relay sends the call to that service's `/v1/oss/files/*` with the link's token (`services/remote-client.js` for JSON, a streamed `http` / `https` / tunnel request for `object` GET and PUT, `tunnel://` included). The provider must list `oss:files` in `/v1/info` (checked before the first call and remembered for a minute); without it 501 `OSS_FILES_UNSUPPORTED`. An own configuration always wins. The provider's own agent-access switch applies, and its answers with the codes above pass through with `provider` (its name) added; no answer is 502 `LINKED_PROVIDER_OFFLINE`, a refused token (401 / 403 without an OSS code) 502 `LINKED_PROVIDER_UNAUTHORIZED`. Uploads stream on both transports with backpressure: on a direct link through the socket, through a service link tunnel through the stream's credit (see "Service links: tunnel"), so the limit is 1 GiB there too and memory stays at about one window per hop. Through a tunnel the relay first checks the provider's announced body limit (`requestBodyLimit`): a provider on a T-Agent from before streamed tunnel bodies takes 64 MiB, and a larger upload is 413 `TOO_LARGE` ("... takes at most 64 MiB per object; update T-Agent there ...") before anything is sent; a tunnel that is down is 502 `LINKED_PROVIDER_OFFLINE`. When the terminal goes away mid-upload the relay destroys the provider request, the provider sees an aborted body and stores nothing. Downloads through the tunnel stream the same way, up to 2 GiB. `/v1/oss/files` (`createOssFilesEngineRouter`, behind `requireEngineAuth('engine:admin')`, which a service link's token has) only uses the provider's own bucket, so calls never chain; `server.js` keeps the global body parsers off it (`OWN_PARSERS`) so an upload of any type is streamed. It holds no tasks, so per-task visibility does not apply.

**Notify** (`tcli notify`, `scripts/tcli-notify.js`, relay `routes/tcli-notify.js`; tests `test/tcli-notify.test.js`). An agent session tells the user something ("the long build finished", "I need you to decide X") on the notifiers set up in T-Attention, through `sendDirect` of `services/attention-notify.js` (see "Direct messages" under "T-Attention notifiers").
- Relay `/api/tcli/notify` (mounted in `server.js` after the site relay, with the same terminal credential and this-machine rule, before the body parsers and the gates; a body of at most 16 KB, 413 `PAYLOAD_TOO_LARGE`): `POST` `{ text, title?, via?: ['telegram', 'email', 'widget'] | 'all', link? }` → 200 `{ results: [{ notifier, outcome, detail?, via? }] }` when at least one notifier was tried; 409 `NOTIFY_NOT_CONFIGURED` "No notifier can send messages. Set up Telegram or email in Settings → T-Attention" when no selected notifier is switched on and set up (or relayed through a linked sender); 403 `NOTIFY_AGENT_ACCESS_OFF` when the rules switch `agentMessages` is off; 400 `TEXT_REQUIRED`, `TEXT_TOO_LONG` (over 3000), `TITLE_TOO_LONG` (over 200), `INVALID_TITLE`, `INVALID_LINK`, `INVALID_VIA`, `INVALID_REQUEST`. `GET /status` → `{ agentMessages, quietHours: { enabled, start, end, timeZone, active }, notifiers: [{ name, label, enabled, ready, via? }] }` (also while the switch is off).
- `from` is made on the server, never taken from the body: "<task title> · <terminal name>" (the name `listTerminals` shows: the person's name or the agent session's). The link is the page under the rules' `publicUrl` (`<publicUrl>/`; the page has no address of one terminal yet) unless the command gives `--link`; without a `publicUrl` there is none.
- CLI: `tcli notify <text...>`, `tcli notify -` (stdin), `--file F` (`-` is stdin too), `--title T`, `--via telegram,email,widget` (default all), `--link URL`, `--json`; `tcli notify status`; `tcli notify -- status` sends the word. The text is checked first (empty, over 3000 characters, two sources: exit 1). One line per notifier: `telegram  sent`, `telegram  relayed through T01 (sent)`, `email  skipped: quiet hours`, `email  failed: <detail>`. Exit 0 when at least one was sent or relayed and sent there; 1 for usage, 409 or when everything was skipped (quiet hours, duplicate, limit), with "do not try again" on stderr; 2 outside a T-Agent terminal or the switch off; 4 for the server, the network, or when every attempt failed. The send waits up to 90 s (a relayed message may take 45 s on the sender).

**tcli attention** (`scripts/tcli-attention.js`; tests `test/tcli-attention.test.js`). Every command of `t-attention` ([attention-cli-and-listener.md](attention-cli-and-listener.md)) under tcli, with the same arguments, output and exit codes: the group calls `main()` of `scripts/t-attention.js` with `name: 'tcli attention'`, so help, hints and error messages say `tcli attention` and the two commands cannot drift apart (a new t-attention command is in tcli at once). It does not use the tcli relay or `TA_HOOK_*`: credentials are t-attention's (`TA_ATTENTION_URL` and `TA_ATTENTION_TOKEN` in a T-Agent terminal, the terminal's own token; elsewhere `tcli attention login` or `pair`), so it also works outside a T-Agent terminal. The group's `run` gets `env` in its context from `main` of `scripts/tcli.js`. What a terminal's token may not do stays refused by the server (a script action: 403 `SCRIPT_NEEDS_PERSON`, exit 2); the person-only routes of the page (CLI tokens, pairing codes, summary and guide settings, plugin settings) are not in the CLI.

**CLI.** `tcli oss ls [prefix] [--recursive] [--all] [--max N] [--marker M]` (`--all` follows `next_marker` up to 10 000 objects), `stat <key>`, `get <key> [-o <file>|-] [--force]` (default `./<last key segment>`; an existing file needs `--force`; written to `<file>.tcli-part-<pid>` and renamed when complete, checked against `Content-Length`; `-o -` writes the bytes to stdout), `put <file> [key] [--prefix P] [--content-type T]` (default key: the file name; the type from the name when not given; prints the key and the URL), `cp <src> <dst>`, `mv <src> <dst>`, `rm <key...> --yes` (without `--yes`: exit 1), `url <key> [--expires S]` (the URL on stdout, its expiry on stderr), `tcli help`, `tcli oss help`. `--json` prints the server's JSON (an error as JSON on stderr). Human output fits a phone-width terminal. Exit codes as `t-attention`: 0 ok, 1 usage or another 4xx, 2 not in a T-Agent terminal or 401 / 403, 3 404, 4 5xx or network (and `rm` with keys OSS did not delete). Metadata calls time out after 30 s; transfers have no time limit once the answer has started; progress is shown on stderr when it is a terminal and the file is over 8 MiB.

**Reading recordings** (`tcli browser record items` and `record requests`; `scripts/tcli-browser-records.js`, the filters and the merge in `lib/browser-recording-query.js`, used by both the server and tcli; tests `test/browser-recording-query.test.js`, `test/browser-recordings.test.js`, `test/browser-ext-routes.test.js`, `test/tcli-browser-cli.test.js`). A recording is one JSON line per item (`services/browser-recordings.js`); the network kinds are `request` (a summary when it starts, status 0), `response` (the same `req_id` when it finished, with the redacted request and response headers and bodies) and `ws` (a WebSocket frame, by URL); a redirect is a `response` of the old hop (3xx) followed by a new `request` with the same `req_id`. Items that tcli commands caused carry `source: 'agent'`; an item without one counts as the person's (`user`). A recording follows the tabs and windows the recorded page opens (popups, `target=_blank`, `window.open`; at most 10 tabs): they join the same recording id, every item carries `tab` (the same as `tab_id`, which older recordings have alone), and an opened tab starts with a `{ kind: 'tab', action: 'opened', tab, opener, url }` item (`action: 'closed'` when it goes). `record show` adds a `tabs` line (`<tab> (<n> items)`, from the summary's `tabs: { "<tab id>": count }`, at most 20 ids) when more than one tab recorded.
- `record items <id>` filters: `--kind` (a comma list of item kinds: `request`, `response`, `ws`, `click`, `input`, `change`, `submit`, `key`, `nav`, `dom`, `console`, and any later kind; `net` stands for the three network kinds), `--type` (the resource type of network items, any case: `XHR,Fetch,Document`), `--source agent|user`, `--url` (a substring, or `/regex/` with the flags `imsu`), `--status` (`200`, `4xx`, `400-499`, `0` for no response yet; comma lists), `--tab T` (the items of one tab: `tab`, else `tab_id`), `--limit N`, `--offset N` (after the filters). A filter on a field leaves out the items without that field (`--type` keeps only network items). Output as before: JSON lines on stdout, `-o file` (written to a part file and renamed; `--force` overwrites).
- `record requests <id>`: one entry per request (per hop of a redirect), in the order they started: `req_id, seq, method, url, type, status (null without an answer), mime, size, duration_ms, started_at, finished_at, from_cache, failed, tab_id, source, request { headers, post_data }, response { headers, mime, size, body | body_base64, body_truncated }, timing, initiator, redirected_from, redirected_to, ws_frames (a WebSocket's frame count), missing ('response' when the recording has only the request, 'request' when only the response)`, redacted as stored. Script, Stylesheet, Image, Font and Media requests are left out unless `--all`; `--type` keeps exactly the types it names. `--url`, `--status`, `--tab`, `--limit`, `--offset` as above, on the merged requests (`--tab` on its `tab_id`). Default output: one line per request (`r7 POST 201 Fetch 1.2 KB 31ms body 9 B (no response)  https://...`; it starts with `tab <id>` when the lines shown come from more than one tab), then how many static files were left out; `--json` prints JSON lines, `-o file` saves them.
- Relay: `GET /api/tcli/browser/recordings/:id/items` without a query sends the file as it is (what older tcli asks for); with `kind`, `type`, `source`, `url`, `status`, `tab`, `limit` or `offset` the server reads the file line by line and sends only the matching lines, with `X-T-Agent-Filtered: 1`. `GET .../requests?type=&all=1&url=&status=&tab=&limit=&offset=` merges on the server and answers JSON lines with `X-T-Agent-Left-Out: <static files left out>`. A value it cannot use is 400 `BAD_FILTER` (tcli checks the same rule first: exit 1). Against an older T-Agent tcli does the work itself: it filters an items answer without `X-T-Agent-Filtered`, and on `UNKNOWN_ROUTE` for `requests` it merges the whole items file, so the output is the same. `--tab` is applied by tcli again (to the items when the answer was filtered, to the merged requests), since a T-Agent from before it ignores the parameter.
- Which to use: `record requests` to learn a site's API (what was called, with what, and what came back); `record items --kind click,input,submit,nav` (with `--source user` for what the person did) for the steps of an action; `record items --kind dom,console` for what the page showed or complained about.

**Browser status** (`tcli browser status`). The default text is the connected browser (paired name, id, extension version, browser), "connected since" and "paired" times and the method count, and the other paired browsers with their online state. `--json` prints a slim answer: `{ protocol, connected, active_browser_id, method_count, browsers: [{ browser_id, name, version, browser, online, active, paired_at, connected_at, last_seen_at, methods (a count), recent_event_count }] }`. `--verbose` adds the method names and the recent tab events (the text), or prints the relay's whole `GET /api/tcli/browser/status` answer (`--json --verbose`). The slimming is done by tcli; the route is unchanged. Exit 0 when a browser is connected, 4 when not.

**Browser tabs, focus and closing** (`scripts/tcli-browser.js`; the rules are "Focus and closing" in [browser-extension.md](browser-extension.md)). `tcli browser open <url>` opens the tab in T-Agent's own Chrome window behind the person's, never taking their focus; `--active` shows it (and focuses that window); `--keep` sends `keep: true`, so it is not closed after the agent's turn, and prints "It stays open after your turn: tell the person it is there". `--record` opens a separate new window for the recording, in front (`window: 'front'` in `tabs.open`), because the person usually acts in the page, and prints "Opened a new window in front for the recording: the person can use the page while it records."; `--record --background` opens its own window unfocused (`window: 'back'`), for a recording the agent drives itself, and prints "Opened its own window in the background for the recording."; `--background` without `--record` is a usage error (exit 1). A plain `open` sends no `window` and goes into the shared background window. An extension without the `open.window` feature refuses `window` with "reload it in chrome://extensions" (`PARAM_FEATURES` in `services/browser-bridge.js`). A tab the recorded page opens (the extension's `tab.opened`) is closed by the same rules as its opener: the tab care gives it the opener's terminal, or none (30 minutes unused only) when the opener is a handed tab. `activate` is for when the person asked to see a page; `shot` needs no activate. The agent's tabs close by themselves 2 minutes after its turn ended (when no command used them since), when its terminal closes, or after 30 minutes unused; a tab the person activates, clicks or types in becomes theirs. A result's `dialogs` (page dialogs the extension answered) are printed on stderr, one `dialog: <type> "<message>" (accepted|dismissed)` line each, also with `--json` (where they are in the answer too). `tabs` marks a kept tab `[group, keep]`. `status` adds a line when the connected extension is older than T-Agent's folder (`extension_version` of the status answer, also in `--json`): "T-Agent has extension X: it reloads itself from 1.0.5 on; reload it once in chrome://extensions if it stays at Y". `tcli browser help` (and `--help` on any browser command) lists all of it. Tests: `test/tcli-browser-cli.test.js`.

**Site entry format** (`tcli site schema`). `ENTRY_SCHEMA` in `services/browser-sites.js` is the one description of a site entry (fields, types, required, limits, a description each) and `ENTRY_EXAMPLE` a valid entry; `buildEntry` validates against the schema, and `tcli site schema` (text, or `--json` `{ schema, example }`) and the "Entry format" part of `tcli site help` print it, so they cannot disagree. `site schema` reads this install's code and needs no T-Agent terminal (a `local` command in `scripts/tcli.js`). A save or edit that is not valid reports every problem in one error: `INVALID_SITE` (or `SITE_TOO_LARGE` when every problem is a size), the message "The entry has N problems (the entry format: tcli site schema):" with one "field: problem" line each (one problem: one line), and `problems: [{ field, problem }]` in the JSON answer (at most 50).
