# Update check and versions

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

- **Version source**: `VERSION.json` in the install directory is the runtime version (`app_version`, `api_version`, `schema_version`, `min_remote_api_version`, `max_remote_api_version`, `published_at`, optional `release_url`); `package.json` and `package-lock.json` carry the same `app_version` (`scripts/release.js` sets them together). `GET /api/system/version` returns the version, the `boot_id` and the remote API range. The field rules are under "D. Data storage".
- **Check** (`services/update-manager.js`, `lib/version-utils.js`): the server reads `VERSION.json` of the configured branch on GitHub over HTTPS (only `raw.githubusercontent.com` / `api.github.com`, checked again after a redirect; 10 s timeout, 16 KiB body limit, ETag / Last-Modified reused on 304). It never runs Git for a check. The first check runs shortly after start, then every `config.updateCheckIntervalMs`; one check runs at a time. `app_version` is compared as strict SemVer: higher = `available`, equal = `current`, lower = `local_newer` (no downgrade), and `restart_pending` when the code on disk is newer than the running process. With `restart_pending` the state also has `restart_target`, what a restart would load: the HEAD commit (Git, when changes between the start commit and HEAD need a restart) or the `app_version` on disk (archive, when it differs from the version read at start-up); null when HEAD cannot be read. The browser cannot pass a URL, remote, branch or command.
- **Apply** (`POST /api/system/apply-update { confirm: true[, force: true] }`): a global update lock; Git installs fetch, check that the target branch has the checked version, that the branch is not ahead or diverged, and that tracked files are clean (`git status --porcelain --untracked-files=no`; untracked files do not block, `git merge --ff-only` refuses a same-named conflict by itself), then fast-forward; archive installs replace the files (`services/archive-updater.js`). A dirty work tree blocks the update with `WORKTREE_DIRTY` and lists the files; only a forced update (offered after that block) backs local changes up to a Git stash. Before the change a timestamped SQLite backup goes to `~/.tagent/backups/`. Then `npm ci --omit=dev --ignore-scripts=false` and the node-pty check, and the process exits with code 75 so PM2 (or launchd / systemd) starts the new code; a frontend-only change skips the install and the restart (`lib/update-impact.js`). On a failure the new version is not started and the log says what to do.
- **What an update installs**: only `dependencies`, like `install.sh` (`npm ci --omit=dev`), about half of the packages of a full install. The dev dependencies are the tools that build the page bundles and run the tests; the bundles under `public/js` are committed, so an update builds nothing (`esbuild` and `highlight.js` are dev dependencies). `test/production-dependencies.test.js` scans the `require` / `import` of every production file (the server, `db`, `lib`, `middleware`, `plugins`, `routes`, `services`, and the scripts under `scripts/` that are not build, test or release tools) against `package.json`, both ways: a production file must not need a dev dependency, and `dependencies` must not list a package no production file needs. The service must start with the dev dependencies present as well as absent, because the update that brings a release in is run by the code of the version before it (up to 2.130.0 that code installed everything). A checkout that is also developed in keeps them with npm's own setting `npm_config_include=dev` in the service's environment, which wins over `--omit`.
- **Update log** (`lib/update-command.js`): two places. Every line goes to an in-memory buffer (the latest 300 lines, `log` of `update-status`), which the Update dialog shows. npm runs at the `http` log level (`NPM_UPDATE_ENV`), so every download gives a line: the progress text shows the latest one, and "no output for 30s" tells a stalled download. The service log (stdout, the PM2 log) gets stage starts and ends with their durations, warnings and errors (`printable`: npm lines by their level, `warn` and `error`; other output by its words), and the last 2000 characters of a command that fails; a `Finished` line says how many progress lines it left out. The Git commands of a version check that is not part of an update are `quiet`: nothing is printed unless one fails. Before this, one `npm ci` printed about 660 `npm http` lines and one check about 14 lines.
- **T-Agent.app after an update** (macOS): the update itself never builds the app. When the restarted server finds an installed `~/Applications/T-Agent.app` whose shell code (the `TAgentSourceHash` in its Info.plist) differs from the new source, it rebuilds and reinstalls it in the background about a minute later (`services/mac-app-autobuild.js`; off with `TA_MAC_APP_AUTOBUILD=0`). See "Automatic rebuild after an update" in [mac-app.md](mac-app.md).
- **Status**: `GET /api/system/update-status` gives the stage, log lines and `boot_id`. Remote Engines are updated through `/api/remote-servers/:id/check-update|apply-update|update-status` (`services/remote-engine-updates.js`). The page side is the Update dialog (see "Settings, Devices and Update" under the page). The Update dialog also updates the connected services together with this machine, and Settings can restart this machine's service ("Update and restart" under "Settings, Devices and Update").
- **Restart without an update** (`POST /api/system/restart { confirm: true }`, `lib/server-restart.js`, wired in `services/update-manager.js`): admin only like `apply-update` (403 `UPDATE_ADMIN_REQUIRED`) and behind the same session and same-origin gates; 400 `CONFIRMATION_REQUIRED` without `confirm: true`; 409 `NO_PROCESS_MANAGER` when `detectSupervisor` finds no PM2, launchd or systemd (the same rule as `auto_update.supported`, because exit 75 with no supervisor ends the service for good); 409 `UPDATE_IN_PROGRESS` while `applyPromise` is set. Otherwise it answers 202 `{ accepted: true, boot_id }` with the current `boot_id`, logs one `[update] ... [restart]` line and exits with code 75 about 750 ms later, as at the end of an update; a second request before the exit schedules nothing more. From then until the exit no update starts, since the exit would cut `npm ci` or the merge off halfway: `POST /api/system/apply-update` answers 409 `RESTART_PENDING` (and `apply()` itself refuses without saving a state), and the automatic update skips its ticks (`restartPending` of `createAutoUpdate`). The exported `restartPending()` is also true while an automatic restart is being prepared (below), so `apply-update` answers 409 `RESTART_PENDING` then too. Every PTY ends and the in-memory terminal text is lost, and a chat turn in progress ends too. The page keeps that `boot_id` and reloads once `/api/system/version` or `/api/system/update-status` answers with a different one. Both GET answers carry `restart: { supported, reason: 'NO_PROCESS_MANAGER' | null }`, so the page offers the button only where it works. There is no `/v1` twin: a remote Engine is not restarted from another machine.
- **Release rule**: raise `app_version` before releasable code reaches `main` (clients only see `VERSION.json` on `main`); change `api_version` and the remote range only for an incompatible `/v1` change, and raise `schema_version` for every SQLite schema change.

## Automatic update (`services/auto-update.js`, `lib/update-idle.js`, `lib/update-supervisor.js`)

- **Rule**: about once a minute (an unref'd timer, and right after a check or when the switch is turned on) while the status is `available` or `restart_pending`. `available` goes first (its update restarts anyway when it needs to). `restart_required === false` is applied at once with no idle gate. Otherwise every reason from `idleBlockers` must stay empty for `config.updateAutoQuietMs` (`UPDATE_AUTO_QUIET_SECONDS`, default 600); any reason resets the wait, and the reasons are read once more right before the update. `force` is never passed. A manual update just takes the existing `applyPromise` lock. A quiet window counts for one action only: one started for an update starts again for a restart.
- **Restart for code already on disk** (`restart_pending`, for example after a manual `git pull` or an update that failed after the merge, so the old process serves new page files): the same idle gate and quiet window as an update that needs a restart, then `restartForPending` in `services/update-manager.js`. It takes its own lock (`restartPromise`, counted by `isApplying` like `applyPromise`), checks once more that `restart_target` is still what a restart would load (otherwise it does nothing and counts nothing: `stage: 'stale'`), runs `npm ci --ignore-scripts=false` as `runApply` does when `git diff --name-only <start commit> HEAD -- package-lock.json` is not empty (Git only), then `verifyNodePty`, and asks `lib/server-restart.js` for the exit, releasing the lock in the same synchronous step. So `pending()` blocks updates for the last 750 ms, and the exit is code 75 as for the Restart button. When `npm ci` or node-pty fails, the service is not restarted: the status goes back to `restart_pending` with `error`, and that target is given up with the code in `last_error`. `UPDATE_IN_PROGRESS` / `RESTART_PENDING` (something else got there first) are not failures. Loop guard: `update_auto.restart = { target, count, last_at, boot, restarted, gave_up, last_error }`, saved before the restart starts; at most 2 automatic restarts per target (`MAX_RESTARTS`), at least one quiet window apart. A later process that still finds the same target pending after the second one gives up with `RESTART_DID_NOT_HELP` (for example a commit that is not read right); a new target starts a new count. A `restart_pending` with no `restart_target` is left to a person.
- **What a restart costs**: every PTY ends and the in-memory terminal text is lost. A chat turn in progress ends too.
- **Reasons** (`{ code, count }`, independent, so one terminal can appear under two): `terminal_running` (state `running`, running sub-agents, or an agent stopped at a question for the person: `awaitingAnswer`, the hook event `attention`), `terminal_program` (the foreground is not the shell and cannot be brought back), `chat_running` (`agentChat.activity()`: running turns and queued messages of every person), `recent_input` (`lib/terminal-recent-input.js`, noted where input reaches the PTY and in `services/remote-terminal-proxy.js`; resizes and other control frames do not count). Because `recent_input` is itself a reason, the quiet window starts only after that input has aged out: up to twice the window after the last key.
- **Resumable agent** (`agentResumable` in `routes/terminal.js`): the row's `agent` must be the program in the foreground, the row must have `agent_session_id` (a Codex session is bound first, as `reopenCommand` does), and that id must be in `listSessions` for the directory a new shell will use. An id with no session file does not count: `reopenCommand` would start a fresh session. A person's own `claude` in a plain terminal has no row and blocks.
- **Snapshot**: `updates.setIdleProbe(fn)` is called in `server.js`, so the update manager requires neither the terminal nor the chat module. With no probe, or when it throws, nothing restarts (`last_error` `IDLE_PROBE_UNAVAILABLE` / `IDLE_PROBE_FAILED`).
- **Failures**: attempts are saved per version in `system_state.update_auto` before the update starts. `WORKTREE_DIRTY`, `BRANCH_DIVERGED` and `NO_GIT_CHANGES` stop it for that version at once; others retry at most 3 times, at least one check interval apart. A newer `remote_version` starts a new count. The update that was allowed to skip the gate re-reads the target; if that now needs a restart, it throws `AUTO_RESTART_REQUIRED`, which is not a failure, and the normal wait starts.
- **Supervision** (`lib/update-supervisor.js`): `process.exit(75)` with no supervisor ends the service for good, so `supported` is false (`NO_PROCESS_MANAGER`) unless one is proven. The environment is inherited by anything started in a terminal of a supervised service, so each check also looks at how this process was started: PM2 `pm_id` plus its IPC channel (and not `autorestart=false`); systemd `INVOCATION_ID` plus a parent named `systemd`; launchd a parent of pid 1 and a real `XPC_SERVICE_NAME` (a Terminal gives `0` or `application.*`). `UPDATE_CHECK_ENABLED=false` is `CHECKS_DISABLED`.
- **State**: `update_auto` is its own row, so nothing that resets `update_state` touches it: `{ enabled, shared, attempts, restart, last_auto_version, last_auto_at, last_auto_action, last_auto_boot }`, default enabled.
- **One switch for every engine**: "Update automatically when idle" is the person's one choice, so `enabled` travels with the settings sync (group `update-auto`, [settings-sync.md](settings-sync.md)); the attempts, restarts and history stay on each machine, which updates itself under its own idle rule. Only a switch set with this version or later is shared (`shared: true`, set by `POST /api/system/auto-update` and by a value from a linked engine): a value from before and the default are kept where they are and never sent, so the first sync after the update turns automatic updates neither off nor on anywhere (two engines that differed keep differing until the switch is used once). A value from a peer goes through the running scheduler (`applySync`), which logs "Auto update turned on (from a linked device)" and looks at once, as the switch does. The Update dialog shows the switch as before; turning it off there turns it off on every linked engine. `last_auto_*` is written once the update reaches `restarting` or `completed`, or once the automatic restart is accepted, before the process exits. `last_auto_version` is the version that runs afterwards (for a restart, the version on disk), `last_auto_action` is `update` or `restart`, and `last_auto_boot` is the `boot_id` of the process that ended itself for it (null for an update with no restart).
- **API**: `publicState().auto_update` is `{ enabled, supported, unsupported_reason, state: off|unsupported|idle|waiting|applying|gave_up, action: update|restart|null, waiting_for, quiet_until, last_error, last_auto_version, last_auto_at, last_auto_action, last_auto_boot }`; `quiet_until` is null while a reason blocks. `action` says what `waiting`, `applying` or `gave_up` is about; the page says "Will restart at about …" / "Waiting to restart: …" for `restart`. `POST /api/system/auto-update { enabled }`: 403 `UPDATE_ADMIN_REQUIRED`, 400 `INVALID_AUTO_UPDATE`, otherwise the update status plus `is_update_admin`.
- **Limit**: the last look is before the update starts. `npm ci` can take a minute or two, and work started in that time ends with the restart.

## When engines run different versions

Yesterday's case: T01 stayed four versions behind for hours (its automatic update waits for idle terminals) while K01 had updated, and the features that sync between engines were silently out of step. The rule ("One experience on every device and engine" in `AGENTS.md`): what cannot behave the same everywhere says so on the page. Code: `services/version-skew.js`, `routes/system.js`, `routes/engine-v1.js`, `scripts/h5-shell/VersionSkew.jsx` (chunk `screen-skew.jsx`), `UpdateDialog.jsx`, `LinkedUpdates.jsx`, `Engines.jsx`.

- **What is out of step.** The set is this engine and its online linked engines, each with the version and the capabilities of its `/v1/info` (read through the link, at most every 5 minutes per link, again a few seconds after a link changes; an engine that does not answer is not compared). An engine is **older** when another one of the set runs a newer version (SemVer). What it lacks is every **shared capability** of a newer engine that it does not list. Shared capabilities are those whose features keep something the same between engines (`SHARED_CAPABILITIES`: `settings:sync`, `learn:sync`, `page-state:sync`, `task-order`, `updated-notice`, `notify:relay`, `environment:tools`; a new sync adds its capability there). `/v1/info` also sends the list as `shared_capabilities`, so an older engine learns the names of capabilities it does not know yet; an engine that sends none is read with this engine's list. Only capabilities the newer engine really lists count (a sync switched off there is not shared). The same version with different capabilities (a configuration difference) is not a version skew. Nothing is stored: it is all in memory.
- **Page API.** `update-status` carries `version_skew`: null, or `<instance id>@<version>` for each engine that lacks something, joined by commas, from the cache only (a stale entry is read again in the background), so the first screen needs no request of its own. `GET /api/system/version-skew` -> `{ newest, engines: [{ id ('local' | link id), instance_id, name, version, self, older, missing: [capability] }] }`, by name; it waits for stale entries (4 s per engine).
- **Banner** (top of the task list, below its title; not in a pane of the multi-column view): the updater keeps `version_skew` as `state.versionSkew`; while it is set, the task list draws the lazy banner, which reads the details again whenever the value changes. One MD2 banner (MUI `Alert`, warning) per engine that lacks something: "T01 runs an older version (v2.141.2). Learn progress and Recent sessions and layout are not in step with it until it updates." The capabilities it knows are named with short phrases (`PHRASES`: `learn:sync` Learn progress, `page-state:sync` Recent sessions and layout, `settings:sync` Shared settings, `task-order` Task order, `updated-notice` Update notices, `notify:relay` Notification sending, `environment:tools` Environment compare), joined by `Intl.ListFormat` in the page language; an unknown capability is not named, and when none is known the sentence says "Some things shared between engines are not in step with it until it updates." "Update" (text button at the bottom right) opens the Update dialog; the close button (top right) closes it for that engine and version: `version-skew-closed:<instance id>` = the version in the shared page state, so it is closed on every device and engine and comes back for another older version. It disappears by itself once the versions agree. The first screen holds only the slot (a selector and the lazy component, about 600 bytes); the banner is the chunk `screen-skew`.
- **Nudge** ("an engine that updates tells its linked engines to check at once"). Whenever this engine reads an online linked engine on an older version that lists `update:nudge`, it sends `POST /v1/update/nudge` (link tokens only, 403 `LINKED_ONLY` for another token) once per link and peer version in 6 hours (again at the next read after a failure). The peer answers 202 `{ accepted, checking }` and only starts its own forced check, at most one a minute however many peers nudge; its "Update automatically when idle" switch and its idle rule decide whether and when it restarts. An engine that updated restarts, its links come back, it reads its peers and nudges the ones behind, so they follow within minutes instead of at their next scheduled check. An older peer without the capability is skipped.
- **Update all** (the Update dialog): see "Update and restart" in [page-files-and-settings.md](page-files-and-settings.md). Each engine is asked with `POST /api/system/update-when-idle { confirm: true }` (this machine) or `POST /api/remote-servers/:id/update-when-idle` -> `POST /v1/update/when-idle { confirm: true }` (admin tokens, capability `update:when-idle`; an older engine answers 404, which the page gets as 501 `UPDATE_WHEN_IDLE_UNSUPPORTED`). The engine checks, then `auto.request()` marks the update as asked for: the automatic update applies it under the same idle rule and quiet window even when its switch is off (`auto_update.requested`, and `state` is then `waiting` / `applying`, not `off`). The answer is the update status plus `requested` (false: nothing to update). 409 `AUTO_UPDATE_UNSUPPORTED` with `reason` (`NO_PROCESS_MANAGER`, `CHECKS_DISABLED`) where the service cannot restart itself. The request lives in memory: the update it asks for ends the process; it is dropped when nothing is left to update, and a restart without it falls back to the switch. The switch itself and how it is stored (`update_auto`) are unchanged.
- **Settings → Devices**: a row whose version is lower than the newest version of the list (this machine's and the `remote_version` of every row) has the pill "Older version" (warning, beside the status and "Company computer").
- **Limits.** Only online engines are compared (an offline one cannot be out of step until it is back, and the Offline mark already says so). A plain remote Engine (not linked) is not read for the banner and is not nudged; it still has the Devices pill. A page left open sees a new skew within its next minute poll.

Tests: `test/version-skew.test.js` (the comparison, the flag, the cache and link changes, nudges once per version and not to an older or newer peer, the receiver's one check a minute), `test/version-skew-routes.test.js` (`/v1/info`, the nudge's link-token rule, update when idle here, over `/v1` and through a remote row, an older engine's 501, the page's read), `test/auto-update.test.js` ("Update all" with the switch off, nothing to update, no process manager, a restart for code on disk), `scripts/test-h5-update-linked-browser.cjs` (the banner, its phrases, Update, closed everywhere for a version and back for the next, no chunk without a skew, Update all; `H5_SHOT_DIR` for 390px and 1440px screenshots).

## Automatic refresh after an update

- The on-disk `VERSION.json` is already the new version when the code is merged, and before the old process exits `/api/system/version` also returns the new version number, so the version number cannot be used to decide that "the restart is done".
- Every service process generates a `boot_id` at start-up (`update-manager.bootId`), returned with `/api/system/version` and `/api/system/update-status`. Before clicking update the page reads the current `boot_id` once (the return value of `apply-update` is `{ accepted, status }` and it is taken from there as well), and refreshes as soon as a different `boot_id` is read after the restart.
- Fallback: the old process exits about 0.75 seconds after writing `restarting`, so once the page has seen `restarting` for more than 4 seconds (`RESTART_GRACE_MS`) any successful response comes from the new process and it refreshes directly, without depending on one particular poll hitting the outage and without requiring the version number to equal the target version. An old service without `boot_id` treats a successful response after an observed outage as the new process as well.
- If it still has not refreshed after waiting for more than 20 seconds, a "Refresh now" button is shown; closing the dialog does not interrupt the polling.
- **Silent refresh after an automatic update** (`UpdateButton`, `scripts/h5-shell/Update.jsx`): the page records `boot_id` and `local_version` of its first `update-status` read. A later read with a different `boot_id`, a different `local_version` and `auto_update.last_auto_version` equal to the new `local_version` reloads the page once, with no dialog or banner; a plain restart or the manual flow does not match. An automatic restart may keep the version, so the page also keeps the `boot_id` of its last read and reloads when a read with another `boot_id` has `auto_update.last_auto_boot` equal to it: the process it last talked to ended itself automatically. A manual restart (`pm2 restart`, the Restart button) leaves `last_auto_boot` naming an older process, so it does not match. The manual flow (`monitor()`) does its own reload, and this path stands aside while it runs. The reload waits while the person is busy (the page is hidden, a dialog, sheet, menu or the copy view is open, the agent chat is open, the translate box has text, a focused field has text, or a translation or upload is running), is tried again every second and on `visibilitychange`, and runs the same steps as the Refresh button (`ui.actions.refresh`). Each version (or, after an automatic restart, each new process: the key `boot:<id>`) is reloaded at most once per tab (`sessionStorage`); without `sessionStorage` the page does not reload. After a read fails with no answer or a 5xx, the page reads every 3 seconds, for at most 5 minutes, until the service is back; a page that becomes visible reads at once. The reload returns to the saved Engine, task and terminal (`localStorage`, see the end of `public/js/h5.js`); an open agent chat, sheet or scroll position is not restored, which is why those count as busy.

## Notice after an update

The person learns that the service was updated: the next time they open the page (or come back to it, or the page reloads itself after an automatic update) a dialog says so, once. Code: `services/updated-notice.js`, `routes/updated-notice.js`, `scripts/h5-shell/UpdatedNotice.jsx` (chunk `screen-updated.jsx`).

- **Recording** (at listen time in `server.js`, before `updates.start()`): the running version (`update-manager.runningVersion`) is compared with `system_state.updated_running_v1` `{ version }`. When it went up, the owner (the single user) gets `updated_notice_v1:<owner>` = `{ version, previous_version, updated_at }` (`updated_at`: this start). A notice not acknowledged yet keeps its `previous_version`, so several updates in a row are one dialog from the oldest version not seen. Nothing recorded yet: the `running_version` an older release left in `update_state` stands in (so the first update to this feature shows too); with neither (a fresh install) nothing is told. A downgrade removes the notice. The same version again (a plain restart) changes nothing.
- **Page API** (`/api/system`, session and same-origin gates): `update-status` carries `updated_notice` (true while the owner has a notice for the running version and no update is being applied), so the first screen needs no request of its own. `GET /api/system/updated-notice` -> `{ show: false }` or `{ show: true, version, previous_version, updated_at, engine_name, notes: [{ version, note }], linked: [{ id, name, version }] }`; `POST /api/system/updated-notice { version, linked?: [{ id, version }] }` -> `{ acknowledged, linked: [{ id, acknowledged }] }`, 400 `INVALID_UPDATED_NOTICE` for a malformed version. Only the version that was shown is acknowledged: an update that came in meanwhile still shows.
- **Release notes**: the "Recent versions" lines at the end of `DESIGN.md` in the install folder (`> vX.Y.Z note`, appended by `scripts/release.js`; nothing else on the server reads them), cached by the file's time and size. The versions after `previous_version` up to `version`, newest first, at most 60; a version without a line is left out; a missing file gives none. Shown in English as written (`translate="no"`).
- **Linked engines**: each engine tells about its own update. `GET` adds one line for each online linked engine that has a notice of its own ("K01 was also updated to v…"), and OK acknowledges those on them, so that engine's page does not show its own dialog again. Over the service link with the link token: `/v1/info` must list `updated-notice` (cached 10 minutes per link; an older peer is skipped), then `GET /v1/updated-notice` -> `{ pending, version, previous_version, updated_at, name }` and `POST /v1/updated-notice/ack { version }` -> `{ acknowledged }` (link tokens only, 403 `LINKED_ONLY`). 4 s per peer; a peer that fails or is offline is left out, logged once per link and code.
- **Page**: the updater (`UpdateButton`, Update.jsx) calls `showUpdatedNotice(ui)` of `lazy-screens.jsx` whenever a read of `update-status` (at start, on `visibilitychange`, every minute) has `updated_notice`. The chunk asks for the notice and draws the dialog in a React root of its own with the page's theme. Only the top page (not in a pane, whose updater is not drawn, nor in any frame). It waits while the page is hidden, another MUI modal is open (the Update dialog, an update being followed, a sheet) or a key was pressed in the last 1.5 s, so keys typed into the terminal are not taken. One dialog pattern: title "Updated to v<version>", the line "T-Agent on <engine> was updated on <date, time in the browser's zone>, from v<previous>.", the linked lines, the overline "What's new" with the notes (version in the primary colour; the list scrolls inside the dialog, at most `min(280px, 40vh)`), one text button OK. `maxWidth="xs"`: 444px on a computer, 16px margins on a phone. OK, Escape and a click outside acknowledge. The focus goes back where it was; when that was nowhere (the dialog came before the terminal took it), `ui.actions.focusTerminal` (h5.js) gives it to the terminal as the page would.
- **Not covered**: a page left open across a manual restart into new code (no reload) shows the dialog on its next read only when its own chunk names still exist; otherwise on the next load. Owners other than the single user get no notice.

Tests: `test/updated-notice.test.js` (recording, several updates as one notice, fresh install, downgrade, acknowledgement, notes of the range, a missing `DESIGN.md`, linked engines over real HTTP), `scripts/test-h5-updated-notice-browser.cjs` (390 x 844 touch and 1440 x 900: shown on load, rows and the linked line, OK and Escape acknowledge, not shown again, not when the API says no, not in a pane, the Chinese UI).
