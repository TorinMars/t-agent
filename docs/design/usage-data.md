# Usage data

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

## Usage data

Private tracking of which buttons of the page (`/` and `/h5`, its lazy chunks and the columns of the multi-column view) are pressed, so the layout can later be improved from real use: what is used most, what is never used, what is pressed after what. Each engine records the presses of its pages, and the rows of every normal machine joined by service links are one data set for the person (see "Merged across linked devices"); a company computer hands its rows over and keeps none. Nothing is sent to any outside service. The tabs Time and Memories of the same Settings group (page time, session clocks, memories and the weekly digest) are in [usage-time.md](usage-time.md).

- **Page**: `scripts/h5-shell/usage-track.mjs` (first screen, about 1.8 KB minified) and `scripts/h5-shell/usage-recorder.mjs` (a chunk of its own, `usage-recorder-<hash>.js`, loaded only while recording is on). Settings group: `scripts/h5-shell/UsageData.jsx` (in the Settings chunk).
- **Server**: `services/ui-events.js` (storage, summary, export, retention, the schema 16 columns and the change numbers), `routes/ui-events.js` (`/api/ui-events`), `services/ui-events-sync.js` and `routes/ui-events-sync.js` (`/v1/usage-sync`, the merge across linked devices), tables `ui_events` and `ui_controls` in `db/schema.sql` (schema 12; the sync columns schema 16).
- **Tests**: `test/h5-usage-track.test.js` (keys, surfaces, privacy, batches, the switch), `test/ui-events.test.js` (route, caps, login, retention, summary, export, clear), `test/ui-events-sync.test.js` (the client kind, the 15 → 16 columns, the shared switch, services joined by links over HTTP: both ways, the split by engine and client, an echo, a chain with pages, an older peer, Clear, retention, the company computer's hand-over, summary, export and offline queue, every machine marked), the 11 → 12 and 15 → 16 migrations in `test/data-home.test.js`, and `scripts/test-h5-usage-data-browser.cjs` (real presses on a computer and a phone, raw request bodies, the beacon, the switch, the Settings group, Clear and Export).

### What is recorded, and what never is

One event per activation of a button-like control: `button`, `[role=button|menuitem|menuitemcheckbox|menuitemradio|tab|option|switch]`, checkbox and radio inputs (a Switch or Checkbox counts by its input; its round ButtonBase is mapped to the input), links and labels styled as MUI buttons (`a.MuiButtonBase-root`, `label.MuiButtonBase-root`) and any `.MuiButtonBase-root` (list rows, chips, tabs, nav items, toggle buttons). One capture-phase `click` listener on the document covers every control, also new ones, without touching the ~310 handlers; Enter / Space count through a capture-phase `keydown` only on controls that are not native buttons (MUI calls their `onClick` without a DOM click: list rows, menu items, tabs). A disabled control is not recorded.

Never recorded: visible text, `aria-label`, `title`, input values, task / session / device / file names, paths, terminal text, URLs, `data-session`, `data-path` or any other data attribute outside the list below. The character keys of the on-screen keyboard (`data-char`, `Osk.jsx`) are typing and are not recorded at all, not even as a count.

Each event: `at` (ms), `key`, optional `detail`, `surface`, `view` (`sessions` | `columns` | `maps`), `layout` (`wide` | `narrow`), `input` (`pointer` | `touch`), `pane` (pressed inside a column of the multi-column view), `device` (`local` | `remote`: where the shown session runs, never its name), optional `state` (`on` | `off`: the new state of a switch, checkbox or `aria-pressed` toggle). The server adds `page` (a random id of one page load), `version` (its app version), `uid` (a random id, the identity of the press on every engine), `engine` (`''`: recorded by this engine; a peer's row keeps the instance id of the engine that recorded it) and `client` (`phone` | `computer` | `mac-app`, from the User-Agent of the request: ` T-AgentApp/` is the Mac app, iPhone / iPad / iPod / Android / Mobile a phone, anything else a computer; the User-Agent itself is never stored; rows from before schema 16 have none and count by their layout, narrow as a phone), and corrects `at` to its own clock.

### Keys

The key is the control's stable identity (`identityOf` in `usage-recorder.mjs`), in this order:

1. `data-track` (added where a control has no id: `h5-paste-text`, `h5-add-menu-command`, `h5-add-menu-key`, `h5-menu-action`).
2. The element id, cleaned (`cleanId`): React / MUI generated ids (`:r1:`, `_r_1_`, `mui-4`) are refused, a run of hex with digits (a uuid) becomes `*`, a number between dashes `#` (`h5-settings-tab-3` → `h5-settings-tab-#`), and ids that end in a name (`h5-agent-skill-install-…`, `h5-plugin-login-…`, `h5-plugins-tab-…`, `h5-notify-mode-…`) keep only the prefix plus `*`.
3. `data-action` as `action:<value>` (`action:more`, `action:approve`).
4. A fixed data attribute as `<prefix>:<value>`, only when the value is a short plain word: `data-key` → `key:Escape`, `data-modifier` → `mod:ctrl`, `data-shortcut`, `data-view`, `data-filter`, `data-group`, `data-cols`. A value with other characters (the switcher card's `data-key="remote:7|12|c1"`) is ignored.
5. Fallbacks: the element's own project class (`h5-task-item`, `h5-terminal-main`, `h5-task-more`, `h5-switcher-card`: the kind of a row, never its content), else the closest project class or `h5-` id above it with the role (`h5-header-more-menu/menuitem`), else the role alone.

`detail` (`data-track-detail`, printable ASCII, at most 48 characters) is a fixed product string of a list row: the preset command of `commands.mjs` (there is no user editing of the presets; if it comes, the detail must go), the label of a key combination, or the label of a task / session menu row when it is one of `MENU_ACTIONS` in `usage-track.mjs` and not a `raw` (name) label.

Measured in `scripts/test-h5-usage-data-browser.cjs` (visible controls): computer main screen 29 controls, 6 by their own class (the task rows' `h5-task-item`, `h5-task-more`, `h5-task-add`); with the saved commands open 47, 16 by class (the session rows and the command rows' edit pencil); phone terminal page 32, none by a fallback; the Settings group's own controls all by id.

### Surfaces

A small fixed set from the closest known container (`surfaceOf`): `settings:<group>` (or `settings` for the group list), `switcher`, `rail`, `bottom-nav`, `menu:commands` (the saved commands list), `key-row`, `keyboard` (the on-screen keyboard), `attention`, `design`, `files`, `maps`, `chat`, `task-menu`, `menu:<id>` / `dialog:<id>` (an MUI menu or dialog, by its cleaned id without `h5-`), `task-list`, `tool-row` (row 2 of a phone) or `bottom-row` (the one row of a computer or a column, the draft box), `header`, `columns`, `notice`, `page`.

### Sending

`usage-track.mjs` keeps only the target and the store's state of each press; 1.5 s after the start it reads the switch (`GET /api/ui-events/settings`, again when the page comes back after 10 minutes or more) into `state.usageRecording`. Only when it is on is the recorder chunk loaded; up to 50 presses before that are kept and then turned into events (or dropped when it is off). The recorder buffers events and sends them with `fetch(..., { keepalive: true })` 10 s after the first buffered one or at 50 events, and on `pagehide` / `visibilitychange` to hidden with `navigator.sendBeacon`. No request per press. It also reports the controls on screen (`seen`: key, surface, layout; only combinations not sent yet by this page), scanned in an idle callback 3 s after it starts and 1.5 s after each press (a press often opens a menu or dialog). The handler does no layout reads beyond `closest()`. While the switch is off nothing is buffered, scanned or sent, and turning it off drops what was buffered; a POST answered with `enabled: false` (turned off on another page) turns it off here.

### Storage and retention

In the SQLite database of each engine: `ui_events` (one row per press, indexes on `at`, `uid` (unique) and `sync_seq`) and `ui_controls` (`key`, `surface`, `layout`, `first_seen`, `last_seen`, `sync_seq`). Schema 12 made the tables; schema 16 added `uid`, `engine`, `client` and `sync_seq` to `ui_events` and `sync_seq` to `ui_controls` (`ensureSchema` in `services/ui-events.js`, run by `db/index.js` before `schema.sql`, which makes the indexes on them; rows from before get a random `uid`, engine `''`, no client and change numbers in their order). Rows older than 90 days (and controls not seen for 90 days) are deleted at start and once a day (`startRetention`, an unref'd timer), on each engine. Clear deletes both tables and writes the clear mark (`system_state` `ui_usage_clear_v1` `{ at, by, seq }`), which travels with the sync: every linked engine deletes the presses up to `at` (and the controls last seen by then), and a press at or before it is refused from then on, also one recorded later by a page whose batch was late.

### Merged across linked devices

`services/ui-events-sync.js`, the pattern of the Learn sync ("Sync across linked devices" in [learn-english.md](learn-english.md)) with simpler rows. Off on one service with `SETTINGS_SYNC_ENABLED=false` or `USAGE_SYNC_ENABLED=false` (no capability, no rounds, 404 on `/v1/usage-sync`; the data then stays on that engine).

- **Rows.** A press is its `uid` and never changes: a union. A seen control is its key, surface and layout: the earliest `first_seen` and the latest `last_seen`. The clear mark: the later `at` wins, a tie to the greater instance id. A row from a peer is checked like a batch of the page (keys, surfaces, enums, sizes) and refused when it is older than 90 days or not after the clear mark. The names of the engines whose presses a page carries travel with it (`names`, kept in `ui_usage_engines_v1`), so a summary names an engine of a chain.
- **Change numbers and pages.** Every press, control and clear mark written here, recorded or merged, gets the next number of one counter per database; the newest number is also kept in `ui_usage_seq_v1` before rows are deleted (retention, a hand-over), so the numbers never go back. Each machine keeps per link how far it has the peer's numbers (`ui_usage_sync_peers_v1`); a round pulls the peer's rows after that and pushes its own after the peer's, at most 500 per page (`PAGE_SIZE`, at most 2,000 asked). A receiver applies a row only when it changes something; what it applied gets new numbers and a round to its other peers, so a chain reaches every machine and an echo stops after one page.
- **When.** 10 s after the last stored batch or a Clear (`DEBOUNCE_MS`; 2 s on a company computer), when a link comes online, at start and every 5 minutes.
- **Transport.** `GET /v1/info` lists `usage:sync` (an older peer is skipped). Link tokens only (403 `LINKED_ONLY`). `GET /v1/usage-sync` → `{ instance_id, public_key, company, max_seq, have }`; `POST /v1/usage-sync/pull { instance_id, public_key, after, limit }` → `{ instance_id, sealed }`; `PUT /v1/usage-sync { instance_id, public_key, sealed }` → `{ applied, have }`; `GET /v1/usage-sync/summary?days&layout&engine&client` → the summary of the merged set (what a company computer shows). The page `{ events, controls, clear, names, after, next, more }` travels only inside the settings sync's AES-256-GCM envelope, with a key derived by HKDF from that link's settings-sync key (info `t-agent usage-sync v1`) and the additional data `t-agent usage-sync v1|<push|pull>|<sender>|<link id>`. Failures are logged once per link and reason (`[usage-sync] sync with <name> failed: <code>`).
- **Company computer** ("Company computer" in [linked-device-settings.md](linked-device-settings.md)). Usage data is personal data: a company computer with a normal linked machine (its home: the online normal machine with the oldest link, as for Learn) records presses here, pushes them to the home soon after (it never pulls) and deletes the presses and controls the home has (`have`). Normal machines never sync with it themselves, and its `/v1/usage-sync` pull, push and summary answer 409 `USAGE_COMPANY_COMPUTER`. Its summary is the home's (after handing its last presses over, at most 4 s), and its export the home's rows, read page by page through the sealed pull. While no normal machine is online the presses wait here, the summary and the export are those waiting presses, and Settings says so; when every linked machine is marked, or none was ever seen, it keeps its data as a normal machine does.
- **Known limits.** Times are each server's clock, so a clock that runs behind can lose a press made just after a Clear elsewhere. With an engine chosen, "Not used" compares that engine's presses with the controls seen on any engine. A database restored to an older copy is read again from the start by its peers.

### The switch

"Record button use", on by default, one choice for every linked engine: `system_state` key `ui_usage_v1` `{ enabled }`, the settings sync group `usage-record` (scope shared, so it also reaches a company computer). It is in Settings → Usage data, in the Shared tab with the "Shared across devices" label (in this device's tab when there is no Shared tab).

### API

Behind the page login and same-origin check like every `/api` route.

- `GET /api/ui-events/settings` → `{ enabled }`; `PUT` with exactly `{ enabled: boolean }` → `{ enabled }` (else 400 `INVALID_UI_EVENTS_SETTING`).
- `POST /api/ui-events` with `{ page, sent, events, seen }` → `{ accepted, enabled }`. Checked whole, any problem refuses the batch with 400 `INVALID_UI_EVENTS`: unknown fields (batch, event or seen entry), `page` not 6–32 lower-case letters / digits, more than 100 events or 200 seen entries, a key outside `^[A-Za-z][A-Za-z0-9_:#*./-]{0,79}$`, a surface outside `^[a-z][a-z0-9-]{0,23}(:[A-Za-z0-9#*_-]{1,48})?$`, a detail that is not printable ASCII of at most 48, an unknown view / layout / input / device / state, `pane` not a boolean. Times are moved by `server now − sent`; an event still older than a day or more than a minute ahead is dropped. While the switch is off: `{ accepted: 0, enabled: false }` and nothing is stored.
- `GET /api/ui-events/summary?days=30&layout=wide|narrow&engine=<instance id>&client=phone|computer|mac-app` (days 1–90; the others optional; 400 `INVALID_UI_EVENTS_QUERY`) → the merged set,
  `{ enabled, days, layout, engine, client, since, total, top, unused, next, engines, clients, data, where }`:
  - `top`: up to 10 keys by count, each `{ key, count, surfaces: [{ surface, count }], layouts: { wide, narrow }, details: [{ detail, count }] }`;
  - `unused`: controls seen in the window and never pressed there, compared per key, surface and layout, joined per key and surface: `{ key, surface, layouts, first_seen, last_seen }`;
  - `next`: for each key the most common following key within 30 s in the same page load, `{ key, next, count, followed }` (followed: how many presses of the key had any next press), the 30 most frequent;
  - `engines`: the presses of the window per engine with the other filters, `[{ id, name, self, count }]` (most first); `clients`: the same per client kind, `{ phone, computer, 'mac-app' }`;
  - `data`: the whole store, `{ count, first_at, retention_days: 90, bytes }` (size of the tables and indexes from SQLite's `dbstat`, an estimate where it is missing);
  - `where`: where the data is kept, `{ company_computer, hands_over, home_name, home_online, waiting, shared_with }` (`shared_with`: the normal linked machines that keep the same set; on a company computer that hands over, its home, whether it is online and how many presses wait here).
- `GET /api/ui-events/export` → a JSON download (`t-agent-usage-<date>.json`): `{ exported_at, retention_days, events: [...every row of the merged set with an ISO time, `engine` (instance id), `engine_name` and `client`...], controls: [...] }`, written in pieces as the rows are read.
- `DELETE /api/ui-events` → `{ cleared }`: here, and through the clear mark on every linked engine.

### Settings group "Usage data"

The last group of Settings (`usage-data` in `settings-target.mjs`; parts `usage-record` in the Shared tab, `usage-top`, `usage-unused`, `usage-store` in every tab, since the data is the same set), both layouts, `openSettings('usage-data')`. Cards, as in the mockup: the switch row; "Most used · last 30 days" with an All / Computer / Phone toggle (`#h5-usage-layout`, reads the summary of that layout) and the top keys as bars (name, surface with "· computer" / "· phone" when all presses were on one layout, a bar relative to the first, the count; on a phone the name, surface and count on one line and the bar under them); "Not used in 30 days" with chips ("Candidates to move into a menu.", a layout or surface added when it tells them apart); "Data" with the count, first date, "kept for 90 days", size, where it is kept (`#h5-usage-where`, `whereText`: "Kept on this machine only.", "Kept on this machine and on T01, as one set.", on a company computer "Kept on T01. This company computer hands its presses over and keeps none." or, with T01 away, "Kept on T01, which can't be reached right now. 3 presses wait on this computer and move there when it is back."), Clear (error colour, a confirmation dialog of the one dialog pattern: Cancel, Clear) and Export JSON (a link to the export). Readable names come from `NAMES` in `UsageData.jsx` (key → English, translated through `i18n-zh-ui.js`), `key:` / `mod:` keys read "<key> key", anything else is shown as the key itself.
