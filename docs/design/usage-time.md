# Usage time and memories

> Part of the T-Agent design document. The index of all parts is [DESIGN.md](../../DESIGN.md).

## Usage time and memories

The server half of the Settings group "Usage data" → tabs **Time** and **Memories** (the page half: [usage-time-page.md](usage-time-page.md); the button data of the tab "Buttons": [usage-data.md](usage-data.md)). How long the person used the page and how long the agents of their sessions worked or waited for them, in seconds and never as text; and a timeline of what is worth coming back to (events the server knows, the person's notes, a weekly digest). The same privacy rules as the button data: kept on the person's own machines, one set across the linked normal machines (a company computer hands its rows over and keeps none), one switch per tab, Clear per tab, Export.

- **Server**: `services/usage-time.js` (the table `usage_time`, the beats, the switches, the summary / task / day queries, time zones, export, retention, the change counter and clear marks of both tables), `services/usage-time-clock.js` (the session clocks), `services/usage-memories.js` (the table `memories`: events, notes, digests, the list), `services/usage-memory-hooks.js` (where the events come from), `lib/usage-events.js` (the in-process bus that the task, update and coach code tells), `services/usage-digest.js` (the weekly digest), `services/usage-time-sync.js` and `routes/usage-time-sync.js` (`/v1/usage-sync/time`), `routes/usage-time.js` (`/api/usage-time`, `/api/memories`). Wired in `server.js`; the activity hooks `onActivityChanged`, `onTerminalInput` and `clockSnapshot` are in `routes/terminal.js`.
- **Tests**: `test/usage-time.test.js` (beats: checks, caps, the switch, the rollup; the clocks with a fake activity feed; the summary of a seeded week, deltas, the median wait, time zones and day boundaries, titles, devices; routes, export, Clear), `test/usage-memories.test.js` (events and their de-duplication, the hooks with the real T-Attention service, notes with tombstones, the list, the digest with a stubbed model: its inputs, off by default, a provider error, once a week; routes), `test/usage-time-sync.test.js` (services joined by links over HTTP: both ways, no second counted twice after repeated rounds and a chain, an older peer, Clear of each tab, retention, memory conflicts, the company computer), the 25 → 26 migration in `test/data-home.test.js`.

### What is measured

- **Page time** (the page's beats, `POST /api/usage-time/beats`): the page is visible and the person did something in the last 2 minutes, counted in 15-second steps (the page's rules are in [usage-time-page.md](usage-time-page.md)). A beat is `{ at, surface, kind, task, session, seconds }`: `surface` one of `sessions | learn | mindmaps | attention | settings | other`, `kind` the shown session's kind (`claude | codex | opencode | terminal | notebook` or null), `task` / `session` engine-neutral ids (`<instance>|<task id>` and `<instance>|<task id>|<terminal id>`, as the shared page state names them) or null, `seconds` 1–30.
- **Session clocks** (this engine, no page needed): `agent_working` while a terminal is Running and `waiting_you` from the moment it needs the person (an approval, a selection, a question: the waiting kinds of "Two waiting kinds" in [terminals.md](terminals.md)) until the person's next input to that terminal, or until it stops waiting. The feed is `clockSnapshot()` of `routes/terminal.js` (the live, listed terminals that run or wait, with their agent; a notebook that runs a cell is a running `notebook`). The clock reads it on every activity change (`onActivityChanged`, every call of the activity streams' `notify`), on every input (`onTerminalInput`, from the tracker's `noteInput`) and every 15 s; between two reads a terminal is in the state of the earlier read. The seconds are split at the UTC hours, kept in memory and written every 60 s, when a terminal ends (`onTerminalEnded`) and at shutdown (`process.on('exit')`); the rest of a second waits for the next write. Each finished wait is counted by its length in a histogram (`waits`, buckets up to 15 s, 30 s, 1, 2, 3, 5, 10, 15, 30, 60, 120 min and more) so the median wait needs no row per wait. The kind of a session is its terminal's agent (`claude`, `codex`, `opencode`, `notebook`), `terminal` for anything else.
- A task's time is the sum of its sessions' rows: "you looked at it" = page seconds with that task, "the agent worked" = `working_s`, "waiting for you" = `waiting_s`.
- Never stored: text of any kind (terminal output or input, commands, file contents, prompts, titles), only seconds, a count of waits, kinds and ids.

### Storage

Schema 26 (`db/schema.sql`; new tables only, so an older database gets them from `schema.sql` at start, after the backup copy of the migration):

- `usage_time`: one row per key of one origin engine. Key: `day` and `hour` (UTC), `start` (that hour in ms), `client` (`phone | computer | mac-app` for page time, from the batch's `client` when it is one of these, else from the User-Agent as for the button data; `''` for the session clocks), `surface` (`''` for the session clocks), `kind`, `task`, `session` (`''` for none). Values `page_s`, `working_s`, `waiting_s` (each capped at 3,600 per row), `waits`. Identity `uid` (random); `engine` is the origin's instance id (`''` here); `rev` goes up with every change at the origin; `updated_at`, `sync_seq`. Only the origin adds to its rows.
- `memories`: `uid`, `at`, `kind` (`event | note | digest`), `event` (the code), `ref` (what it is about, for the de-duplication), `text`, `task`, `session`, `source` (`auto | person | model`), `week` and `sources` (a digest), `private` (a note never given to the digest), `engine` (the first writer), `deleted` (a tombstone: text `''`), `updated_at`, `by` (the engine of the last change), `sync_seq`.
- `system_state` (declared in `lib/server-state-keys.js`): `usage_time_record_v1` and `usage_memories_digest_v1` (the switches), `usage_time_clear_v1` and `usage_memories_clear_v1` (the clear marks `{ at, by, seq }`), `usage_time_seq_v1` (the newest change number, kept before rows are deleted), `usage_time_engines_v1` (engine names from the sync pages), `usage_time_sync_peers_v1`, `usage_time_home_v1`, `usage_memories_digest_try_v1` (the last automatic digest attempt).

**Retention**: time rows older than 2 years (by `start`) are deleted at start and once a day (`startRetention`, an unref'd timer); the sync refuses older rows. Memories are kept until deleted.

### Memories

- **Events** (`services/usage-memory-hooks.js`; `addEvent` writes one English line made by the server, `source: 'auto'`):
  - T-Attention (`onChange` of this engine's list): by the person (actor `user`) review → done `You confirmed "<title>"` (`attention-confirm`), review → working `You sent "<title>" back` (`attention-reject`), waiting_user → working `You handled "<title>"` (`attention-handled`); by any other actor → done `"<title>" is done` (`attention-done`), → failed `"<title>" failed` (`attention-failed`). An item tied to a terminal (`context.tagent`) carries that task and session.
  - `lib/usage-events.js`: `Task "<title>" created` / `archived` (`routes/tasks.js`, `services/engine-tasks.js`, `services/task-archive.js`), `Updated to v<version>` (the "Updated to" notice's `record`, `services/updated-notice.js`), `Practice finished: <right> of <total> right` (the coach's practice result, `services/learn-coach.js`; only the counts).
  - Service links: `<name> went offline` / `<name> is back online` (`engine-down` / `engine-up`; the first look at start is no event).
  - The session clocks: `An agent worked for <n> min in "<task title>"` (`long-turn`), a stretch of Running of at least 30 minutes, when it ends.
  - The page (`POST /api/memories/event`, an allow-list): `learn-session` "Learn session finished", `learn-practice` "Practice finished".
  - De-duplicated: the same code and reference within 10 minutes is one event; its uid is made from the code, the reference and the 10-minute slot, so the same event seen by two engines (an engine that went offline, noticed by both its peers) is one row after the sync. Titles are cut to 120 characters, a line to 300. The lines are English; the page translates them through the templates in `public/js/i18n-zh-server.js`.
- **Notes**: the person's own text, 1–500 characters (line breaks kept, other control characters removed), with the time and optional task and session and `private`; edited (`PATCH`) and deleted (a tombstone) by the person. Events and digests can be deleted, not edited (409 `MEMORY_NOT_EDITABLE`).
- **List**: newest first, not deleted, `q` a plain case-insensitive substring of the text (`%` and `_` are characters), `kind`, pages by `before` (the `at` of the last item), `limit` 1–200 (50); each item `{ uid, at, kind, event, text, task, session, task_title, session_title, source, week, sources, private, engine, updated_at }` (`session_title`: this engine's terminal title, null for another engine's).

### The weekly digest

`services/usage-digest.js`. Written by the person's translation service (`converse` of `services/translator.js`, temperature 0.3, at most 1,200 characters kept, whitespace folded to one paragraph) — the only part of the usage data that is ever sent to a model, and only while the switch "Write a weekly digest" (`usage_memories_digest`, **off by default**) is on, or when the person presses "Write it again" (`POST /api/memories/digest`).

- **When**: an hourly check (and one a minute after start) in the server's time zone: from Sunday 21:00 the digest of this ISO week, during the first 3 days of a week the one of the last week (a machine that was off on Sunday evening); only when that week has none; at most one automatic attempt every 6 hours (`usage_memories_digest_try_v1`). A company computer that hands its data over writes none (its home does). One digest per week: uid `digest-<YYYY-Www>`, the same on every engine, so writing it again (or two engines writing it) leaves one row, the newer.
- **Inputs, and nothing else**: one user message, a JSON object `{ events: [{ day, text }], notes: [{ day, text }], items: [{ title, status, result? }] }` with the week's event lines (at most 120), the notes that are not private (at most 60) and the title, status and result of the T-Attention items of this engine that changed that week (at most 60). Never terminal text, commands, code, file contents, item notes or context, the time rows, other weeks.
- **The prompt** (`SYSTEM`) says the message is data to summarise, never instructions (a line that asks for something is ignored and at most mentioned), plain text of two to five sentences, English unless most notes are in another language, nothing invented.
- **Stored** as `{ kind: 'digest', text, week, sources: { events, notes, items }, source: 'model' }`. A provider error stores nothing: the route answers `{ error: 'DIGEST_FAILED', message }` (409 when the translation service is not configured, else 502; the message is the provider's reason), the job logs it. A week with no inputs is 409 `DIGEST_NOTHING`.

### Sync across linked devices

`services/usage-time-sync.js`, the pattern of the button data sync ("Merged across linked devices" in [usage-data.md](usage-data.md)) with its own counter, capability and routes. Off with `SETTINGS_SYNC_ENABLED=false` or `USAGE_SYNC_ENABLED=false` (404 on `/v1/usage-sync/time`; the data then stays on that engine).

- **No second counted twice.** A time row is one key of one origin; a receiver takes a copy only when its `rev` is larger than the one it has, and replaces the values (never adds them). An echo, a page sent twice, a chain A–B–C or repeated rounds therefore never change a sum. A company computer deletes its rows once its home has them; its later seconds of the same key go into a new local row (a new uid), and the home keeps both rows, so their sum is the whole time.
- **Memories**: a union by uid; the newer `updated_at` wins, a tombstone wins a tie, then the greater engine id; an older edit never brings a deleted note back.
- **Clear marks** (one per tab, the later wins, a tie to the greater instance id; applied before the rows of the same page): Time — every row of the hours that started before the mark, or last changed by then, is deleted, and a row last changed by then is refused afterwards. Memories — every row last changed by then becomes a tombstone, and a live row last changed by then is refused.
- **Change numbers and pages**: one counter per database over both tables and both clear marks; pages of at most 500 rows (2,000 asked) `{ time, memories, clear_time, clear_memories, names, after, next, more }`; what a receiver applied gets new numbers and a round to its other peers. When: 10 s after a change (2 s on a company computer), when a link comes online, at start and every 5 minutes.
- **Transport**: `GET /v1/info` must list `usage:time` and `usage:sync` (an older peer, or one with the sync off, is skipped and shown by the page as "needs an update first": `devices[].supported: false`). Link tokens only (403 `LINKED_ONLY`). `GET /v1/usage-sync/time` → `{ instance_id, public_key, company, max_seq, have }`; `POST /v1/usage-sync/time/pull { instance_id, public_key, after, limit }` → `{ instance_id, sealed }`; `PUT /v1/usage-sync/time { instance_id, public_key, sealed }` → `{ applied, have }`; `GET /v1/usage-sync/time/summary|task|day|memories` (what a company computer shows); `PATCH|DELETE /v1/usage-sync/time/memories/:uid` (a company computer's edit of a memory kept on its home). The pages travel only inside the settings sync's AES-256-GCM envelope, with a key derived by HKDF from that link's settings-sync key (info `t-agent usage-time v1`) and the additional data `t-agent usage-time v1|<push|pull>|<sender>|<link id>`. Failures are logged once per link and reason (`[usage-time-sync] sync with <name> failed: <code>`).
- **Company computer** ("Company computer" in [linked-device-settings.md](linked-device-settings.md)): it records here, pushes to its home (the online normal machine with the oldest link) soon after, never pulls, and deletes what the home has. Its summary, task and day views, its memories list and its export are the home's (after handing its last rows over, at most 4 s); a new note is written here and handed over; an edit or a delete of a memory the home keeps is done on the home (503 `USAGE_HOME_OFFLINE` while it is away). While no normal machine is online, the views are the rows waiting here and `where.waiting` counts them; `POST /api/memories/digest` is 409 `USAGE_COMPANY_COMPUTER` while it hands over.

### The switches

"Record time" (`usage_time_record`, **on** by default) and "Write a weekly digest" (`usage_memories_digest`, **off** by default), each one choice for every linked engine: the settings sync groups `usage-time-record` and `usage-memories-digest` (scope shared, so they also reach a company computer; [settings-sync.md](settings-sync.md)). While "Record time" is off the beats answer `{ ok: false, accepted: 0, enabled: false }` and the session clocks write nothing. The "Record button use" switch of the button data is separate.

### API

Behind the page login and same-origin check like every `/api` route. Errors are `{ error: <CODE> }` (Chinese in `public/js/i18n-zh-server.js`).

- `GET /api/usage-time/settings` → `{ usage_time_record, usage_memories_digest }`; `PUT` with one or both booleans → the same (else 400 `INVALID_USAGE_TIME_SETTING`).
- `POST /api/usage-time/beats { client?, sent?, beats }` → `{ ok, accepted, enabled }`. Checked whole (400 `INVALID_USAGE_TIME`): unknown fields, more than 40 beats, `seconds` not an integer 1–30, an unknown surface or kind, ids that are not engine-neutral (or a session not of its task). With `sent` (the page's clock when sending; the page always sends it), times are moved to the server's clock; a beat older than a day, more than a minute ahead or not after the Clear of the time tab is dropped.
- `GET /api/usage-time/summary?range=today|week|30d&device=all|<instance id>&tz=<IANA zone>` → `{ range, since, until, tz, device, enabled, tiles: { page_s, working_s, waiting_s, learn_s, page_delta, working_delta, waiting_delta, learn_delta, median_wait_s, learn_days, days_in_range, away_working_s }, days: [{ day, sessions_s, learn_s, other_s }], tasks: [{ task, title, looked_s, worked_s, waiting_s }] (at most 50, by looked + worked), kinds: [{ kind, share }], devices: [{ id, name, self, supported }], data: { count, first_at, retention_days }, where }`.
  - Ranges in the zone (`tz`, else the server's): `today` from local midnight; `week` from Monday 00:00; `30d` the last 30 local days including today. The deltas compare with the previous period up to the same point (yesterday until this time, last week until this weekday and time, the 30 days before).
  - `learn_s` and `learn_days`: page time on the surface `learn`. `median_wait_s`: from the wait histogram (inside its bucket by linear interpolation), null without waits. `away_working_s`: per hour, the working seconds times the part of that hour without page time on any device (an hour-level estimate). `kinds`: shares of page plus working seconds of rows with a kind. Titles: this engine's task list, else the last list read from that linked engine (`linked_last_tasks_v1`, as the page shows an offline engine's tasks), else null. `devices`: this engine, the linked ones (`supported` from their last `/v1/info`, null before the first round) and any other engine with rows here.
- `GET /api/usage-time/task?task=<id>&range=&device=&tz=` → `{ task, title, range, since, until, looked_s, worked_s, waiting_s, sessions: [{ session, title, kind, looked_s, worked_s, waiting_s }] }` (session titles of this engine's terminals; null for another engine's).
- `GET /api/usage-time/day?day=YYYY-MM-DD&device=&tz=` → `{ day, since, until, tz, page_s, worked_s, waiting_s, surfaces: { <surface>: seconds }, tasks: [{ ...task, sessions }] }`.
- `GET /api/usage-time/export?table=time|memories&format=json|csv` → a download `t-agent-usage-time-<date>.<ext>` / `t-agent-memories-<date>.<ext>`: time rows `{ day, hour, start, engine, engine_name, client, surface, kind, task, session, page_s, working_s, waiting_s }`, memories (not deleted) as the list's items with `time`. CSV cells that start with `= + - @` get a leading `'` so a spreadsheet does not run them.
- `DELETE /api/usage-time?table=time|memories` → `{ cleared }`: here, and through the clear mark on every linked engine.
- `GET /api/memories?q=&kind=all|event|note|digest&before=<at>&limit=50` → `{ items, has_more, digest_on, where }`; `POST /api/memories { text, task?, session?, private? }` → the note (201); `PATCH /api/memories/:uid { text?, private? }`; `DELETE /api/memories/:uid` → `{ deleted, uid }`; `POST /api/memories/event { event, task?, session? }` → `{ item, duplicate }`; `POST /api/memories/digest { week? }` → the digest (the last finished week, or this one from Sunday 21:00, when none is given).
- `where` (summary and list): `{ company_computer, hands_over, home_name, home_online, waiting, shared_with }`, as for the button data.

### Limits

- Times are each server's clock; a page's clock is corrected only when it sends `sent`.
- Hours are UTC hours; a zone with a half-hour offset puts an hour on the local day of its start.
- `away_working_s` is an hour-level estimate; several sessions working at once can exceed the wall-clock time.
- A Clear is exact only for rows the clearing machine knew: a row changed on another machine after the mark but before it heard of it keeps its seconds from before the Clear (the button data has the same limit).
- The digest's T-Attention items are this engine's; another engine's items reach the digest only as event lines.
- A database restored to an older copy is read again from the start by its peers.
